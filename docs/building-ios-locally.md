# Building the iOS app locally

Everyday work needs none of this — `npm start` serves JS to an already-installed build, and Fast Refresh covers any change to `src/`, `app/`, or `server/`. This file is for the times you need a **native rebuild**, which is a genuinely different operation and has two environment traps that cost about half an hour to diagnose the first time (2026-08-27).

## When you actually need a native rebuild

Only when the native project changes underneath you:

- a dependency with native code was bumped — **including by Dependabot** (see the trap below)
- a new native module or Expo config plugin was added
- `app.json`'s native-affecting config changed (bundle id, scheme, permissions, entitlements)

Not for JS/TS changes. If the app is running and Fast Refresh works, don't rebuild.

## Trap 1: CocoaPods is broken on Ruby 4.x — set the locale

`pod install` (and so `npx pod-install`, and so `npx expo run:ios`) fails on this machine's Homebrew Ruby 4.0.2 with CocoaPods 1.16.2:

```
Unicode Normalization not appropriate for ASCII-8BIT (Encoding::CompatibilityError)
  cocoapods/config.rb:167:in 'String#unicode_normalize'
```

CocoaPods normalises the installation path and gets an ASCII-8BIT string. Force a UTF-8 locale:

```bash
cd ios && LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 pod install
```

The same prefix works on `npx expo run:ios`. The durable alternative is pinning CocoaPods to a Ruby it supports (3.3.x) via a version manager; the locale prefix is the cheap fix and has been sufficient so far.

**This failure is easy to miss.** `pod install` exits non-zero, but a pipeline like `npx pod-install | tail -20 && echo done` reports *tail's* exit code, so the crash looks like success and the next command runs against pods that were never installed. Check `$?` directly, or confirm `ios/Podfile.lock` actually changed.

## Trap 2: Dependabot bumps native packages, and nothing rebuilds

`ios/` is gitignored (regenerated by `expo prebuild`), so `ios/Podfile.lock` isn't tracked either. When Dependabot bumps a package with native code, the JS updates and the installed pods do not. **CI never catches this** — it runs typecheck, lint, format, Jest and pgTAP, and never builds an iOS app. An existing build also keeps working, because nothing recompiles until someone asks for a native build.

So the mismatch surfaces only on the next rebuild, as a compile error that looks like a bug in the dependency rather than a stale-pods problem. The instance that produced this file: `@sentry/react-native` was bumped 8.21.0 → 8.23.0 (`a107720`), pods stayed at 8.21.0, and the build failed 22 times over with

```
use of undeclared identifier 'RNSentryInternal'   RNSentry.mm
```

`RNSentryInternal` is a Swift class bridged into Objective-C. Reading that as "Sentry is broken" or "the Swift interop header isn't generating" sends you into the pod's internals; the actual cause was simply that `pod install` had never succeeded (trap 1), so the version could not move. **A compile error naming a native dependency is a stale-pods suspect first, a library bug second** — check `ios/Podfile.lock` against `node_modules/<pkg>/package.json` before anything else.

## The sequence that works

```bash
cd ios && LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 pod install && cd ..
LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 npx expo run:ios --device "<simulator name or udid>"
```

Verify the lock actually moved before rebuilding:

```bash
grep -E '^\s+- RNSentry \(' ios/Podfile.lock          # pods
node -p "require('./node_modules/@sentry/react-native/package.json').version"   # js
```

Pass `--device` explicitly. With a physical iPhone connected, `expo run:ios` can select it, which pulls in code signing and provisioning — a completely different failure surface from a simulator build, and a misleading one when you were expecting a simulator.

`npx expo prebuild --clean -p ios` regenerates the native project wholesale. It is a real reset, not a bigger `pod install`: it deletes `ios/`, **including any signing or team settings configured in Xcode for device builds**. Prefer deleting `ios/Pods` and `ios/Podfile.lock` and reinstalling, which keeps the Xcode project intact — and confirm `pod install` can actually succeed before removing what it is meant to replace.
