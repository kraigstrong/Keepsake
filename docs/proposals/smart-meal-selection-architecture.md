# Smart Meal Selection ("Help Me Choose") — Architecture Proposal

**Status:** Proposed, not yet reviewed or scheduled. **Not an ADR** — this is a pre-work-item architecture pass; specific consequential decisions inside it (marked below) will still need their own ADR once accepted, per `docs/adr/TEMPLATE.md`'s bar. Corresponds to `docs/roadmap.md`'s Unplaced item "Swipe-style meal planning."

**Naming:** the design package's user-facing name is "Help Me Choose." Backend identifiers (tables, RPCs, event names) keep the `selection_*` prefix used throughout this document — the two names refer to the same feature.

**Reconciled against the design handoff, 2026-08-19.** The Claude Design Studio package — preserved in full at [`docs/design/help-me-choose-handoff/`](../design/help-me-choose-handoff/) (`Keepsake Visual Directions.dc.html`, `Help Me Choose.dc.html` with its live drag prototype, `HELP-ME-CHOOSE.md`, `README.md`, plus that package's own copy of the PRD and design-tool support scripts) — arrived after the first draft of this proposal and is treated as guidance, not a rigid spec — exact copy and the deadline default below are the design's illustrative example, not a hard requirement. - **Confirmed, and sharpened:** votes are private during the round (blind ballots) — but the design reveals *who* chose what once the round closes ("2 of 3 chose this · Priya passed"), not just aggregate counts. Privacy is time-boxed to the round's `active` lifetime, not permanent. See §5/§7.
- **Changed:** early closing is creator-only, paired with a soft "wrap up by" deadline that auto-closes the round for everyone else. My first draft recommended open access for symmetry with This Week's editing model; the design is explicit enough here (a whole screen built around "the creator") that I'm following it instead. See §3.
- **Changed:** a "suggest a few more" action needs the round to accept new candidates and reopen after closing, which my first draft had ruled out in favor of always starting fresh. Revised in §3.
- **New:** candidate deck size scales off the "meals to find" target (design shows target 4 → deck of 12) rather than a flat number. See §5.
- **New:** push notifications ("Maya started a round," nudges, close confirmations) are assumed by the design's copy, but **no push infrastructure exists anywhere in this codebase today** — no `expo-notifications`, no device-token storage, no APNs config, confirmed by search. This is a genuine net-new capability this feature can't absorb quietly. Flagged in §12.
- I also reviewed `Help Me Choose.dc.html`'s live prototype (frame 1d) directly — real pointer-drag physics (rotation/translation tied to drag distance, fading YES/NOT-THIS-WEEK stamps, spring-back below a commit threshold). That's a pure client (Reanimated/Gesture Handler) concern with no backend implications; it just sets the interaction-fidelity bar for M6 below.

## 1. Current-state findings

**Household & membership** (`supabase/migrations/20260802120000_household_and_membership_schema.sql`) — `households(id, created_at)` has no other columns. `household_membership(id, household_id, user_id, created_at)` is flat: `unique(user_id)` means one user belongs to exactly one household ever, **no `role` column** — PRD confirms "All members have equal permissions" (`docs/prd.md:149`) and membership is fixed once joined. `my_household_id()` and `is_household_member(target_household_id)` (`supabase/migrations/20260802120200_household_rls_helper_functions.sql`) are the two shared building blocks: every RLS policy uses `is_household_member`, every mutating RPC calls `my_household_id()` to re-derive the caller's household server-side rather than trusting a client-supplied id (`docs/adr/0008-household-auth-and-server-operations.md:35`).

**Recipe schema & lifecycle** — `recipes` (`supabase/migrations/20260803100000_recipe_schema.sql`) gains `planned_count integer default 0` and two independent nullable timestamps, `archived_at`/`deleted_at` (`20260811100000_recipe_lifecycle_schema.sql`), not a status enum (ADR-0025). Standard visibility filter used everywhere selectable recipes are listed: `archived_at is null and deleted_at is null` (`src/recipes/api.ts:131-132`). A `deleted_recipes` tombstone table plus a `before delete` trigger back sync and idempotent permanent-delete.

**Weekly plan / "This Week"** (ADR-0021, `supabase/migrations/20260806110000_weekly_plan_schema.sql` + `...110200_weekly_plan_rpcs.sql`) — `weekly_plans(id, household_id, week_key, status 'planning'|'confirmed', ...)`, unique on `(household_id, week_key)`; `planning_entries(id, weekly_plan_id, household_id, recipe_id, servings→multiplier, position int, added_by, counted bool)`. Ordering is a plain reassigned integer `position`. Six RPCs cover get-or-create/add/batch-add/reorder/remove/confirm/reopen, all following the same re-derive-household pattern. `add_to_weekly_plan` locks the plan row (`select ... for update`) before computing `next_position`, added specifically to serialize concurrent adds. This Week bypasses the offline sync mirror entirely — direct Postgrest/RPC, refetch-on-focus, no Realtime anywhere in the app.

**Planned-count / cooking history** — `planned_count` increments **only** inside `confirm_weekly_plan`, gated per-entry on `planning_entries.counted = false`, making re-confirmation idempotent and forward-only. Cooking history is a fully separate append-only `cooking_events(recipe_id, household_id, cooked_at, note, cooked_by, client_event_id unique)` table with no precomputed recency columns on `recipes` — **no `last_planned_at`/`last_cooked_at`/`cooked_count` column exists**, but recency is derivable on demand via `max(cooking_events.cooked_at)` and `max(planning_entries.created_at)` (historical `planning_entries` rows persist past their week — nothing prunes them).

**Idempotency/concurrency — the canonical pattern** (ADR-0020, `finalize_import_job` in `supabase/migrations/20260806100100_import_job_fencing_rpcs.sql`): claim via an atomic `UPDATE ... WHERE status = 'processing' AND (claimed_at is null or stale) RETURNING`, minting a fresh `claim_token`; finalize takes a row lock (`select ... for update`), short-circuits to a stored-row replay if already `'complete'`, rejects a superseded `claim_token`, and calls the existing write RPC (`save_recipe`) directly as a nested `SECURITY DEFINER` call so both commit or roll back together. This is the pattern AGENTS.md names as canonical for any new multi-step state transition.

**Authorization tests** — `supabase/tests/database/weekly_plan_rpcs.test.sql` is the model: two-household fixture, JWT impersonation via `set_config('request.jwt.claims', ...)`, `throws_ok` asserting cross-household rejection and userless-caller rejection.

**Client conventions** — no global state library; per-feature `api.ts` modules wrap direct Postgrest/RPC calls; `ThisWeekScreen.tsx` is the direct precedent for optimistic UI (snapshot → apply locally → await RPC → roll back + toast on failure), used for reorder, remove-with-undo, and confirm. A batch RPC (`add_recipes_to_weekly_plan`) already exists specifically to apply multiple selections atomically rather than looping client-side — the closest existing precedent for "apply a reviewed set of selections."

**Feature flags** — `src/featureFlags/flags.ts`: a single typed, empty, build-time-only `Record<string, boolean>`; no remote/staged rollout capability exists.

**Telemetry** — `trackEvent(name, props)` is the only sanctioned call site; `AnalyticsEvent` is a compile-time string-literal union (ADR-0006) — a new event requires adding its name to that union, and `props` must never carry recipe content.

**Image fallback** — `ImagePlaceholder` renders first/underneath, an `Image` fades in on `onLoad` if a signed URL resolved; no `onError` handler, so an image-load failure just leaves the placeholder visible (passive, z-order-based fallback).

**No offline-swipe or Realtime infrastructure exists to build on** — every finding above supports treating this as online-only shared state, matching This Week's own precedent (ADR-0021/OFF-04).

## 2. Recommended domain model

Four new tables, purely additive — no changes to `recipes`, `weekly_plans`, or `planning_entries`.

**`selection_rounds`** — `id`, `household_id`, `created_by`, `mode` (`'solo'|'group'`), `status` (`'active'|'ready_for_review'|'applied'|'cancelled'`), `target_count` (nullable int, advisory — see §5), `closes_at` (nullable timestamptz — the design's "wrap up by" soft deadline; null for solo rounds, which have no deadline concept), `candidate_strategy_version` (text, e.g. `'heuristic-v1'`), `created_at`, `updated_at`, `closed_at`, `applied_at`, `applied_by`, `applied_weekly_plan_id` (nullable FK to `weekly_plans`). **Partial unique index `unique(household_id) where status = 'active'`** — at most one active round per household at a time (§12).

**`selection_round_participants`** — `id`, `round_id`, `user_id`, `completed_at` (nullable — the only state needed; "left midway" is just "still null," not a distinct state), `created_at`. `unique(round_id, user_id)`.

**`selection_round_candidates`** — `id`, `round_id`, `recipe_id`, `score` (numeric, snapshot of the ranking at generation time), `reason_codes` (text[], up to two signals in priority order — see §5), `created_at`. `unique(round_id, recipe_id)`. **No "excluded" column** — a candidate row is never mutated once written; availability is checked live at read/apply time instead (see §6), which keeps the historical deck stable for consensus math even if a recipe is later archived.

**`selection_decisions`** — `id`, `round_id`, `recipe_id`, `user_id`, `decision` (`'yes'|'no'`), `decided_at`, `updated_at`. `unique(round_id, recipe_id, user_id)`. **"Skip"/unseen is the absence of a row** — not a third stored value. This is the simplest representation that structurally guarantees acceptance criterion 7 (unseen ≠ No): there is no code path that can turn "never decided" into a persisted negative vote, because there is nothing to write.

No `left` participant state, no `applied_recipe_ids` join table (idempotent-apply is handled by the round's own `status`/`applied_weekly_plan_id`, not a separate ledger), no per-participant candidate ordering column (see §5 on presentation order).

## 3. State transitions

**Round:** `active → ready_for_review → applied`, with `active`/`ready_for_review → cancelled`, and — per the design's "suggest a few more" affordance (1j/1l) — `ready_for_review → active` via a dedicated refill operation, not a generic reopen. `applied` is terminal (no reopen; asking "why can't I undo an apply" gets the same answer as This Week's own edit-after-confirm flow — edit This Week directly).

| Transition | Who | Mechanism |
|---|---|---|
| (none) → `active` | any household member (creator becomes first participant) | `start_selection_round` |
| `active` → `ready_for_review` | **the round's creator**, or automatically once `closes_at` passes | `close_selection_round` (creator-only, atomic `UPDATE ... WHERE status='active' RETURNING`); see below for the auto-close mechanism |
| `ready_for_review` → `active` | any household member | `refill_selection_round(round_id, additional_count, new_closes_at)` — generates fresh candidates via §5's scoring, excluding this round's existing candidates, appends them, sets a **new** `closes_at` for group rounds (required, not cleared), flips status back to `active` |
| `ready_for_review` → `applied` | any household member | `apply_selection_round`, atomic `UPDATE ... WHERE status='ready_for_review' RETURNING` |
| `active`/`ready_for_review` → `cancelled` | any household member | `cancel_selection_round` |

**Why creator-only closing, unlike everywhere else in this codebase:** This Week's edit model is deliberately equal-access (any member reorders/removes any entry), and my first pass here defaulted to matching that. The design is explicit enough to override it — 1h ("Group waiting") is framed entirely around what *the creator* sees and decides, with a cost-of-closing-early note ("Priya's remaining swipes just won't count") that only makes sense as something the closer is told before they act on others' behalf. Applying (writing to This Week) stays open to any household member, matching This Week's existing precedent — only the *close-early* action is scoped to the creator. The deadline is the equalizer: anyone stuck waiting on a slow participant isn't stuck forever, they just wait for `closes_at`.

**Auto-close without a scheduler:** this codebase has no background job infrastructure, and a round's deadline doesn't need one — `close_selection_round`, `record_selection_decision`, and `get_selection_round` all check `status = 'active' AND closes_at < now()` first and perform the same atomic `active → ready_for_review` transition before proceeding, exactly as if the creator had closed it. So the round is never *stale* from the caller's point of view — the first RPC call after the deadline (a read or a write) resolves it lazily, no cron required. A push-notification-driven "closed at exactly 8:00pm" moment is a separate, currently-nonexistent capability (§12).

**Participant:** `pending (completed_at null) → completed (completed_at set)`, via `finish_selection_participation`, idempotent (setting it again is a no-op). Completing does **not** lock the ballot — a participant may still call `record_selection_decision`/`clear_selection_decision` afterward, since results are computed live at read time, not snapshotted (see §5). A round closing while a participant is still `pending` simply leaves them out of the consensus denominator; their partial decisions are retained (not deleted), but decision-writes are rejected once the round leaves `active` (a refill reopens it, so a `pending` participant can still contribute after a refill).

**Refill must not orphan a group round if the creator disappears** (Codex review, PR #84): an earlier draft had `refill_selection_round` clear `closes_at` entirely. For a group round that removes the only safety net — early-close is creator-only (above), so if the creator becomes unreachable after a refill, nobody could ever advance the round. Fixed: refill requires a **new** `closes_at` for group rounds (solo rounds still have none, matching creation). The auto-close check itself isn't creator-gated — it's a status/timestamp guard any RPC call performs — so once the new deadline passes, the round advances to `ready_for_review` on the next interaction from *any* household member, creator present or not.

## 4. Server operations and contracts

All RPCs follow the existing `SECURITY DEFINER` + re-derive-`my_household_id()` pattern; none accept a client-supplied `household_id`. `start_selection_round` and `refill_selection_round` are client-facing *Edge Function* calls, not single RPCs — see §5's "Execution boundary" for why and for the two RPCs each of them orchestrates (`create_selection_round`, `finalize_selection_round_candidates`).

- **`start_selection_round(mode, participant_user_ids[], target_count)`** (Edge Function) — calls `create_selection_round(...)` (RPC: creates the round + participant rows, creator implicit) then §5's scoring, then `finalize_selection_round_candidates(...)` (RPC: writes the resulting deck). Validates every id in `participant_user_ids` is an existing `household_membership` row for the caller's own household — a smuggled cross-household id is rejected, never silently accepted (directly satisfies the brief's "no new participant via a shareable identifier"). Solo mode ignores `participant_user_ids`. Fails clearly if a round is already `active` for the household (unique-index violation surfaced as a descriptive error).
- **`get_selection_round(round_id)`** — round + participants (with `completed_at`) + candidates, filtered to exclude candidates whose recipe is now archived/deleted from what's still presented to a participant who hasn't reached them yet.
- **`record_selection_decision(round_id, recipe_id, decision)`** — upsert on `(round_id, recipe_id, user_id)`. Rejects if `round.status != 'active'`, caller isn't a participant, or `recipe_id` isn't among that round's `selection_round_candidates` (never accepts an arbitrary recipe id). Naturally idempotent — replaying the same call just overwrites with the same value.
- **`clear_selection_decision(round_id, recipe_id)`** — deletes the caller's decision row, reverting to unseen. Backs "undo."
- **`finish_selection_participation(round_id)`** — sets `completed_at` if null.
- **`close_selection_round(round_id)`** — atomic status transition (§3).
- **`get_selection_round_results(round_id)`** — read-only, `SECURITY DEFINER`. **Rejects outright (raises, returns nothing) while `status = 'active'`** — not just an anonymized partial result (Codex review, PR #84: since this is `SECURITY DEFINER`, it bypasses `selection_decisions`' owner-scoped RLS by design, so even a *count-only* response computed mid-round would leak information the design's "write-only until close" rule promises stays hidden — e.g. two participants where a count ticking up to 1 tells the caller exactly who cast it). Only once the round has left `active` does it compute consensus across **completed participants only**, returning per-recipe `yes_count`, `completed_participant_count`, a `category` (`unanimous|majority|mixed`), and the names of completed participants who chose it (§7).
- **`cancel_selection_round(round_id)`** — status guard as above.
- **`refill_selection_round(round_id, additional_count, new_closes_at)`** (Edge Function, same shape as `start_selection_round`) — requires `status = 'ready_for_review'`; runs §5's scoring excluding recipe ids already in this round, then calls `finalize_selection_round_candidates(round_id, candidates, is_refill=true)` (the RPC that appends the new rows, sets the **new** `closes_at` for group rounds — required, see §3's refill note; null stays null for solo — and transitions to `active`, atomically). Backs the design's "suggest a few more" / "send more suggestions" actions (1j/1l).
- **`apply_selection_round(round_id, weekly_plan_id, selections[])`** — the highest-risk operation; see §6.

## 5. Smart Selection v1

Deterministic, versioned (`candidate_strategy_version`), no LLM, no new metadata — built entirely from existing columns and derivable aggregates.

**Filter** (candidate eligibility): `household_id` match, `archived_at is null and deleted_at is null`, and not already present in the current `weekly_plans`/`planning_entries` for that household — unconditional, matching `HELP-ME-CHOOSE.md`'s stated rule with no override, which settles what my first draft had left open.

**Deck size** scales off `target_count` rather than a flat number, matching the design's "12 suggestions" for a target of 4 (`deck_size = clamp(target_count * 3, 8, 24)`, defaulting to 12 when `target_count` is the default 4). This also gives the "why these" framing line (1b) real numbers to reference instead of a canned "20."

**Score** — per candidate recipe, computed once at round creation from three cheap aggregates:
- `never_planned` — no `planning_entries` row ever exists for this recipe (strong positive weight; directly serves product goal 2, "resurface forgotten recipes").
- `recency` — `max(planning_entries.created_at)` and `max(cooking_events.cooked_at)`, whichever is more recent; a small negative weight inside a fixed lookback window (e.g. 21 days) so something cooked last week doesn't dominate the deck, and neutral (no penalty) once outside that window.
- `engagement` — `recipes.planned_count`, a small positive tie-breaking weight (mild "household likes this" signal) — deliberately weighted low relative to `never_planned`, since a naive popularity weighting would fight goal 2 rather than support it.

**Diversification** — after scoring, a greedy pass selects the deck round-robining across `tags` and category `group_name` values, and additionally deprioritizing overlap with tags/categories already present in the household's *current* This Week plan (the design's 1f example: "it doesn't overlap with the pasta already in This Week" — a cheap join against the same `planning_entries` already excluded from candidacy above). Recipes with no tags/categories get no diversity bonus or penalty (never excluded for sparse metadata).

**Anti-staleness without a taste profile** — the same small household's collection will otherwise resurface the same top-scored handful every round. Mitigation: mildly deprioritize (not exclude) recipes that appeared in that household's candidate deck within the last 1–2 rounds, tracked via `selection_round_candidates` history. This deliberately uses **deck membership, not swipe outcomes** — a repeated "No" never feeds back into scoring, confirmed with the developer (§12): it satisfies "avoid repeatedly presenting the same small group" without building the explicitly out-of-scope permanent taste-profile system.

**Ties** broken deterministically via a stable hash of `(round_id, recipe_id)`, not `random()` — reproducible and testable.

**"Why this recipe?"** — the design's 1f detail screen composes a full sentence from 2–3 real signals ("You haven't made it since March, it's the only fish in the deck, and it doesn't overlap with the pasta already in This Week"). Rather than one `reason_code` enum, store up to two `reason_codes text[]` per candidate — the top-contributing signals in priority order (`never_planned`/`resurfaced` first, then `diversity`, then `this_week_variety`) — and a fixed client-side template joins whichever 1–2 are present into one sentence. Still no generation step, no LLM — just picking which true facts to mention.

**Versioning/testability** — the scoring function lives as a pure module (mirroring `server/units/parseQuantity.ts`'s runtime-neutral, side-effect-free convention) taking a snapshot of eligible recipes + their aggregates and returning a ranked list; this makes it directly unit-testable without a database, and `candidate_strategy_version` lets a future v2 change scoring without breaking the interpretability of already-applied rounds.

**Execution boundary** (Codex review, PR #84: an earlier draft left this unstated — Postgres cannot call a TypeScript module, and `start_selection_round` had been described as a single RPC that "generates and stores the candidate deck synchronously," which doesn't typecheck as an implementation). Candidate generation runs in a **new Edge Function**, the same shape as `import-recipe` — the caller's own JWT, no service-role key, RLS applies throughout — rather than inside Postgres. Concretely, `start_selection_round` and `refill_selection_round` (§4) are each a client call to this Edge Function, not a direct RPC call, and the function does three things in order: (1) call `create_selection_round(...)` (a small RPC — creates the round + participant rows, validates `participant_user_ids` against household membership, computes `deck_size`, returns `round_id`); (2) run plain RLS-scoped reads (same trust model as any client read — no new RPC needed) to gather the eligible-recipe pool and the aggregates §5 scores against, then run `server/selection/scoreCandidates.ts` in-process against that snapshot; (3) call `finalize_selection_round_candidates(round_id, candidates, is_refill)` (a second RPC — validates round/household ownership, and for a refill atomically performs the `ready_for_review → active` transition from §3 as part of the same write, mirroring `finalize_import_job`'s claim-then-finalize shape rather than introducing a new pattern). This is the same Edge-Function-uses-caller's-JWT boundary `docs/adr/0015-url-import-foundation.md` established for `import-recipe` — no new authorization pattern, just the second place in this codebase a request needs to leave Postgres to run TypeScript before writing back.

## 6. Concurrency and idempotency

- **Decisions** are collision-free by construction: only the owning `user_id` can write their own `(round_id, recipe_id, user_id)` row (RLS `WITH CHECK user_id = auth.uid()`), so there's no cross-participant race on the same row, and same-user duplicate/out-of-order swipes on the same card simply collapse to last-write-wins via upsert — acceptable for a preference toggle, unlike a financial or destructive operation.
- **Close/apply** use the same atomic `UPDATE ... WHERE status = <expected> ... RETURNING` fencing pattern as `finalize_import_job`: exactly one concurrent caller transitions the row; others observe the changed status and get an idempotent response (already-closed / already-applied) rather than a race-condition error.
- **`apply_selection_round`** is the critical path and gets the full ADR-0020-style treatment, in this exact order: (1) `select * from selection_rounds where id = ... for update`, guard `status = 'ready_for_review'` (short-circuit to a stored-idempotent-success reply if already `'applied'`); (2) **`select id from weekly_plans where id = weekly_plan_id and household_id = caller_household_id for update`** — lock the *target plan* too, before reading its entries; (3) only now read `planning_entries` for that plan and filter `selections` down to recipes that are still valid candidates of this round, not archived/deleted (re-check, don't trust the client-supplied list at face value), and not already present (silently skip duplicates rather than error); (4) call `add_recipes_to_weekly_plan(...)` **directly as a nested `SECURITY DEFINER` call**, sharing the outer transaction exactly as `finalize_import_job` calls `save_recipe`. **Step 2's lock is the fix for a real gap Codex review caught on PR #84:** an earlier draft filtered duplicates *before* acquiring any lock on the plan, so a concurrent direct add from another member (racing between the check and the nested insert) could still land a duplicate — `add_recipes_to_weekly_plan` itself doesn't recheck for existing entries, it just inserts. Locking the plan row first makes the read-then-filter-then-insert sequence atomic: any concurrent `add_to_weekly_plan`/`add_recipes_to_weekly_plan` call against the same plan (the nested call included — same session, same transaction, so re-acquiring is a no-op) blocks on that same row lock until this transaction commits, so nothing can slip a duplicate in between the check and the write. `planned_count` is untouched by apply — it still only increments at the existing `confirm_weekly_plan` step, so apply cannot double-count by construction; it's just another path onto the same `planning_entries` table.
- **Availability changing mid-round** — a candidate row is never mutated; `get_selection_round` filters archived/deleted recipes out of what's still shown to someone who hasn't reached that card yet (graceful exclusion, acceptance criterion 12), while already-cast decisions on it are preserved for consensus math (an already-decided "Yes" on a recipe someone else deletes mid-round should still count toward "3 of 4," but revalidation at apply time will drop it if it's still unavailable then).
- **Retry safety** — every write RPC here is either a pure upsert (decisions) or fenced by an atomic status-guarded `UPDATE` (round/participant transitions), so a client retry after a dropped response is always safe to replay.

## 7. Authorization and security

- Every new table's RLS uses the existing `is_household_member(household_id)` helper — no new authorization primitive.
- **Individual votes are private only while the round is `active`** — matching `HELP-ME-CHOOSE.md`'s explicit rule ("write-only until the round closes") and the design's post-close screens, which name names ("2 of 3 chose this · Priya passed"). The `selection_decisions` SELECT policy is `user_id = auth.uid()` **OR** the parent round's `status != 'active'` (a subquery against `selection_rounds`, same household match as everywhere else) — so raw per-participant votes become household-readable exactly when the round leaves `active`, never before. This raw-row policy is necessary but not sufficient on its own: `get_selection_round_results` is `SECURITY DEFINER` and therefore bypasses it entirely, so the function itself must independently refuse to run while `status = 'active'` (§4) — an aggregate is still information a mid-round caller shouldn't get, and the RLS policy alone can't stop a `SECURITY DEFINER` function from reading past it. Once a round has closed, results can now name which *completed* participants chose a given recipe, not just counts.
- **A "no" from an incomplete ballot must never be named as a pass.** `get_selection_round_results` distinguishes an explicit `decision = 'no'` row (from a completed participant — name them, e.g. "Priya passed") from no row at all (never reached that card — say nothing, never imply a negative). This is the same unseen-≠-No guarantee as acceptance criterion 7, extended to the naming logic specifically.
- Table grants: no direct client INSERT/UPDATE/DELETE on any of the four new tables — writes go exclusively through the RPCs above, consistent with the rest of the schema.
- Abuse cases specifically to test: (a) a `participant_user_ids` entry naming a user in a different household — must be rejected in `start_selection_round`, not silently dropped or silently accepted; (b) a `recipe_id` in `record_selection_decision` or `apply_selection_round`'s `selections` that was never a candidate of this round — rejected; (c) a `round_id` belonging to another household passed to any RPC — "selection round not found," same convention as cross-household recipe lookups elsewhere; (d) replaying `apply_selection_round` after success — idempotent no-op, never a second insert.
- **Isolation tests**, modeled directly on `supabase/tests/database/weekly_plan_rpcs.test.sql`'s two-household/JWT-impersonation fixture: cross-household `round_id` rejected on every RPC; cross-household `participant_user_ids` entry rejected at round creation; cross-household `recipe_id` rejected in decision-recording and in apply; concurrent-close and concurrent-apply resolve to exactly one winner (two sessions via pgTAP, or documented as a manual concurrency verification follow-up — this repo already tracks that class of gap explicitly for import fencing, see `docs/roadmap.md`'s Reliability milestone); **`get_selection_round_results` called by a participant during an active group round raises rather than returning any row** (Codex review, PR #84) — a required M4 pgTAP case, not an M4-and-later nice-to-have.

## 8. Client integration

- **Entry point:** a new route sibling to `this-week`/`recipe`/`groceries` (e.g. `app/smart-selection/`), reached from an action on the This Week screen — not a new bottom tab (the app deliberately has only two: This Week and Library). This keeps the feature clearly "supplementary," matching the brief's own framing.
- **Swipe screen:** local card-stack state with real gesture physics (drag-linked rotation/translation, fading YES/NOT-THIS-WEEK stamps, spring-back below a commit threshold — matching the fidelity of the design's live 1d prototype, implemented with Reanimated/Gesture Handler rather than the prototype's own HTML/CSS). Each swipe fires `record_selection_decision` in the background against an optimistically-advanced UI (same shape as `ThisWeekScreen.tsx`'s existing optimistic pattern) — safe because the RPC is a plain idempotent upsert, no outbox required. A toast-style undo (~4s window, per 1e) calls `clear_selection_decision` (or re-records the flipped value) for the specific recipe just swiped, which the client already knows without needing a server-side "last decision" concept.
- **Card visuals:** a recipe with a hero image uses it (per the app's existing signed-URL pattern, §1); a recipe without one gets the design's typographic card treatment with a stable accent tint per recipe, rather than the app's plain-gray `ImagePlaceholder`. The tint is derived client-side from a deterministic hash of `recipe_id` — no new schema, no server involvement, stable across sessions by construction.
- **Connectivity:** no offline swiping in v1 — same "always online" treatment as This Week (ADR-0021/OFF-04); a connectivity gate blocks entry the same way.
- **Resuming/multi-device:** trivial by construction — there's no local mirror, so reopening the round screen on any device just refetches current server state (which candidates, which decisions already made), the same refetch-on-focus precedent This Week already uses. Learning that other participants finished is also refetch-on-focus/pull-to-refresh — no Realtime subscription and no push (per the confirmed decisions above); 1h's per-participant "Remind" action is scoped down accordingly for v1 — it can only be a no-op/disabled affordance or an in-app-only nudge, not an actual push send, until push infrastructure exists as its own work item.
- **Review step:** reuses the *existing* servings/quantity confirmation UI already built for adding to This Week (the same component `AddToThisWeekScreen` uses) rather than building a parallel picker — this is what makes "review leads into the existing confirmation flow" literally true rather than merely similar. The review screen collects final multipliers per selected recipe, then calls `apply_selection_round`.
- **Feature flag:** `FLAGS.smartMealSelection` gates the This Week entry point per `src/featureFlags/flags.ts`'s existing build-time convention, removed once validated.

## 9. Data retention and migration

Purely additive migration — four new tables, their RLS policies, and the RPCs above; zero changes to `recipes`, `weekly_plans`, or `planning_entries` schemas, so no backfill and minimal regression risk to existing flows. No cleanup/expiry job for stale `active` rounds in v1 — any household member can cancel one manually, and at this app's friends-and-family scale an unbounded but small number of historical rounds is an accepted, cheap tradeoff rather than something worth a scheduled job. Historical rows are retained indefinitely; nothing here currently reads old rounds back except the deck anti-staleness check (§5), which only looks at recent history, and vote history is never read back into scoring at all (confirmed decision, §12).

## 10. Testing strategy

- **Domain:** the scoring/diversification function as a pure, database-free unit-tested module (mirrors `server/units/parseQuantity.test.ts`'s convention, runnable under Node for Jest despite also executing inside the Deno Edge Function at runtime) — recency weighting, never-planned bonus, tie-break determinism, sparse-metadata handling, deck anti-staleness. The Edge Function orchestration itself (§5) is Deno-only and untested by Jest, the same accepted gap `import-recipe` already has (AGENTS.md's canonical-commands note) — keeping the actual scoring logic in the pure module is what makes most of this milestone's real risk unit-testable at all, rather than only reachable via a live call.
- **Database (pgTAP):** one file per RPC group, modeled on `weekly_plan_rpcs.test.sql` — status-guard rejections (writing a decision to a non-active round, closing/applying twice), idempotent replay of close/apply, cross-household rejection for every id-shaped input, consensus-calculation edge cases (0 completed participants, 1 completed, exact ties, unanimous-vs-majority boundary).
- **Authorization:** the abuse cases in §7, each as an explicit `throws_ok` case.
- **API (client `api.ts` unit tests):** thin request/response mapping tests with the Supabase client mocked, matching `src/thisWeek/api.test.ts`'s convention.
- **Client (RTL):** swipe screen (decision recording, undo), review screen (reusing the existing confirm-flow component so most of its coverage is inherited), results screen (label rendering for each consensus category) — patterned on `ThisWeekScreen.test.tsx`.
- **Concurrency:** two-session pgTAP where practical for close/apply races; otherwise documented as a manual/live-testing follow-up, consistent with how this repo already treats import-fencing's "true two-connection concurrency" verification.
- **End-to-end:** a developer-driven live walkthrough (this project's standing convention for anything touching real multi-actor state) — solo round end-to-end, then a two-actor group round, deliberately paired with the still-open Journey 3 (shared household) live session already tracked in `docs/roadmap.md`.

## 11. Observability and rollout

New literal event names added to `AnalyticsEvent`'s compile-time union (`src/observability/trackEvent.ts`): `selection_round_started` (props: `mode`, `participant_count`, `deck_size` — no recipe data), `selection_participant_completed`, `selection_round_closed`, `selection_results_viewed` (props: counts per consensus category, never recipe ids/titles), `selection_round_applied` (props: `applied_count`), `selection_round_cancelled`, `selection_deck_exhausted`, `selection_no_match` (a reviewed round with zero unanimous/majority hits), `selection_technical_failure` (props: a coarse category, e.g. `'apply_failed'|'candidate_generation_failed'`). No recipe titles, tags, ids-as-content, or notes in any prop — only counts and enums, matching the existing `trackEvent` contract.

**Rollout:** `FLAGS.smartMealSelection` gates the entry point; reversible by flipping the flag and shipping a build (this repo's only rollout mechanism today — no remote toggle exists, see §1). Sequenced after Milestone 8 below, once solo and group flows have both had at least one live walkthrough.

## 12. Implementation sequence

Each milestone is one focused, independently reviewable PR.

**M1 — Schema, RLS, round skeleton.** Four new tables + RLS policies + `create_selection_round`/`get_selection_round`/`cancel_selection_round`/`finalize_selection_round_candidates` (RPCs), a new `select-candidates` Edge Function wiring `start_selection_round` end-to-end per §5's execution-boundary shape, candidate generation using only the *filter* step from §5 (no scoring/diversification yet — just household-scoped, available, not-already-in-This-Week, capped at deck size). Tests: pgTAP isolation suite (cross-household rejection on every id input), one-active-round-per-household constraint. Dependencies: none. Non-goals: no real scoring, no `refill_selection_round`, no decisions, no client UI.

**M2 — Smart Selection v1 heuristic.** Pure `server/selection/scoreCandidates.ts` module (scoring/diversification/tie-break/`reason_codes`) wired into the M1 Edge Function; `refill_selection_round` added (same Edge Function, `is_refill=true` path). Tests: domain unit tests per §5 (recency, never-planned, sparse metadata, determinism), pgTAP for refill's `ready_for_review → active` transition and required `new_closes_at` on group rounds. Dependencies: M1. Non-goals: no client-facing "why this recipe" copy yet — `reason_codes` only.

**M3 — Decision recording.** `record_selection_decision`, `clear_selection_decision`, `finish_selection_participation`. Tests: pgTAP — status guards, idempotent upsert, undo, candidate-membership validation on recipe_id. Dependencies: M1. Non-goals: no results calculation, no apply.

**M4 — Close + results.** `close_selection_round`, `get_selection_round_results` (consensus categories/labels, completed-participants-only denominator, per-recipe chooser names for a closed round). Tests: pgTAP edge cases (0/1 completed, ties, unanimous-vs-majority boundary), blind-ballot RLS verification (a participant cannot select another's raw decision row while `active`), **`get_selection_round_results` raises during an active group round** (Codex review, PR #84 — required, not optional). Dependencies: M3. Non-goals: This Week is not touched by this milestone at all.

**M5 — Apply.** `apply_selection_round`: transactional, revalidating, idempotent-on-replay, locking the round *and* the target weekly plan (§6's lock ordering — required before any duplicate-filtering, not after) before reusing `add_recipes_to_weekly_plan` as a nested call. This is the highest-risk milestone and should get the most scrutiny at review. Tests: pgTAP concurrent-apply race, availability-revalidation (archive/delete a candidate mid-flight), **duplicate-in-This-Week skip under genuine concurrency** (a second session attempting a direct add to the same plan while apply holds the lock — not just a sequential check, per Codex review PR #84), double-apply idempotency. Dependencies: M4. Non-goals: no client UI yet.

**M6 — Client: solo flow.** Entry point, swipe screen, review screen (reusing the existing servings-confirmation component), wired to M1–M5's RPCs, behind `FLAGS.smartMealSelection`. Tests: RTL for swipe/undo/review; a live Simulator walkthrough of the solo path. Dependencies: M1–M5. Non-goals: no group participant picker, no results screen.

**M7 — Client: group flow.** Participant picker (household members only), pending/completed indicators, async resume, results screen rendering the three consensus buckets. Tests: RTL for the results screen's label logic; a live two-actor walkthrough (pairable with the already-open Journey 3 session). Dependencies: M6. Non-goals: no new server capability — pure client work on top of M4's results RPC.

**M8 — Observability + rollout.** Wire the `AnalyticsEvent` additions from §11, update `docs/prd-traceability.md`, flip the feature flag once M6/M7 have each had a live pass. Dependencies: M6, M7. Non-goals: no new product behavior.

## Decisions made in this pass (settled, not open)

Most of the decisions an earlier draft of this proposal would have flagged here are now settled — either by the design handoff directly, or because they're local/reversible/consistent-with-existing-patterns calls that don't warrant stopping for:

- **Blind ballots, time-boxed to the round's `active` lifetime** — confirmed and sharpened by the design (§7).
- **Creator-only early close; any household member may apply** — settled by the design's 1h screen (§3).
- **Deck size scales off the target-meals stepper; This Week overlap is unconditionally excluded** — settled by the design (§5).
- **`ready_for_review` can reopen to `active` via an explicit refill operation** (not a generic reopen) — settled by the design's "suggest a few more" (§3).
- **One active round per household at a time**, enforced by a partial unique index — my own call, reversible (drop the index later), consistent with keeping the UI simple; not re-litigated here.
- **No Supabase Realtime; refetch-on-focus for group awareness** — matches This Week's own existing, already-accepted tradeoff (ADR-0021); not a new pattern this feature would be introducing.
- **No scheduled cleanup for stale/abandoned rounds** — manual cancel only, consistent with this product's friends-and-family operating scale.
- **Vote history never feeds future Smart Selection scoring** (confirmed directly with the developer) — only candidate-deck-membership history is used for anti-staleness (§5); a repeated "No" never becomes a taste-profile signal, keeping this clearly separate from the explicitly out-of-scope permanent dietary-preference/taste-profile system, now or in a later version.
- **No push notifications in v1** (confirmed directly with the developer) — the design's copy ("Maya started a round," nudges, close alerts) assumes push, but no push infrastructure (device tokens, APNs/FCM, a send path) exists anywhere in this codebase today. v1 ships with in-app awareness only: This Week's "Round in progress" card (1g) and refetch-on-focus stand in for the notification moments the design assumes. Real push is deliberately out of scope here — it would be its own separately-scoped work item (device token registration, a send mechanism, notification-preference UI), not a milestone folded into this feature. `HELP-ME-CHOOSE.md`'s "Notifications (copy)" section is therefore aspirational for v1, not a v1 requirement — M7's participant-status UI (1h's per-row "Finished"/"7 of 12 · started 2h ago"/"Remind") covers the same information in-app, minus the actual push delivery and the "Remind" action's nudge send.
