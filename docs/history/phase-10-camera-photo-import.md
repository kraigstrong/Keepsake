# Phase 10 — Camera and Existing Photo Import

**Result:** Pass | **Date:** 2026-08-05 | **PR:** [#29](https://github.com/kraigstrong/Keepsake/pull/29)

10 commits on `phase-10-photo-import`, merged via PR #29, all 4 CI checks green — the first real Postgres execution of every migration and pgTAP test that phase added, including the `original_photo_path`/`photo_path` xor constraint, the create-vs-edit immutability test, and the `originals/` Storage-path household-isolation test.

ADR-0017 resolved four design questions before writing code: "preserve original image" (IMG-02/03) is read as preserving what the user captured, not every byte the camera produced — the original a user gets back is EXIF-stripped and re-encoded (via a new `preserveOriginalPhoto()`, a less-aggressive sibling of Phase 4's `stripMetadataAndResize` at a 2400px/0.92-quality cap suited to a reference photo rather than a thumbnail), never the camera's raw output, since a raw photo can carry GPS/device metadata a user sharing a recipe-card photo has no reason to expect gets stored. Upload-before-processing (the client uploads the preserved original to Storage *before* calling the Edge Function, unlike every prior import path's fetch-then-process shape) means a photo survives even if extraction fails afterward, and stays under the Edge Function's request-size ceiling. Vision extraction floors at Sonnet in every environment, dev included — unlike the text path's Haiku-dev-default — since photo extraction quality varies far more (handwriting, glare, cropped pages) and this phase's own validation scope names "poor image quality cases" directly. Camera/photo import stays a single synchronous request reusing Phase 8's original call shape, not Phase 9's job/poll batch machinery — no batching need exists for one photo per capture.

Schema: `recipes.original_photo_path` (nullable, set only on `save_recipe`'s create branch — absent from the update branch's SET clause entirely, so editing a recipe can never blank out or change the preserved original; proven by pgTAP, not just documented) and `import_jobs.photo_path` (nullable, with a check constraint enforcing exactly one of `source_url`/`photo_path` is ever set, proven to hold even bypassing the RPC directly). `create_import_job` gained an optional `photo_path` parameter following the same signature-change handling ADR-0016 established (old arity dropped explicitly, not just shadowed).

`server/ai/extractRecipe.ts` gained `extractRecipeFromImage()` — a vision-input sibling to `extractRecipe()` sharing the same `RecipeExtractionSchema` and Sonnet/Opus escalation logic, with its own system prompt covering partial/illegible photos (leave sections empty rather than invent, flag ambiguous handwriting into `uncertainFields`). `supabase/functions/import-recipe/index.ts` accepts an optional `photoPath` alongside the existing `url`/`jobId` shapes: downloads the original from Storage via the caller's own JWT (never service-role), base64-encodes it (chunked, to stay under `btoa`'s practical input-size pattern for a multi-megabyte photo), extracts, and reuses the original as the initial hero image (no `og:image` equivalent exists for a photo) — `hero_image_path` and `original_photo_path` are independent from that point on, so replacing/removing the hero image (Phase 4, reused unchanged) never touches the preserved original.

Client: `src/photoImport/photoImport.ts` gained `preserveOriginalPhoto()`/`uploadOriginalPhoto()` (new `originals/` path segment under the existing `recipe-images` bucket — reuses its RLS unchanged, since policies key off the household-id path prefix only, verified rather than assumed via a dedicated Storage-isolation pgTAP test). `src/import/api.ts` gained `importRecipeFromPhoto()` with its own `photo_import_upload_failed` telemetry event, distinct from `submitImportJob`'s `import_completed`/`import_failed`, so a Storage failure during upload is observable the same way a fetch/extraction failure already is on the URL path. New `PhotoImportScreen` (Take Photo / Choose Photo, no in-app preview step since the OS camera/picker sheet already gives its own retake/confirm) replaces the Add sheet's "coming soon" placeholder for camera/photo. New `OriginalPhotoScreen` (`/recipe/[id]/original-photo`) plus a conditional "Original Photo" button on `RecipeDetailScreen`, reading `original_photo_path` end-to-end through both the live Supabase fetch (`src/recipes/api.ts`) and the offline SQLite sync mirror (local schema bumped to v5 — no resync-cursor reset needed unlike schema v3's `created_at` backfill, since photo import doesn't exist before this phase so no pre-existing row could have a real value to backfill).

A `security-check` pass (run before opening the PR) found no blocking findings — full report covered household isolation on the new Storage path (pgTAP-proven, including the specific cross-household read-denial case the Edge Function's new `.download()` call depends on), the vision-extraction prompt-injection surface (same schema-validation backstop as the existing text-path threat), and confirmed no new dependency, credential, or SSRF surface (this phase actually reduces SSRF exposure relative to URL import, since no external fetch happens anywhere in the photo path). Two threat-model entries added: T14 (vision prompt injection, same mitigation class as T5) and T15 (an uploaded original can be orphaned in Storage if extraction fails or the client abandons the flow — not a data-exposure risk, a disclosed storage-cost item). One known limitation accepted, not fixed: no dedicated client-side check for oversized/unsupported photo files beyond the `recipe-images` bucket's blunt 50MB/MIME-allowlist backstop — developer confirmed this is fine given Keepsake's actual scale (friends and family, not the general public).
