# Phase 7 — Library, Smart Sort, Search, and Filters

**Result:** Conditional Pass | **Date:** 2026-08-04 | **PR:** (merged, see `main` history — 10 commits on `phase-7-library-search` plus a cherry-picked Phase 6 exit-decision commit at the base)

ADR-0014 resolved three design questions before writing schema or client code: FTS5 tables are standalone, not external-content against `recipes` (recipes.id is a text UUID; SQLite's implicit rowid for external-content linking isn't VACUUM-stable) — `recipe_id` is a plain `unindexed` FTS5 column instead, maintained by the sync engine's delete-then-reinsert, not SQL triggers. Title-priority ranking (SRCH-02) is a strict tier (title matches, then ingredients matches, then everything-else matches, each internally bm25-ranked), not blended bm25 column weights — the Phase 1 risk spike found weighting alone doesn't reliably outrank title matches (IDF can dominate the weight multiplier). Smart sort ships 2 of its 3 tiers (Recently Added <2wk, then alphabetical remaining); the third, Frequently Selected, is an explicit, tracked gap rather than a guess — no planned-count data exists until Phase 12's This Week planning, and its storage shape isn't decided yet.

`src/db/schema.ts` migration 2 adds the real `recipe_fts`/`recipe_trigram` tables (replacing Phase 1's standalone spike schema entirely); migration 3 adds `recipes.created_at` (needed for Smart sort's Recently Added tier, distinct from `updated_at`) and force-resets the recipes sync cursor so already-synced local rows get backfilled via a real resync — the first actual exercise of an "add a column, backfill via resync" migration, which Phase 6 flagged as never having run. `src/search/buildSearchQuery.ts` rebuilt around three column-scoped MATCH queries (`title:(...)`, `ingredients:(...)`, unscoped) merged in priority order (`mergeTiers`), plus the existing typo-tolerant trigram-OR fallback carried over from Phase 1. `src/search/indexRecipe.ts` (pure) flattens a recipe into the FTS columns; `src/sync/local.ts` calls it on every upsert/delete so the index never drifts from what Library shows. `src/recipes/librarySort.ts`/`libraryFilters.ts` (both pure, both fully unit tested) implement Smart/Alphabetical/Recently-Added sort and category/tag filtering (multiple selections OR'd within a facet, AND'd across facets); `sortPreference.ts` persists the chosen sort via AsyncStorage.

`LibraryScreen` gained a debounced search box, sort chips, and a filter sheet (grouped category chips + a tag vocabulary derived from whatever's actually in the library) — three distinct empty states (truly-empty library, no search matches, filters-excluded-everything with a clear action) instead of one generic one. Search query/sort/filters live in the screen's own state, untouched by the existing focus-triggered resync, so returning to the tab never clears what was typed or selected. `searchRecipes()` now emits a `search_performed` timing event (duration + result count only, never the raw query text) for production regression visibility; `searchPerformance.test.ts` benchmarks the real schema/queries at 100/1,000/5,000 recipes via `node:sqlite` (same legitimate methodology as the Phase 1 risk spike — Jest can't exercise the real `expo-sqlite` native module, but FTS5/bm25 behavior and performance is core SQLite extension code, not iOS-platform-specific).

Ran the `security-check` skill: the search box is the only new external-input surface, and the new column-filter query construction (`title:(...)`) was separately verified (both a unit test and an ad hoc `node:sqlite` injection check against parens/colons/`NOT`/`OR`/`*`) to still treat every word as literal text, never syntax. Telemetry never carries raw query text (tested explicitly). No new server/RLS/Storage surface — search/sort/filter are 100% local reads over data the sync engine already scoped correctly.

SRCH-01/02/03/04/05, LIB-03, LIB-04, OFF-02 → `Done (tested)`. LIB-01/LIB-02 → `In Progress` (Frequently Selected tier/option deferred to Phase 12, tracked not guessed). `searchCorrectness.test.ts` (added during exit review, prompted by scanning execution-plan.md's Release-Blocking Defect Rules) directly proves exact-multi-word-title findability and title-ranks-above-ingredients-only, against the real schema/tokenizer via `node:sqlite` — closing a real evidence gap for the "Exact titles are not findable" High-severity defect that neither the query-builder unit tests nor the performance benchmark happened to cover. 61 suites, 356 passed, 1 skipped; typecheck/lint/format clean; `npm audit --omit=dev --audit-level=high` exit 0 (11 moderate-severity findings only, same category as prior phases). No live Simulator/device verification this phase — Jest evidence only.
