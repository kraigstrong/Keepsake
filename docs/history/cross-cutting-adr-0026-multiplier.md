# Multiplier as the Canonical Recipe-Scaling Unit (ADR-0026)

**Result:** Merged | **Date:** 2026-08-12 | **PR:** [#51](https://github.com/kraigstrong/Keepsake/pull/51) — cross-cutting, not a numbered phase

ADR-0026 (written during Phase 16 walkthrough-feedback work, PR #50) replaced `planning_entries.servings` (an absolute integer every downstream reader had to divide by `recipes.servings_count` to recover a scale factor — a field that's `null` by design, ADR-0018, whenever a recipe's yield isn't a servings count at all) with `planning_entries.multiplier`, stored directly. PR #50 shipped a stopgap (`ASSUMED_SERVINGS_WHEN_UNKNOWN`/`DEFAULT_SERVINGS_WHEN_UNKNOWN`, both assuming the same fallback base on both ends of a round-trip); this work implements the ADR's real fix and removes that stopgap entirely. Full rationale and alternatives considered live in the ADR — this entry is what shipped, not why.

New migration `supabase/migrations/20260812150000_planning_entries_multiplier.sql`: adds `multiplier numeric not null default 1.0 check (multiplier > 0)`, backfills existing rows (`servings / recipe.servings_count` where known, else `servings / 4` — see the ADR's PR #51 amendment below for why `4`, not `1.0`), drops `servings`. `add_to_weekly_plan`/`add_recipes_to_weekly_plan` take `multiplier`/`multiplier_list` instead of `servings`/`servings_list` — the old `integer`-typed overloads are dropped, not just replaced, since Postgres treats `(uuid,uuid,integer)` and `(uuid,uuid,numeric)` as distinct signatures.

Every downstream reader follows: `generateGroceryList.ts`'s `multiplierFor()` (a division with an assumed-base fallback) is gone, `PlanningEntryForGroceries.multiplier` is read directly. `CookingModeScreen`'s plan-default drops its `planServings / (recipe.servingsCount ?? DEFAULT_SERVINGS_WHEN_UNKNOWN)` division for a direct read. `RecipeDetailScreen`'s `servingsToAdd` (a derived absolute count) is gone — `handleAddToThisWeek` sends the screen's own multiplier state as-is. `ThisWeekEntry` gains `servingsCount` (the recipe's own field) so This Week's rows can show "Serves N" when known and "N×" otherwise (decision 6) — the same conditional `RecipeDetailScreen`'s `timingParts` already applied to its own scaling state.

`AddToThisWeekScreen`'s servings step went further than a rename: per decision 3, a recipe with a known `servingsCount` keeps its numeric stepper (converted to a multiplier at submit), but a recipe without one now shows the same preset chips (`SCALE_PRESETS`) `RecipeDetailScreen`'s own scaling controls already offer, instead of the screen's prior `DEFAULT_SERVINGS = 4` fallback — the same bug class this ADR closes everywhere else, just not one of the three call sites PR #50's stopgap had patched.

`ASSUMED_SERVINGS_WHEN_UNKNOWN`/`DEFAULT_SERVINGS_WHEN_UNKNOWN` and every stopgap comment citing "PR #50"/"assumed base" are removed — there is no absolute count left anywhere in this path to divide back out of.

Evidence: full local CI sequence green (`typecheck`, `lint`, `format:check`, 109 Jest suites / 968 tests, `check:client-secrets`); one new pgTAP case (`weekly_plan_rpcs.test.sql`, fractional-multiplier round-trip) plus renamed error-message assertions across the three RPC-touching pgTAP suites. `npm run db:test` was not run locally (no Supabase/Docker in the session that built this) but ran green in CI ("Migration apply/reset and RLS tests") on push — that check runs against a fresh schema, though, so it couldn't have caught the backfill-formula bug below (nothing to backfill on an empty table); Codex review caught that one instead. Per ADR consequence 2, this is a real breaking schema/RPC change (not backward-compatible), so client and server need a synchronized deploy, not a rolling one.

**Codex review, PR #51 (P2, fixed):** the backfill's "else `1.0`" branch (as ADR-0026 itself specified) silently reset any existing non-1x selection on a recipe with no parsed servings count — PR #50's stopgap had already stored `servings = round(4 * multiplier)` for exactly that case, and grocery generation / Cooking Mode both divided by that same `4` to recover the multiplier, so `1.0` was actual data loss, not a neutral default. Fixed to divide by `4` in that branch too, matching what those two consumers already trusted for these rows. See the ADR's own amendment for the full account.

No PRD traceability changes: `UNIT-05`/`WEEK-02` describe user-facing servings behavior, which is unchanged (still "choose servings" as the input UX wherever a recipe has one) — this is a storage-representation change only.

Migrations pushed to staging post-merge (`supabase db push`), along with the previously-stranded `20260811204300_reopen_emptied_confirmed_plan.sql` that had never been applied — `supabase migration list` confirms local and remote now match exactly. No edge function redeploy needed: `import-recipe` (this repo's only one) doesn't import `server/groceries/*` or `server/units/scaleQuantity.ts`, since grocery generation is client-side, not a function.
