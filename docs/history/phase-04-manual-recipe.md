**Result:** Conditional Pass | **Date:** 2026-08-03 | **PR:** [#17](https://github.com/kraigstrong/Keepsake/pull/17)

ADR-0010: recipe data model decisions (sections as separate ingredient/instruction table pairs with plain-text lines, not structured quantity/unit — that's Phase 11's job; categories as a seeded lookup table, not an enum or free array; tags as plain `text[]`; no versioning/lifecycle/AI this phase). Schema + RLS for `recipes`/`recipe_ingredient_sections`/`recipe_ingredients`/`recipe_instruction_sections`/`recipe_instructions`/`categories`/`recipe_categories`, `household_id` denormalized onto every child table so RLS stays a flat `is_household_member(household_id)` check everywhere (ADR-0004: a recipe's household never changes). Single `save_recipe` RPC handles both create and edit atomically — wipes and reinserts child rows on edit rather than diffing, since child rows have no external identity; pgTAP proves real atomicity (an invalid category mid-write rolls back the whole recipe, not just the bad row) alongside cross-household denial and no-household denial. Client `src/recipes/api.ts` wraps the nested-embed read and the RPC write. Hero image handling (`src/recipes/heroImage.ts`): native square-crop UI via `expo-image-picker`, an explicit `expo-image-manipulator` resize+re-encode pass (strips EXIF as a side effect — SEC checklist item, not incidental), upload to the Phase 3 `recipe-images` bucket keyed by a random id (not the recipe's own id, since a hero photo can be picked before a new recipe has an id yet), and a signed-URL helper for display since the bucket is private. `RecipeEditorScreen` (create and edit share one screen/form) and `RecipeDetailScreen` (read-only) as testable `src/recipes/` components with thin `app/recipe/` route wrappers; `LibraryScreen` rewritten to fetch real recipes on tab focus (not just mount, so returning from create/edit shows the change) with loading/error/empty states; the global Add sheet's "Create manually" option now actually navigates to `/recipe/new` instead of showing a placeholder.

Found and fixed a real bug while writing this phase's end-to-end route tests: `app/_layout.tsx`'s `Stack.Protected` block only listed `"(tabs)"` and `"settings"` — the new `recipe/*` routes existed on disk and were fully unit-tested in isolation, but were never registered under the authenticated Stack, so `/recipe/new` and friends were unreachable in the real app despite looking complete. Added `app/recipe/_layout.tsx` (mirrors Settings' header styling) and registered it; `src/navigation/recipeRoutes.test.tsx` now exercises create/detail/edit through the real router, which is what caught it.

## Conditional Pass follow-ups (tracked until closed)

Phase 4 exited **Conditional Pass** (developer decision, 2026-08-03) — build scope and automated test coverage are real and complete, but two things couldn't be verified in this sandboxed environment:

1. **No live iOS Simulator demonstration.** Every phase's exit gate calls for Simulator evidence by default (execution-plan.md §3.6); this phase only has Jest evidence (component tests + `expo-router/testing-library` end-to-end route tests). The installed build in this environment's Simulator predates `expo-image-manipulator` (this phase's new native dependency) and would need a fresh `pod install` + rebuild, plus a real sign-in — no staging Supabase reachable here, discussed with the developer at exit review.
2. **Migrations and pgTAP have never actually executed anywhere.** Same category Phase 3 hit — no Docker in this environment, so `recipe_isolation.test.sql` and `save_recipe_rpc.test.sql` are written and reviewed but unexecuted until real CI runs them on the PR.

**Conditional Pass, not Pass**, because at exit time neither a live Simulator demonstration nor real migration execution (no Docker in this environment) could happen.
