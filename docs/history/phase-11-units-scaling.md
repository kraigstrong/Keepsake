# Phase 11 — Units, Scaling, and Quantity Integrity

**Result:** Conditional Pass | **Date:** 2026-08-05/06 | **PR:** [#31](https://github.com/kraigstrong/Keepsake/pull/31)

6 commits on `phase-11-units-scaling`. ADR-0018 resolved five design questions before writing code: quantity is parsed once and stored as structured columns (`recipe_ingredients.quantity_min/quantity_max/unit/ingredient_text`), not re-parsed on every render, with `line_text` kept as the immutable fallback — a line the parser can't confidently read leaves every structured field null and always displays as original text, never guessed at; parsing itself is a pure `server/units/` module run at the call site (client manual entry, Edge Function AI-extracted lines) before `save_recipe`, not inside the RPC, following the established `server/import/*.ts` shared-pure-module pattern; the unit vocabulary is closed and split by measurement class (volume/mass), so a mass↔volume conversion is structurally unreachable, not just discouraged; "Preferred" is a global `profiles.preferred_unit_system` (US Customary/Metric) with the Original/Preferred toggle living as local `RecipeDetailScreen` state; `recipes.servings_count` is parsed from `yield_text` only when it clearly names a single serving count, leaving ranges and non-serving yields (`"makes one 9x13 pan"`) to the ½×–4× presets alone. A real design gap was caught and fixed mid-build, not shipped: `restore_recipe_version` replays historical `recipe_versions.snapshot` JSON back through `save_recipe`, and pre-Phase-11 snapshots have the old string-shaped ingredient lines — `save_recipe`'s insert now branches on `jsonb_typeof` so a pre-Phase-11 version still restores (as an unparsed line) instead of hitting the new `line_text` not-null constraint, with a dedicated pgTAP test proving it.

Schema: `recipe_ingredients.quantity_min/quantity_max/unit/ingredient_text` (unit a closed check-constraint vocabulary, not a lookup table like categories — a safety property, not a taxonomy), `recipes.servings_count`, `profiles.preferred_unit_system` (`not null default 'us_customary'`). `save_recipe`'s ingredient-line payload changes from a bare string to an object carrying the parsed fields. `server/units/`: `parseQuantity.ts` (fraction/range/unit/remainder, ascii and unicode vulgar fractions, a closed unit-synonym table, an extreme-value guard), `quantityVocabulary.ts` (the closed unit table + exact same-class conversion factors + unit labels), `convertUnit.ts` (cross-system conversion picking a best-fit target unit, same-system values left untouched), `scaleQuantity.ts` (multiplier, handles ranges), `formatQuantity.ts`/`formatIngredientLine.ts` (kitchen-friendly fraction/decimal rounding with a never-zero floor and an approximation indicator), `parseServings.ts`. A 71-test fixture corpus in `parseQuantity.test.ts` plus focused suites per module.

Client: both `save_recipe` call sites (`RecipeEditorScreen`, `import-recipe` Edge Function) parse before saving; `Recipe`/`RecipeSavePayload`/`SyncedRecipe`/local-SQLite types (schema v6) carry the structured fields end to end, offline included; `RecipeDetailScreen` gains the Original/Preferred toggle, ½×–4× preset chips, and an arbitrary-serving-count stepper (screen-local state, reset on recipe navigation via React's adjust-state-during-render pattern rather than a setState-in-effect cascade, to satisfy the stricter `react-hooks/set-state-in-effect` lint rule); `SettingsScreen` gains the unit-system preference control and the first real `profiles` UPDATE this app has needed (`src/household/api.ts`'s `updateProfile`, using the existing own-row RLS policy from Phase 3 — no new RPC).

A `security-check` pass found no blocking findings: no new dependency, no new RLS surface (new columns inherit existing row-level scoping), the new `profiles` UPDATE path tested for cross-user denial. Threat-model T16 added: the parser as a new consumer of AI-extracted text, mitigated structurally (never guesses, closed vocabulary, never reads instruction text) rather than by trusting the AI. UNIT-01 through UNIT-06 → `Done (tested)`. Existing (pre-Phase-11) `recipe_ingredients` rows keep their structured fields `null` until next edited and re-saved — no bulk backfill migration was written, since that would mean a second parser implementation in plpgsql purely for one-time use; those lines display as unparsed (their original text) until then, the same safe fallback as any other unparsed line.

**CI's first real run against PR #31 caught three real issues in one pass**, none of which local `tsc`/Jest could have caught: (1) Deno — which bundles the `import-recipe` Edge Function — requires explicit `.ts` extensions on every local relative import; `server/units/`'s internal cross-file imports (`parseQuantity.ts` → `quantityVocabulary.ts`, etc.) are the first case of one `server/` module importing a sibling rather than being self-contained, so this had never been exercised before (fixed by adding the extensions plus `allowImportingTsExtensions` in `tsconfig.json`). (2) A genuine regression: the `save_recipe` rewrite was based on Phase 5's version of the function and silently dropped Phase 10's `original_photo_path` handling entirely — both the create-branch insert and its deliberate absence from the update branch (ADR-0017's immutability guarantee) — caught by Phase 10's own pgTAP test failing, not a new test written this phase; fixed by diffing the two function bodies field-by-field against Phase 10's migration. (3) A wrong test assertion, not a schema bug: `units_scaling_schema.test.sql` expected alice's UPDATE against bob's profile row to throw, but Postgres RLS's `USING` clause on UPDATE silently filters non-matching rows from the candidate set (0 rows affected) rather than raising the `WITH CHECK` violation an INSERT would — fixed to `lives_ok`. All 4 CI checks green after the fixes.
