# Phase 11.5 — Import Concurrency and Local Data Isolation

**Result:** Conditional Pass | **Date:** 2026-08-06/07 | **PR:** [#33](https://github.com/kraigstrong/Keepsake/pull/33)

7 commits on `phase-11.5-hardening`. ADR-0020 resolved three fixes for defects an external code review surfaced (KS-002, KS-003/KS-004, KS-005), inserted as its own phase — following the Phase 3.5 precedent — rather than folded into Phase 12, since none of them belong to a numbered phase's build scope and all three needed closing before more import/sync work stacked on top. KS-001 (a fourth defect from the same review, `original_photo_path` dropped from `save_recipe`'s create branch) turned out to already be fixed — Phase 11's own real-Postgres CI run had independently caught and fixed the identical regression before merge (commit `c5158b3` on PR #31).

`accept_invitation` (Phase 3, already shipped) gained `for update` on its initial invitation lookup — closes a read-check-then-write race where two different users racing the same single-use token could both redeem it. `import-recipe`'s `save_recipe`+`complete_import_job` two-call sequence (a recurring atomicity gap in this codebase — the same bug class as KS-001) is replaced by one call to a new `finalize_import_job`, which calls `save_recipe` directly from inside its own transaction (nested `security definer` calls share the outer transaction, no logic duplicated) so a failure partway through rolls back both together instead of leaving a real recipe paired with a stuck job. `claim_import_job` now generates a `claim_token` fencing value on every claim, checked by `finalize_import_job`/`complete_import_job`/`fail_import_job` alike, so a worker superseded by a reclaim can no longer act on a job it no longer holds; the staleness window moved 60s → 180s since fencing, not the window, is what makes a late completion harmless now.

Local SQLite reads (`offlineRecipes.ts`, and `recipe_fts`/`recipe_trigram` search, which now join back to `recipes` for the first time) are household-scoped, making that filter — not a successful sign-out wipe — the real local-data authorization boundary; `LibraryScreen`/`RecipeDetailScreen` now wait for the live household context before any local read, a deliberate tradeoff over a locally-cached fallback that would reopen a smaller version of the same leak. `import_outbox` (local schema v7) gained a nullable `household_id`, stamped when drained while a household is known — a null value (signed-out capture) preserves Phase 9's existing "submits under whoever signs in next" design unchanged, but a row already stamped for one household can no longer auto-submit under a different one.

Threat-model gained T18 (invitation race), T19 (import finalization atomicity/fencing), T20 (local cross-account data isolation). No PRD requirement ID maps cleanly to any of the three fixes — internal correctness/security properties, not new product requirements — so `prd-traceability.md` is unchanged. A `security-check` pass found no blocking findings, explicitly framing KS-005 as client-side defense-in-depth against stale-cache disclosure on a shared/reused device, not a substitute for server-side RLS (unchanged, still the real enforcement boundary).

**Codex review on PR #33 caught two real issues, and correctly flagged a documentation inconsistency, all addressed before merge:**
1. A `SELECT public.save_recipe(...) INTO result_recipe` in `finalize_import_job` called a composite-returning function as a bare scalar expression — Postgres doesn't decompose that into the row variable's columns, it crams the whole stringified tuple into the first field (`id`, a uuid) and fails to parse it. Caught by real CI, not local review. Fixed to `select * into result_recipe from public.save_recipe(...)`, matching the composite-capturing idiom used everywhere else in this codebase.
2. A real deploy-ordering hazard: the migration drops `complete_import_job`/`fail_import_job`'s old signatures, so applying it *before* redeploying the Edge Function (rather than after) could reproduce the exact orphaned-recipe/stuck-job bug this phase fixes, during the gap. Documented as a required deploy order (function first, then migration) rather than solved with RPC versioning — disproportionate to this app's manual, low-traffic deploy model.
3. A TOCTOU gap in the outbox submission loop: `submitPendingOutboxItems` snapshotted the submittable list once, but a fast account switch mid-drain could submit a later item under a different household's session. Fixed with a live `getCurrentHouseholdId` recheck before every item, wired through a ref in `app/_layout.tsx`.
4. The ADR's own text had promised an adoption-confirmation prompt for signed-out outbox captures that the implementation never built — corrected the ADR to describe what was actually shipped (preserving Phase 9's existing behavior for that case) rather than promise a confirmation screen out of proportion to this hardening PR's scope.

A second test-fixture bug (a household-level import cooldown collision in the new pgTAP fixtures, not backdating a prior job's `created_at` the way `import_jobs.test.sql` already does) was also caught by real CI and fixed. All four CI checks green after fixes; merged.

82 suites, 656 passed, 1 skipped; typecheck/lint/format clean; `check:client-secrets` clean on every commit. Migrations/pgTAP ran for real in CI this phase and caught two genuine bugs (see above) — the sandboxed-environment gap Phase 9/11 also hit.

## Conditional Pass follow-ups (closed at merge)

Phase 11.5 exited **Conditional Pass** (developer decision, 2026-08-06) — build scope and client-side automated evidence were real and complete at exit-review time, but two things couldn't be verified in the sandboxed authoring environment:

1. **Migrations/pgTAP unexecuted against real Postgres.** Resolved by PR #33's actual CI runs, which caught the two real bugs described above.
2. **True two-connection concurrency** (the invitation-redemption race, KS-002; import-claim fencing, KS-004) isn't provable inside pgTAP's single-transaction model. Still open as a manual staging check (two `psql` sessions racing the same call) — worth running once staging is reachable, before considering T18/T19 fully closed.
