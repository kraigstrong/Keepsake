# Phase 9 — Safari Share Sheet and Bulk URL Import

**Result:** Conditional Pass | **Date:** 2026-08-05 | **PR:** [#27](https://github.com/kraigstrong/Keepsake/pull/27), staging deployment via [#28](https://github.com/kraigstrong/Keepsake/pull/28)

16 commits on `phase-9-share-extension`, all 4 CI checks green — the first real execution of every migration this phase added.

ADR-0016 resolved four design questions before writing code, adopting Phase 1's `durable-import-submission.md` design as-is for the parts it already covered: the local outbox is a separate SQLite table explicitly excluded from `wipeDatabase()`'s table-name list (not the whole-file drop Phase 6 used) — an unsent share is the only copy of that share until the server confirms it, so it must survive sign-out, unlike the rebuildable recipe mirror; bulk paste is a direct online RPC call (`create_import_batch`), not routed through the offline outbox, since it has none of the background-process/no-session-guarantee failure modes the outbox exists for; `create_import_job`/`create_import_batch` both gained a client-generated idempotency key (`client_import_id`/`client_batch_id`) with the Edge Function skipping its whole pipeline on a replay hit — no second fetch, no second Anthropic charge; and progress is a polled `import_jobs`/`import_batches` read, not a held-open request, which is what makes "leave-and-return" actually work. A real design gap was caught and fixed mid-build, not shipped: `create_import_batch` originally required pre-normalized URLs, but normalization (`server/import/normalizeUrl.ts`) is Deno/server-only code the client can't run — fixed by storing a same-as-source-url placeholder and having the per-item Edge Function call (which already does this for the single-URL path) compute the real value.

Schema: `import_batches` + `import_jobs.client_import_id`/`.batch_id` (Postgres), `import_outbox` (local SQLite, schema v4). `supabase/functions/import-recipe/index.ts` extended to accept an optional pre-created `jobId` (a batch item) alongside Phase 8's original `url` shape, plus `clientImportId`, with Phase 8's own call site untouched. `targets/share/ShareViewController.swift` now writes one `<uuid>.json` per share into a `share-inbox/` directory instead of one fixed file (fixes the Phase 1 spike's known "second share overwrites the first" gap) and changes the 0.6s text-only auto-dismiss to 1.5s with a checkmark and a success haptic (the Phase 1 physical-device finding that the old confirmation "just disappeared"). `src/import/outboxEngine.ts` drains the App Group queue into the outbox unconditionally (no auth needed, must survive being captured signed-out) and submits pending items gated on household/connectivity, treating the existing 5s-cooldown/30-per-hour-cap guards as retry-later rather than permanent failures, and expiring anything unsubmitted after 30 days (execution-plan.md's "Staging data expires" security item) rather than keeping it forever. `src/import/batchEngine.ts` fires each batch job's Edge Function call with concurrency capped at 3. Two new screens: `BulkImportRecipesScreen` (multi-line paste box, developer's chosen UX over a repeatable-row form or Share-Sheet-multi-select) just reserves the batch and hands off; `ImportActivityScreen` (`/recipe/import-batch/[batchId]`) does the actual per-item work and polls for live progress, resuming any still-`processing` job on a return visit — safe by construction since the Edge Function only ever processes a given job id once.

IMP-02 → `Done (untested)` (real code, real unit tests where Jest can reach it, but the Swift path itself is unverified — see Conditional Pass follow-ups); IMP-03 → `Done (tested)` (bulk import has no native dependency, so it has full coverage: `parseBulkUrls` pure-function tests, RPC pgTAP, screen-level RTL tests, and the batch engine's concurrency behavior). Two threat-model entries added: T12 (idempotent replay prevents a retried/duplicated submission from creating a second recipe or double-charging Anthropic) and T13 (the batch RPC's 20-URL cap plus an atomic check against the existing hourly cap, so bulk import can't be used to exhaust or probe the rate limit one item at a time). 73 suites, 507 passed, 1 skipped; typecheck/lint/format clean; `npm audit --omit=dev --audit-level=high` exit 0; `check:client-secrets` clean.

## Live Simulator verification, 2026-08-05

Built for real (`expo prebuild` + `pod install` + a real `xcodebuild`, not just written and assumed) and ran the actual flow on a booted iPhone 17 Pro Simulator — the first time this session's environment turned out capable of that (prior phases' notes assumed no Simulator access here). `ShareExtension.appex` compiled and embedded in `Keepsake.app/PlugIns/` correctly.

**Confirmed working, live:** Safari's Share Sheet showed "Keepsake" as a real registered extension (not just a config file). Sharing a page wrote a real `<uuid>.json` file into the App Group's `share-inbox/` directory with the correct `{id, url, receivedAt}` shape. A second share immediately after produced a *second*, distinct file rather than overwriting the first — directly confirms the Phase 1 spike's known bug is fixed. Force-quitting and relaunching the app drained files out of the App Group queue into the local SQLite outbox and correctly emptied the queue directory. Outbox rows went all the way through the real pipeline — outbox → Edge Function → a live `secureFetch` of the shared URL → a real HTTP response → correctly recorded back, both success and failure cases — proof the `clientImportId` idempotency plumbing and the full submission path work against the deployed backend, not just Jest mocks.

**Not yet confirmed:** the 1.5s+checkmark+haptic Share Extension confirmation UI — screenshots kept landing just after it would have shown. The file-write succeeding (which gates that code path) makes it very likely correct, but "likely" isn't "confirmed" the way everything else is.

**Five real gaps found live and fixed this same session:**
1. A Share-Extension-originated import had no user-visible signal at all once the background drain/submit finished — no screen, no toast, nothing; the developer had to ask "where did it go?" to surface this. Fixed: `submitPendingOutboxItems()` now returns per-item outcomes, and `app/_layout.tsx` shows a toast summarizing them via the existing `ToastProvider`.
2. A recipe's hero image can silently vanish after import. Root cause: a **pre-existing Phase 6 bug**, not Phase 9's — both `ensureImageCached` and `readCachedImageUri` trusted a `cached_images` row's `local_uri` without checking the file still exists, and iOS is documented to purge `Library/Caches/` under storage pressure at any time — exactly where hero images live (ADR-0013). A live, latent bug for any real user, not just this session's repeated terminate/relaunch testing (which happened to reproduce it reliably). Fixed: `ImageStore` gained `fileExists(uri)`, checked before trusting a cache hit.
3. The hero image's first-view load was a genuine layout jump (a 200×200 placeholder swapping to a full-width 200-tall image), not just a content pop, and the fallback path never cached what it fetched — meaning a just-imported recipe re-fetched and re-downloaded its image from the network on *every* view, not just the first. Fixed: the placeholder is now sized to match the real image and stays mounted underneath, crossfading the image in on load; the fallback path now caches via `offlineRecipes.cacheHeroImage`.
4. Drain/submit only ran on cold launch or network reconnect — not a plain foreground, which is the actual realistic path ("share from Safari, switch back to Keepsake," not force-quit-and-relaunch). Confirmed live: a share sat undrained in the queue for a full minute until the app was foregrounded. Fixed: `ImportOutboxLifecycle` now also listens for `AppState` transitioning to `'active'`, mirroring `SessionProvider`'s existing pattern.
5. **The serious one**: sharing one URL produced two separate recipes, 3 seconds apart, from a single outbox entry. The existing idempotent-replay check only protects against replaying an *already-finished* job — it does nothing when two concurrent callers both find the same job while it's still genuinely in flight (very plausibly made easier to hit by fix #4 adding another trigger point). Both calls ran the full pipeline independently, each creating its own recipe. Fixed with `claim_import_job` — an atomic, single-winner claim (60s staleness window) — plus a `recipes(household_id, source_url)` partial unique index as a database-level backstop independent of the specific fix. This is the same underlying issue previously tracked as an unexplained "double-processing" delay (self-healing, no visible data loss) — it wasn't harmless, it just hadn't produced a visible duplicate yet. (The 60s window and the underlying fencing gap were later revisited in Phase 11.5/ADR-0020.)

## Staging deployment, 2026-08-05 (post-merge)

`supabase db push` applied all 6 of this phase's migrations to staging for the first time. The last one (the `recipes` uniqueness backstop) initially failed — the exact duplicate recipe from finding #5 above was still sitting in staging's real data, blocking the constraint from being created. Investigated before touching anything: both duplicate rows turned out to have their own independently-completed `import_jobs` record (not one orphaned, as first assumed), so `import_jobs.recipe_id`'s foreign key — no cascade — would have blocked a plain delete either way. Presented the two rows to the developer (identical in every meaningful way, 3 seconds apart) rather than deleting either one unilaterally; developer chose to keep the older row. Cleared the newer row's `import_jobs` record and the recipe itself in one transaction, then the migration applied cleanly. `import-recipe` redeployed with the `claim_import_job` fix and the Haiku default (confirmed no `APP_ENV` secret is set on staging, so the cheap-by-default behavior needs no further config). Developer then imported a real recipe (chocolate chip cookies) through the deployed function directly — worked cleanly end to end, and Haiku's extraction quality held up.

Also surfaced, unrelated to this phase: the dev auto-sign-in hit a `"JWT issued at future"` error on this Simulator run (clock-skew) — pre-existing, nothing to do with Phase 9's code, didn't block verification.
