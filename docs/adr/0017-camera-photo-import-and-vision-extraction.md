# ADR-0017: Camera/photo import and vision-based recipe extraction

- **Status:** Accepted
- **Date:** 2026-08-05
- **Phase:** 10

## Context

Phase 10's build scope (execution-plan.md) adds two new import sources — camera capture and existing-photo picking, both already proven at the picker level by Phase 1's risk spike (`src/photoImport/photoImport.ts`) — plus a new server-side extraction path: Claude vision on an image instead of Claude text-completion on reduced HTML. Hero-image replace/crop/remove is explicitly *not* new work (`src/recipes/heroImage.ts`, Phase 4) — this phase's own image responsibility is the *source* photo: upload-before-processing, metadata stripping, and retaining the original separately from whatever becomes the hero.

Four things neither the PRD, execution-plan.md, nor an existing ADR resolves:

1. **"Preserve original image" (IMG-02) and "Metadata stripping" (this phase's own security checklist) are in tension.** A camera photo's EXIF can carry GPS coordinates and device info — real privacy-sensitive data a user sharing a recipe card photo has no reason to expect gets stored. But IMG-02/IMG-03 require the original be preserved and viewable later. What does "original" mean once metadata is stripped?
2. **Upload-before-processing changes the pipeline shape.** Every prior import path (Phase 8 URL, Phase 9 Share/bulk) fetches content *then* processes it — no client upload happens first. This phase's own build scope lists "Upload-before-processing" as a named item, distinct from Phase 8/9's flow, so it needs a reason and a concrete shape, not just an assumed carryover.
3. **Vision extraction reuses Phase 8's schema/prompt machinery, but not its model-selection defaults as-is.** `extractRecipe.ts`'s existing environment-gated Haiku-dev/Sonnet-prod-with-Opus-escalation strategy (Phase 9 change, 2026-08-05) was tuned for clean extracted webpage text. Does the same default apply to photos of recipe cards, cookbook pages, and handwritten notes — a harder, more visually variable input?
4. **What does a camera/photo import job look like server-side** — a new job type, a variant of `import_jobs`, or something else — and does it need the async job/polling shape Phase 9 built, or can it stay synchronous like Phase 8's original single-URL path?

## Decision

**1. The "original" a user gets back is EXIF-stripped and re-encoded, not the camera's raw output — this is a deliberate, disclosed choice, not a shortcut.** `stripMetadataAndResize()` already exists (Phase 4, `heroImage.ts`) and re-encoding as a fresh JPEG already strips EXIF as a side effect; Phase 10 adds a *second*, less aggressive variant — `preserveOriginalPhoto()` — that runs the same strip-via-re-encode step but at a much larger cap (2400px longest edge, not 1200px) and higher JPEG quality (0.92, not 0.85), since this copy exists to be viewed full-detail later (IMG-03), not to be a lightweight card thumbnail. The *visual content* is preserved losslessly-enough for a photo of a recipe card or page to stay legible; the *metadata* is never preserved, full stop — "preserve original image" is read as "preserve what the user was trying to capture," not "preserve every byte the camera produced," and this reading is recorded here explicitly so it doesn't look like an oversight later.

**2. Upload-before-processing means: the client uploads the (metadata-stripped) original to Storage first, then calls the Edge Function with the object's path, not with image bytes in the request body.** Two reasons, both concrete: (a) Supabase Edge Functions have a request-body size ceiling well under what a full-resolution photo can hit, where Storage does not; (b) if vision extraction fails or the function times out, the original is already durably saved — the user doesn't lose their photo just because AI parsing had a bad run, which matters more here than for a URL import (a URL can always be re-fetched; a photo of a hand-written recipe card might be the only copy that exists). Concretely: client calls `pickHeroImage`-sibling `capturePhotoForImport()` (new, in `src/photoImport/photoImport.ts`), runs `preserveOriginalPhoto()`, uploads to the existing `recipe-images` bucket under `<household_id>/originals/<uuid>.jpg` (new path segment, same RLS policies — they key off the household-id path segment only, already permissive to any suffix), then calls the Edge Function with `{ photoPath: string }` instead of `{ url: string }`.

**3. Vision extraction defaults to Sonnet in every environment, dev included — no Haiku-by-default for this path.** Unlike clean reduced HTML text, a photo's extraction quality depends on real visual parsing (handwriting, glare, cropped edges, multi-column layouts) where a materially weaker model is more likely to produce exactly the kind of confidently-wrong output AI-08 exists to prevent, and this phase's own "Poor image quality cases" validation item names that risk directly. The existing Sonnet-primary/Opus-escalate-on-uncertain-core-fields logic (`extractRecipe.ts`'s `useProductionModels` gate) is reused unchanged for the escalation decision — only the *dev-environment floor* changes, from Haiku up to Sonnet, for this one extraction path. Cost impact is bounded by the fact that photo import is inherently a manual, one-at-a-time, physically-present-with-a-camera action — nothing like bulk URL import's 20-at-once ceiling exists or is needed here.

**4. Camera/photo import stays synchronous, like Phase 8's original single-URL path — no new job-polling UI.** It reuses `import_jobs` (a new nullable `photo_path` column, `source_url` stays null for this path) and the existing `create_import_job`/`complete_import_job`/`fail_import_job` RPCs unchanged — this is bookkeeping only, the same role it already plays for the in-app URL flow. The Edge Function's existing single-request/single-response shape (Phase 8) is extended with the alternative `photoPath` input, mirroring how Phase 9 already added the alternative `jobId` input alongside `url` without disturbing the original call shape. Reusing Phase 9's outbox/batch machinery was considered and rejected (see below) — a camera capture is an interactive, in-app, already-signed-in action with no background-process or offline-capture requirement, the same category Phase 9's own ADR-0016 used to keep bulk paste off the outbox.

**5. Partial recipes and uncertainty reuse the existing `RecipeExtractionSchema`/`uncertainFields` mechanism as-is** — no new schema needed. A photo that's illegible or only partially a recipe produces the same shape of output Phase 8 already handles (empty/uncertain sections flagged, not guessed), and the existing "Recipe cleaned → Uncertainties highlighted → Save" review surface (`ImportRecipeScreen`'s pattern) is reused for the photo-import result rather than building a second uncertainty UI.

## Alternatives considered

- **Send image bytes directly in the Edge Function request body (base64), skip the Storage upload step.** Rejected: hits Edge Function request-size limits on a full-resolution photo, and loses the original entirely if extraction fails — directly against IMG-02/IMG-03 and this phase's own "Upload interruption"/"Partial-page behavior" validation items.
- **Keep the original photo's real EXIF and only strip metadata from the hero-image derivative.** Rejected: the "original" IS the camera capture in this case (unlike a hero image, which is always a deliberate crop/replace of something else) — leaving GPS/device metadata in the one copy explicitly described as "preserve original" and "viewable later" is a real, disclosed privacy gap, not a hypothetical one.
- **Reuse Haiku-dev-default for vision extraction, matching the text path exactly.** Rejected: the two inputs aren't comparably easy, and this phase's own validation scope explicitly names poor-image-quality handling — worth the extra dev-environment cost given photo-import volume is low by nature (see decision 3).
- **Route photo import through Phase 9's `import_jobs`/polling batch machinery for consistency.** Rejected: no batching need exists (one photo per capture), and forcing a polling UI onto a single synchronous call would be a regression from Phase 8's already-working single-URL UX for no benefit — same reasoning ADR-0016 already used to keep bulk paste off the *outbox* specifically applies here to keep single-photo import off the *batch/poll* machinery.

## Consequences

- **`recipes` gains an `original_photo_path` column** (nullable, `recipe-images` bucket path) — separate from `hero_image_path`, since replacing/removing the hero image (Phase 4's existing feature, reused per execution-plan.md) must never affect the preserved original.
- **`import_jobs` gains a nullable `photo_path` column** alongside the existing `source_url` — exactly one of the two is expected to be set per job (checked, not merely assumed) for a camera/photo-sourced job vs. a URL-sourced one.
- **`docs/threat-model.md`** needs a new entry for the upload-before-processing flow: an uploaded original that never gets successfully extracted (abandoned mid-flow) is an orphaned Storage object, not a data-loss risk, but worth a stated cleanup/lifecycle note rather than leaving it implicit — Phase 9's "Staging data expires" precedent (30-day outbox expiry) is a plausible pattern to reuse if this becomes a real cost concern, not committed to yet.
- **No changes to `heroImage.ts`, `import_outbox`, or `import_batches`** — this phase adds a third, independent input path to the existing Edge Function, the same additive shape Phase 9 used for `jobId`.
- **Testability:** `preserveOriginalPhoto()` and the Storage-path convention are unit-testable the same way `stripMetadataAndResize()` already is; the vision-extraction call itself needs a live Claude call to verify for real (same category as Phase 1's `claude-extraction.md` risk spike) — Jest can cover the schema/prompt-construction logic and mock the API response, but real image-quality behavior needs the same kind of live-call verification Phase 8 did for text extraction, flagged here so it isn't skipped silently at exit review.
