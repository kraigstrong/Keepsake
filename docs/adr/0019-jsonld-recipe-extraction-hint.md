# ADR-0019: JSON-LD structured data as an AI extraction hint, not a bypass

- **Status:** Accepted
- **Date:** 2026-08-06
- **Phase:** — (cross-cutting addition to the Phase 8 URL import pipeline; flagged during Phase 11 units/scaling work as a real, previously-unevaluated gap, but out of scope for Phase 11 itself)

## Context

`server/import/reduceHtmlToText.ts` (ADR-0015 decision 6) unconditionally strips `<script>` tags before any content reaches Claude — including `<script type="application/ld+json">` blocks, which on most real recipe blogs carry schema.org `Recipe` structured data (`name`, `recipeIngredient`, `recipeInstructions`, `recipeYield`, `prepTime`/`cookTime`/`totalTime`, `image`) — the same data that powers Google's recipe rich snippets. That data is currently thrown away before extraction ever sees it, even though it's frequently more precise than what a regex-based text reducer can recover from the surrounding page.

Three things neither the PRD nor an existing ADR resolves:

1. **How much of the AI extraction pipeline should be bypassed when JSON-LD is present and looks complete, versus partial?** The obvious-looking option is: skip the Claude call entirely for a "complete" JSON-LD `Recipe` and map its fields straight into `save_recipe` — cheaper, and no hallucination risk since nothing is being generated.
2. **How does this interact with `RecipeExtractionSchema`'s `uncertainFields` and the Sonnet/Opus escalation logic** (`server/ai/extractRecipe.ts`)?
3. **What happens when JSON-LD is malformed, incomplete, or a prompt-injection vector** — it is exactly as untrusted as the rest of the page (`docs/threat-model.md` T5, same posture as every other input this pipeline touches).

## Decision

**1. JSON-LD never bypasses the AI extraction call. It becomes a sanitized, plain-text hint prepended to the same prompt `reduceHtmlToText`'s output already goes into — every import still runs the full `Page reduced to relevant text → AI parses → Recipe cleaned → Uncertainties highlighted → Save` workflow prd.md §8 documents, for every URL import, with or without JSON-LD present.** This is the deciding constraint: §8 doesn't describe "sometimes AI parses, sometimes structured data is trusted directly" — it describes one workflow, and AI-07/AI-08's uncertainty-highlighting step is written as something that happens on every import, not conditionally. A full bypass would silently change that contract for whichever fraction of imports happen to hit a site with complete-looking JSON-LD, and would need its own reconciliation logic for cases (common in the wild) where a site's structured data is stale or wrong relative to what the page actually shows — logic Claude's own extraction already effectively performs today by reading the visible text. Feeding JSON-LD in as a hint gets nearly all the reliability benefit (Claude is far less likely to invent or misread a field it can see stated twice, once in the hint and once in the reduced text) without discarding Claude's role as the thing that reconciles and validates what actually gets saved.

**2. `server/import/extractJsonLdHint.ts` (new, pure, Web-standard-only, following the existing `server/import/*.ts` pattern) parses every `<script type="application/ld+json">` block on the *original* fetched HTML — before `reduceHtmlToText` strips it — for a `Recipe` node (top-level, inside a top-level array, or inside `@graph`; the first one found wins) and formats whatever fields it finds into a short labeled text block** (`Title:`, `Yield:`, `Prep time:`/`Cook time:`/`Total time:` from parsed ISO 8601 durations, `Category:`, `Keywords:`, `Ingredients:`, `Instructions:`), explicitly framed in its own first line as something to verify against the surrounding text rather than trust outright. `supabase/functions/import-recipe/index.ts` prepends this block to the reduced text handed to `extractRecipe` when present; when absent (no JSON-LD, malformed JSON, no `Recipe` type found, or nothing usable extracted), the pipeline behaves exactly as it does today. `recipeInstructions`'s several legal shapes (a bare string, an array of strings, an array of `HowToStep` objects, or an array of `HowToSection` objects nesting their own `HowToStep`s) are all flattened into a plain list, with a `HowToSection`'s `name` kept as a heading line — the same section-structure signal `reduceHtmlToText`'s HTML-based output already tries to preserve, given through a different mechanism here.

**3. No changes to `RecipeExtractionSchema`, the extraction system prompts, or the Sonnet/Opus escalation logic (`seemsUncertain`) in `server/ai/extractRecipe.ts`.** The hint is folded into the plain-string `pageText` argument `extractRecipe` already accepts — from that function's point of view, a page with rich JSON-LD just happens to be an easier page to extract from, the same way a well-structured recipe blog already produces a cleaner `reduceHtmlToText` output than a cluttered one. `uncertainFields` still reflects Claude's own confidence in what it's about to save, computed the same way regardless of whether a hint contributed to the input; a hint that's genuinely complete and accurate simply makes an uncertain result less likely, which is also a secondary cost benefit (less frequent Opus escalation) without being a second decision mechanism to reason about.

**4. JSON-LD is untrusted input, same posture as the rest of the page (threat-model.md T5).** Every string pulled out of a parsed JSON-LD node is stripped of embedded HTML tags, HTML-entity-decoded, and length-capped (500 chars/field, 100 items/list, 4000 chars total hint) before being folded into the prompt — bounding both prompt-injection surface and token cost, the same reasoning `reduceHtmlToText`'s own `MAX_OUTPUT_LENGTH` and tag-stripping already apply to the rest of the page. Malformed JSON in one `<script>` block is caught and skipped, not fatal to the rest of the page — a page can carry more than one JSON-LD block (e.g. `Recipe` plus `BreadcrumbList`/`Organization`), and a broken block from a third-party plugin shouldn't take down a working one from the actual recipe markup. No `Recipe` type found, or a found node with no usable `name`/`recipeIngredient`/`recipeInstructions` at all, both resolve to `null` — the caller falls back to today's behavior unchanged. Because the hint only ever becomes more prompt input, `RecipeExtractionSchema`'s `.strict()` validation remains the sole write-time backstop (T5's existing mitigation, not a new one) — there is no second, less-audited path from JSON-LD into `save_recipe`.

**5. The pre-extraction "not enough content" early return in `supabase/functions/import-recipe/index.ts` is relaxed to also check for a JSON-LD hint.** A page that's mostly a JS-rendered shell (little text `reduceHtmlToText` can recover) but that still emits server-rendered JSON-LD for SEO purposes is a real, common pattern — today that page fails the import outright at the 200-char minimum-useful-text gate; with a hint present, it's worth still attempting extraction even if the reduced text alone falls short.

## Alternatives considered

- **Skip the AI call entirely for a "complete" JSON-LD `Recipe` (name + ≥1 ingredient + ≥1 instruction present), mapping fields straight into `save_recipe`.** Rejected as the primary path per decision 1 — the PRD's own documented workflow runs AI parsing and uncertainty-highlighting on every import, and a silent second, non-AI write path duplicates category/tag inference (`ORG-04`'s existing string-matching would need its own copy) and reintroduces exactly the "second, harder-to-audit path" ADR-0015 decision 1 already argued against for the service-role-key question. Worth revisiting later, narrowly, if a live-traffic accuracy/cost review shows Claude essentially never changes a truly complete JSON-LD `Recipe`'s core fields — but that's a decision to make with real data, not speculatively now.
- **A real DOM/JSON-LD parsing library.** Rejected for the same reason `reduceHtmlToText` rejected a DOM dependency (ADR-0015 decision 6, execution-plan.md T8 supply-chain surface) — `<script type="application/ld+json">` blocks are trivially isolable with a regex, and the payload inside is just `JSON.parse`, no HTML parsing needed for the JSON-LD extraction itself.
- **Trust JSON-LD text fields as-is (no sanitization) since they're "data," not markup.** Rejected — schema.org places no restriction on what a publisher puts in a JSON-LD string field, and real-world CMS output has been observed embedding raw HTML in text fields; treating it as trusted would be inconsistent with treating the surrounding page text as untrusted just because it arrives inside `{}` instead of `<>`.

## Consequences

- **New module, no new dependency:** `server/import/extractJsonLdHint.ts`, Web-standard APIs only, Jest-tested in Node, Deno-executed via the same relative-import pattern every other `server/import/*.ts` module already uses in `supabase/functions/import-recipe/index.ts`.
- **No schema, RPC, or database changes.** `RecipeExtractionSchema`, `save_recipe`, and `import_jobs` are all untouched — this is purely a better-quality-input change to an existing extraction call.
- **No new PRD IDs owned** — this strengthens AI-01/AI-05/AI-06/AI-08's existing reliability without being a distinct requirement itself, the same "no PRD IDs owned" framing ADR-0012 used for a cross-cutting addition.
- **`docs/threat-model.md`** gains T16 (JSON-LD as an additional untrusted-input surface into the same extraction prompt) — same mitigation class as T5, not a new mechanism.
- **Testability:** fully Jest-testable without a live Anthropic call — the hint-construction logic is pure string-in/string-out, same category as `reduceHtmlToText.test.ts`/`extractHeroImageUrl.test.ts`. Whether the hint measurably improves extraction accuracy on real sites is a live-call question this ADR doesn't attempt to answer from Jest evidence alone — worth a live import comparison (same site, before/after) the next time a live Anthropic call happens with the developer watching, per this project's live-API-test convention.
