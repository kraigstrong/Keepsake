# ADR-0027: Smart Meal Selection round model, lifecycle, and ballot privacy

- **Status:** Accepted
- **Date:** 2026-08-20
- **Phase:** Milestone 4 (Smart Meal Selection)

## Context

`docs/roadmap.md`'s milestone 4 builds "Help Me Choose": a household starts a selection round, each participant swipes through a deck of that household's own recipes, and the picks land in This Week. `docs/proposals/smart-meal-selection-architecture.md` is the full codebase-grounded design. Most of what it settles is local and reversible and belongs in commit messages, not here. Three decisions inside it clear `TEMPLATE.md`'s bar — they are persistence architecture and a security boundary, and reversing any of them six months from now means a real migration or a security redesign:

1. **How a round and its votes are persisted**, given that this is the first feature in Keepsake with per-user state inside a shared household. Every existing table is household-scoped and equally readable by every member (`is_household_member`); nothing so far has needed a row that one member can write and others deliberately cannot read.
2. **Who may read an individual vote, and when.** The design specifies blind ballots during a round, and then reveals *who* chose what once it closes ("2 of 3 chose this · Priya passed"). That is a privacy boundary with a time dimension, not a display preference.
3. **Where candidate generation executes.** Ranking is TypeScript; Postgres cannot call it. This is the second place in the codebase where a request has to leave Postgres to run TypeScript before writing back.

Constraints that apply: `household_membership` is flat with no `role` column and PRD `docs/prd.md:149` states all members have equal permissions; ADR-0008 requires every mutating RPC to re-derive the caller's household server-side; ADR-0021 established that This Week bypasses the offline mirror entirely (direct RPC, refetch-on-focus, no Realtime); ADR-0020's `finalize_import_job` is the canonical fencing pattern for a multi-step state transition.

## Decision

**1. Four additive tables, with absence as the third vote state.** `selection_rounds`, `selection_round_participants`, `selection_round_candidates`, `selection_decisions` — no changes to `recipes`, `weekly_plans`, or `planning_entries`. Three details carry the weight:

- **"Unseen" is the absence of a `selection_decisions` row, not a stored third enum value.** This structurally guarantees that a card someone never reached can never be counted as a No: there is no code path that can turn "never decided" into a persisted negative, because there is nothing to write.
- **A `selection_round_candidates` row is never mutated once written.** Availability (archived/deleted) is re-checked live at read and apply time instead. The historical deck stays stable for consensus math even if a recipe is archived mid-round.
- **At most one non-terminal round per household**, enforced by a partial unique index `unique(household_id) where status IN ('pending_candidates', 'active', 'ready_for_review')`. Terminal statuses (`applied`, `cancelled`) are excluded, so history accumulates freely. See 1a for why the predicate spans all three rather than just `active`.

The full schema — including `mode`, `closes_at`, and `selection_round_participants` — ships even though the first work item builds only the solo flow. A solo round is a one-participant group round as far as Postgres is concerned.

**1a. A round is born `pending_candidates`, not `active`, so a half-finished creation is recoverable.** Creation spans two commits with a scoring step between them (decision 5): `create_selection_round` writes the round and its participants, the Edge Function scores, then `finalize_selection_round_candidates` writes the deck. If the function dies in that gap, an initial status of `'active'` would leave behind a round that is active, has an empty deck, and — because of the partial unique index above — blocks every retry, stranding the household until someone thinks to cancel a round they cannot see. `finalize_selection_round_candidates` therefore performs the `pending_candidates → active` transition atomically as part of writing the deck, which has three consequences worth stating:

- **No client ever observes a deckless active round.** Incompleteness is a distinct status, not an `active` round that happens to look broken.
- **The singleton predicate spans every non-terminal status, and getting this wrong has bitten twice.** Scoping it to `'active'` alone lets two members hold separate `pending_candidates` rows, after which the loser's delayed finalize succeeds *later* — once the winner's round has closed and the index stops conflicting — spontaneously starting a round nobody asked for from a stale deck. Extending it to only `pending_candidates` and `active` fixes that but still leaves a gap the guarantee claims to cover: `ready_for_review` is not terminal, because a refill sends it back to `active`. A round could therefore sit in review while a second round starts, and refilling the first would then collide with the second. Covering all three is what makes "one round at a time" a property of the schema rather than a claim in prose.
- **The cost is bounded and visible.** An abandoned `ready_for_review` round blocks new rounds until someone cancels it — but unlike an abandoned `pending_candidates` row, it is *visible* in the UI and cancellable by any member, so the household is never stuck on something it cannot see. That asymmetry is exactly why pending rounds need the adoption path below and review-stage rounds do not.
- **Creation is a claim, fenced exactly like `finalize_import_job`** (ADR-0020, which AGENTS.md names canonical for this). `create_selection_round` mints a `claim_token` on the pending round; `finalize_selection_round_candidates` must present a matching token *and* find the round still `pending_candidates`, as one atomic status-guarded `UPDATE`. A superseded or delayed attempt therefore cannot write a deck or activate a round — it loses cleanly and idempotently, the same way a superseded import claim does.
- **A retry resumes rather than strands.** Widening the index would otherwise reintroduce the very problem this decision exists to solve: a permanently-dead creation would block the household forever. So `create_selection_round` adopts an existing `pending_candidates` row rather than failing — resuming it for the same creator, and taking it over (fresh `claim_token`, invalidating the old attempt) once it is older than a short staleness window, since scoring takes seconds. A *fresh* pending round belonging to someone else is reported as "a round is already starting," which is correct product behavior under one-round-at-a-time.

Orphaned `pending_candidates` rows are inert and invisible — the same accepted tradeoff as stale `active` rounds (no scheduled cleanup at this product's scale).

**2. Individual votes become readable only when a round *completes*, and the predicate is an allowlist.** The `selection_decisions` SELECT policy is `user_id = auth.uid()` **OR** the parent round's `status IN ('ready_for_review', 'applied')`. A cancelled round's ballots stay private permanently — nobody who swiped in it ever consented to a reveal, because the reveal is what closing *means* and a cancellation is an abort, not a close.

**The allowlist is load-bearing, not stylistic.** Writing this as `status != 'active'` — the obvious phrasing, and the one an earlier draft of this ADR used — silently makes `cancel_selection_round` a ballot-disclosure path: cancellation is open to any household member (unlike closing, which is creator-only per decision 3), and `'cancelled'` satisfies `!= 'active'`. Any participant could cancel a round mid-flight and immediately read everyone else's blind ballots, routing straight around the creator-only close gate. Enumerating the two statuses that *should* reveal is the difference; a future fifth status then defaults to private instead of defaulting to exposed.

Because `get_selection_round_results` is `SECURITY DEFINER` it bypasses that policy by design, so **the function must independently enforce the same allowlist** — raising unless the round is `ready_for_review` or `applied`, rather than merely checking that it is not `active`, and never returning an anonymized partial. An aggregate is still information a mid-round caller should not have: in a two-participant round, a count ticking to 1 identifies the voter exactly. The RLS policy alone cannot stop a `SECURITY DEFINER` function from reading past it, so the guard has to live in both places, and both must use the allowlist form.

**2a. A revealed ballot is frozen; a refill may only accept decisions on candidates added after the reveal.** Decision 2 makes ballots household-readable at `ready_for_review`, and the group flow's `refill_selection_round` ("suggest a few more") sends that same round back to `active` — where the proposal otherwise allows a participant to keep editing decisions, including ones they already cast. Composed, those two reasonable decisions cancel the feature's central promise: read everyone's votes on the results screen, trigger a refill, then change your own earlier vote knowing exactly what everyone else picked. The refilled round is no longer blind, and nothing about it looks broken.

So the round records a `revealed_at` the first time it enters `ready_for_review`, and any decision on a candidate that was already revealed becomes immutable — `record_selection_decision` and `clear_selection_decision` reject it. Candidates a refill adds were never revealed, so they stay freely swipeable, which is the entire point of a refill. Freezing per-candidate rather than per-round is what keeps "suggest a few more" working instead of degrading it into "start over."

This is bounded by the group flow, so it lands with that work item, not the solo one. It is recorded here rather than deferred with the rest of refill because it is a property of the privacy boundary decision 2 establishes — leaving it out would mean shipping an accepted ADR with a known way around its own guarantee.

**2b. `append_selection_round_candidates` is a separate mechanism from the documented `refill_selection_round`, guarded purely to `status = 'active'` — not `mode`.** Live developer feedback surfaced a distinct need from decision 2a's group-flow refill: when a household's recipe library is small (or the heuristic is unlucky), the swipe deck can run out of cards before the caller reaches their target count, mid-round, with the deck still `active` and nothing yet revealed to anyone. That has no privacy boundary to protect — `active` is precisely "nothing revealed yet" for solo and group alike, so this structurally cannot interact with `revealed_at` or the reveal freeze regardless of mode. Restricting it to `mode = 'solo'` would be an arbitrary narrowing with no privacy justification.

It ships wired into solo screens only today because the group flow's participant/waiting/results UI doesn't exist yet — not because the RPC excludes group. When group's UI is eventually built, this same append mechanism is already usable pre-reveal, and `refill_selection_round`'s name/shape stays free for the group flow's distinct *post-reveal* "suggest a few more" (decision 2a).

**3. Round closing is creator-only; applying is not.** This deliberately breaks the equal-access symmetry every other shared surface in Keepsake follows. The design is explicit enough to override it — a whole screen is built around what *the creator* sees and decides, including a cost-of-closing-early note that only makes sense as something the closer is told before acting on other people's behalf. Applying to This Week stays open to any member, matching This Week's existing model. The `closes_at` deadline is the equalizer, so nobody waits forever on an absent creator.

**4. Auto-close is lazy, not scheduled — and centralized rather than enumerated.** A single internal helper checks `status = 'active' AND closes_at < now()` and performs the atomic `active → ready_for_review` transition, and **every RPC that reads or mutates round-scoped state calls it before doing anything else**. The first call after the deadline — read or write — resolves the round. No cron, no background job infrastructure.

The centralization is the decision, not an implementation detail. An earlier draft named three RPCs (`close_selection_round`, `record_selection_decision`, `get_selection_round`), which leaves `clear_selection_decision` and `finish_selection_participation` as unguarded active-round writes: an undo arriving after the deadline would delete a vote from a result that is supposed to be frozen, and a late `finish_selection_participation` would move the completed-participant denominator after the fact. Both silently corrupt a closed round's results. Any hand-maintained list of "the RPCs that check the deadline" is a list that will be wrong the first time someone adds a seventh RPC, so the check belongs in one helper that every entry point is obliged to call.

**5. Candidate generation runs in an Edge Function using the caller's JWT**, not a service-role key and not inside Postgres — the same boundary ADR-0015 established for `import-recipe`. `start_selection_round` is therefore a client call to that function, which orchestrates two small RPCs around an in-process call to a pure `server/selection/scoreCandidates.ts` module.

**The Edge Function is not a trust boundary; the RPCs are.** Because it calls `finalize_selection_round_candidates` with the caller's ordinary JWT, any authenticated client can invoke that RPC directly with a hand-written candidate array — the function being the *intended* caller confers nothing. So finalize must **re-derive and validate every candidate `recipe_id` server-side**: each must belong to the caller's own household and satisfy the same eligibility filter, exactly as `record_selection_decision` and `apply_selection_round` already re-validate the ids handed to them. Validating only round/household ownership — an earlier draft's wording — lets a caller who knows another household's recipe UUID persist it as a candidate, after which the `SECURITY DEFINER` round getter follows that pointer and reads across the household boundary with recipe RLS bypassed. This is the codebase's oldest rule (ADR-0008: re-derive, never trust a client-supplied id) applied to an RPC that was mistakenly being thought of as internal. It needs a direct cross-household-finalize pgTAP case, called without going through the Edge Function at all.

**6. `apply_selection_round` locks the round *and* the target weekly plan before filtering duplicates**, then calls the existing `add_recipes_to_weekly_plan` as a nested `SECURITY DEFINER` call sharing the outer transaction — ADR-0020's shape exactly. Lock ordering is load-bearing, not incidental: `add_recipes_to_weekly_plan` does not itself recheck for existing entries, so filtering duplicates *before* holding the plan lock leaves a window where a concurrent direct add lands a duplicate between the check and the insert.

## Alternatives considered

**A stored `'skip'` decision value instead of row absence.** Rejected: it makes "unseen counted as No" a bug that correct code must continuously avoid, rather than a state the schema cannot represent. The acceptance criterion is important enough to enforce structurally.

**Mutating candidate rows with an `excluded` flag when a recipe is archived mid-round.** Rejected: it destroys the historical deck, so an already-cast Yes on a since-archived recipe stops counting toward "3 of 4" retroactively. Live re-checking costs a join and keeps the deck honest.

**Equal-access closing, matching every other shared surface.** This was the first draft's recommendation, on consistency grounds. Overridden by the design, which is specific rather than incidental on this point. Recorded here because the inconsistency is real and a future reader will otherwise assume it was an oversight.

**A scheduled job to close rounds at their deadline.** Rejected: it would be the first background job infrastructure in the codebase, bought for a deadline that no caller can observe as stale anyway. A push-notification-driven "closed at exactly 8:00pm" moment is a genuinely different capability and is out of scope.

**Supabase Realtime for group awareness.** Rejected: refetch-on-focus is the tradeoff ADR-0021 already accepted for This Week. This feature is not the place to introduce a second sync model.

**Generating candidates inside Postgres in PL/pgSQL.** Rejected: the ranking heuristic is the part most likely to change and most needing unit tests. Keeping it as a pure, database-free TypeScript module is what makes this milestone's real risk testable at all rather than reachable only through a live call.

## Consequences

**Easier.** Ranking becomes a pure function testable under Jest with no database. Resume and multi-device are trivial by construction — there is no local mirror, so reopening the screen refetches server state. Every write is either an idempotent upsert, a status-fenced atomic `UPDATE`, or — for the two-commit creation path — resumable via decision 1a, so a client retry after a dropped response is safe to replay. That third case is the one that had to be designed for rather than inherited: it is the only operation here that cannot be made atomic, because scoring runs outside Postgres between its two commits. `planned_count` cannot be double-counted by apply, since it still increments only in `confirm_weekly_plan`.

**Harder.** The blind-ballot guard lives in two places (the RLS policy and the `SECURITY DEFINER` function) and both must hold — a future results-adjacent function that forgets the status check reintroduces the leak with no RLS backstop, so this needs an explicit pgTAP case rather than trusting review. The creator-only close is a genuine inconsistency with the rest of the app's permission model and will read as a bug to anyone who hasn't seen this ADR. Solo and group share one schema, so group-shaped columns sit unused and untested until the group work item lands.

**Security and privacy.** No new authorization primitive — every policy uses the existing `is_household_member`. No direct client INSERT/UPDATE/DELETE on any of the four tables; writes go exclusively through RPCs. Specific abuse cases requiring explicit `throws_ok` coverage: a `participant_user_ids` entry naming a user in another household (rejected at creation, never silently dropped); a `recipe_id` that was never a candidate of the round (rejected in both decision-recording and apply); a cross-household `round_id` on any RPC; a replayed `apply_selection_round` (idempotent no-op, never a second insert); and `get_selection_round_results` called during an active round (raises).

**Cost.** None. The ranking heuristic is deterministic and involves no model call, so this feature adds no AI spend and no new paid service.
