# ADR-0020: Import job fencing, atomic finalization, and local data isolation by household

- **Status:** Accepted
- **Date:** 2026-08-06
- **Phase:** 11.5

## Context

Two independent reviews of the codebase (one external, one this session's own verification against the actual code) surfaced three real, confirmed defects that don't belong to any single existing phase's build scope:

1. **`accept_invitation` ([ADR-0008](0008-household-auth-and-server-operations.md)) is read-check-then-write with no row lock.** Two different users racing the same invitation token can both observe `accepted_at is null` before either writes, and both end up with a membership row — a single-use token isn't actually single-use under concurrency.
2. **`import-recipe/index.ts` calls `save_recipe` and `complete_import_job` as two independent RPCs, not one transaction** (Phase 8/9's original design, unchanged since). If `save_recipe` succeeds and `complete_import_job` fails or the process dies in between, a real recipe exists while its job stays `processing` forever — worse, `complete_import_job`'s own failure path (`index.ts`) returns a 500 without ever calling `fail_import_job`, so the job can't even self-heal into a `failed` state. Separately, Phase 9's `claim_import_job` (ADR-0016 follow-up, `20260805120000_import_job_claiming.sql`) only records a `claimed_at` timestamp with a 60-second staleness window — there's no token identifying *which* claim is current, so a worker whose claim has been superseded by a reclaim can still successfully call `complete_import_job`/`fail_import_job` on a job it no longer owns.
3. **Local SQLite reads (`offlineRecipes.ts`) never filter by `household_id`,** and sign-out's cache wipe (`SessionProvider.tsx`) is explicitly best-effort — a wipe failure leaves the previous account's cached recipes fully readable to whoever signs in next. `import_outbox` (Phase 9, ADR-0016) has no owner column at all by design, since an unsent Share Extension capture must survive sign-out; but that same design means it also has no way to refuse to auto-submit under a *different* account than the one that captured it.

None of these are hypothetical — (1) and (2) are ordinary concurrency bugs any flaky mobile network can trigger (a retried request, an app backgrounded mid-request), not just adversarial exploitation; (3) is a real risk on any shared or reused device, which this app's actual audience (friends and family, ADR-0004's "ordinary account" scale) plausibly includes. Given ADR-0004's "one household per user" model, defect (3)'s real-world trigger is specifically a *different account* signing in after a prior one, not the same user's household changing.

## Decision

**1. Fix the invitation race with a row lock, not a redesign.** `accept_invitation`'s initial `select ... from invitations where token_hash = ...` gains `for update`. This serializes concurrent callers on the specific invitation row — a second caller for the same token blocks until the first transaction commits, then correctly observes `accepted_at is not null` and hits the existing "already used" error. No other logic changes; the expiry check, household-membership check, and idempotent-same-user-retry behavior were already correct, just not atomic with the read.

**2. Merge recipe save and job completion into one `security definer` function, fenced by a claim token.** `import_jobs` gains `claim_token uuid`, generated fresh by `claim_import_job` on every successful claim and returned to the caller. A new `finalize_import_job(job_id, claim_token, recipe_payload, duplicate_of_recipe_id)` atomically verifies `status = 'processing' and claim_token = $token and household_id = caller_household_id`, calls `save_recipe(recipe_payload)` directly (a nested `security definer` call runs inside the same outer transaction — no need to duplicate or refactor `save_recipe`'s ~240 lines), then updates the job's `status`/`recipe_id`/`duplicate_of_recipe_id` in the same function body. `save_recipe`'s insert and the job's completion now commit or roll back together. `fail_import_job` and the duplicate-URL short-circuit's `complete_import_job` call both gain the same `claim_token` check, closing the fencing gap on every path that can currently close out a job. The staleness window moves from 60s to a more conservative value (fencing makes a late completion harmless rather than merely unlikely, so a longer window only costs a slower reclaim of a genuinely-dead worker).

**3. Treat household-scoped filtering, not a successful wipe, as the actual local-data authorization boundary.** `offlineRecipes.ts`'s recipe/category reads gain `and household_id = ?`, sourced from the live session's `household.id` — so even if sign-out's wipe fails, a different account signing in afterward can't read the stale rows, because they no longer match its own household id. Sign-out's wipe stays as best-effort cleanup (freeing storage, keeping the local mirror tidy) rather than the only defense. `import_outbox` gains a nullable `household_id`, stamped when an item is drained while a household is known; submission only auto-fires for rows matching the *current* session's household, and rows captured signed-out (`null`) get an explicit adoption prompt on next sign-in rather than silent auto-submit or silent loss.

## Alternatives considered

- **Heartbeat-based lease renewal for import job claims**, instead of a fencing token plus a longer static window. Rejected: fencing alone already makes a duplicate/late completion harmless (not just unlikely), which is the actual correctness property needed. Renewal adds real machinery (a background renewal call, a new failure mode if renewal itself fails mid-pipeline) for a traffic pattern — one photo or URL at a time, friends-and-family scale — that doesn't need it.
- **Extract `save_recipe`'s body into a shared internal helper called by both the public RPC and `finalize_import_job`**, instead of calling `save_recipe` directly from within `finalize_import_job`. Rejected: Postgres nested `security definer` calls already share the outer transaction, so calling `save_recipe(payload)` directly gets the same atomicity with no duplicated logic and one source of truth for recipe-saving semantics (the `recipe_versions` insert, `recipe_drafts` cleanup, section loops).
- **Household-namespace every local table, including `cached_images` and the FTS tables**, for uniformity. Rejected where it isn't load-bearing: `cached_images` is keyed by Storage path, which is already household-prefixed by RLS, so a cache-key collision across households is structurally impossible — adding a column there would be defense against a threat that can't occur. `recipe_fts`/`recipe_trigram` get checked at implementation time for whether their consuming query already joins back to a now-filtered `recipes` table (sufficient) or needs its own filter (only added if so) — not changed speculatively ahead of that check.
- **Delete/reject signed-out outbox captures under a new account outright**, instead of an adoption prompt. Rejected: a signed-out Share Extension capture is real user data (Phase 9's whole reason for the outbox surviving sign-out) — silently discarding it just because a *different* account happens to sign in next is a worse outcome than asking once.

## Consequences

- **`import_jobs` gains `claim_token uuid`; `import_outbox` gains a nullable `household_id`.** Both are additive, non-breaking migrations.
- **`complete_import_job` is superseded by `finalize_import_job` for the save+complete path** but stays in use, with a `claim_token` parameter added, for the duplicate-URL short-circuit path that never calls `save_recipe`.
- **`docs/threat-model.md`** gains entries for the invitation race, import finalization atomicity/fencing, and local cross-account data isolation.
- **Testability:** the invitation and job-claim fixes are provable by pgTAP for their *logic* (row lock present, fencing check present, atomic update), but a true two-connection race isn't reproducible inside a single pgTAP script — flagged as a staging/CI verification step rather than claimed as covered by the automated suite alone.
- **No change to `cached_images`, `import_batches`, or the outbox's core survive-sign-out guarantee** — this ADR adds scoping on top of existing behavior, it doesn't change what data is captured or how long it's retained.
