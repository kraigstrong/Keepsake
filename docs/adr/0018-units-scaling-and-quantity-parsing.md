# ADR-0018: Units, scaling, and quantity parsing

- **Status:** Accepted
- **Date:** 2026-08-05
- **Phase:** 11

## Context

Phase 4 (ADR-0010) deliberately left `recipe_ingredients.line_text` as plain text ("2 lb baby potatoes, halved") and `recipes.yield_text` as free text ("Serves 4"), explicitly naming Phase 11 as where structured quantity/unit/serving fields belong. execution-plan.md's Phase 11 objective calls out two migrations to design, not assume, plus a build scope (parsing, unit normalization, safe conversions, a global Original/Preferred preference, ½×–4× presets, arbitrary serving count, kitchen-friendly rounding, an approximation indicator) and a safety validation list (temperature preservation, no unsafe mass↔volume conversion, small-quantity rounding, extreme values, malformed imported quantities, range scaling, original values never lost). None of this is resolved by an existing ADR. No Phase 1 risk spike exists for quantity parsing (checked `docs/risk-spikes/`) — this ADR is doing that design work directly, since the problem is well-scoped (a closed unit vocabulary, deterministic arithmetic) rather than needing an exploratory spike the way Share Extension or vision extraction did.

Five real design questions:

1. Is parsed quantity/unit *stored* (structured columns, migration + write-time parsing) or *computed on the fly* from `line_text` at every render?
2. Where does parsing run, given two write paths converge on `save_recipe` (manual entry from the client, AI-imported lines from the `import-recipe` Edge Function)?
3. What counts as a "safe" conversion, and what must the parser refuse to touch?
4. What does "Preferred" mean as a global preference — a unit system choice, or something else?
5. How does `yield_text` become an arbitrary, scalable serving count without inventing one for yields that aren't a serving count at all ("makes one 9x13 pan")?

## Decision

**1. Quantity is parsed once and stored as structured columns, with `line_text` kept as the immutable, always-available fallback.** `recipe_ingredients` gains `quantity_min numeric`, `quantity_max numeric` (equal to `quantity_min` for a non-range value), `unit text` (a closed vocabulary, see below, or null for unitless/uncountable lines like "2 eggs" or vague ones like "a pinch of salt"), and `ingredient_text text` (the descriptive remainder after the quantity/unit are stripped — "baby potatoes, halved" — used to reconstruct a scaled display string). A line that can't be confidently parsed leaves all four columns null; it is never guessed at, and every display path falls back to showing `line_text` verbatim, unaffected by the Original/Preferred toggle or any multiplier. This directly satisfies "Malformed imported quantities" and "Original values never lost," and matches the codebase's existing AI-must-never-invent posture (CLAUDE.md, T5/T14) extended to the parser itself: an ambiguous line degrades to opaque text, it doesn't produce a wrong number.

Storing structured fields (rather than re-parsing `line_text` on every render) was chosen over the on-the-fly alternative because execution-plan.md explicitly frames this as a migration, and because a stored `parse_status` (implicit: `quantity_min is null`) gives a stable, inspectable record of which lines are scalable — useful for the exit gate's fixture corpus and for any future editor UI that might want to show "we couldn't parse this line" without re-running the parser.

**2. Parsing is a pure TypeScript module (`src/units/`) run at the call site, before `save_recipe` is invoked — not inside the RPC.** `save_recipe`'s payload shape for ingredient lines changes from a bare string to `{ lineText, quantityMin, quantityMax, unit, ingredientText }`; the RPC stores what it's given, the same trust posture it already has for `line_text` (household-scoped write access via RLS is the real boundary, not the shape of what's written). Both write paths call the same parser: `RecipeEditorScreen` for manually typed lines, and `import-recipe`'s Edge Function for AI-extracted lines — following the established `server/import/*.ts` pattern (Web-standard-APIs-only pure functions, one implementation, Jest-tested in Node and Deno-executed in production). Doing this in plpgsql instead was rejected: fraction/unicode-fraction/range regex and unit-table lookups are painful and error-prone in SQL, and a safety-critical calculation duplicated in two languages is a correctness risk this phase's own safety validation list explicitly exists to prevent, not just a style preference.

**3. The unit vocabulary is closed and split by measurement class; conversions never cross class.** Volume: `tsp`, `tbsp`, `fl_oz`, `cup`, `pint`, `quart`, `gallon`, `ml`, `l`. Mass: `oz`, `lb`, `g`, `kg`. Anything else (count nouns, vague amounts like "a pinch"/"to taste"/"a few") parses to `unit = null` with the quantity (if any) scaled by simple multiplication and no unit conversion ever attempted. The conversion table only has volume↔volume and mass↔mass entries, using standard exact factors (e.g. 1 cup = 236.588 ml, 1 lb = 453.592 g) — volume↔mass is structurally impossible to reach through this table, not just discouraged, since the app has no per-ingredient density data and guessing one is exactly the "unsafe mass/volume conversion" the safety validation names. The parser only ever runs against `recipe_ingredients.line_text` — instruction text is never fed through it, so an oven temperature mentioned in a step ("bake at 350°F") is structurally untouched, satisfying "Temperature preservation" by construction rather than by a special-case check. A parsed `quantity_min`/`quantity_max` outside a sane bound (>10,000) is treated as a failed parse rather than trusted, guarding "Extreme values" against a bad match producing a nonsensical number.

**4. "Preferred" is a global unit-system choice — US Customary or Metric — stored on `profiles.preferred_unit_system` (`not null default 'us_customary'` given the app's English/US-leaning example data; a user can change it in Settings).** The Original/Preferred toggle lives on `RecipeDetailScreen` as local screen state (defaults to Preferred, not persisted per-recipe): "Original" always shows the recipe's own stored unit and value untouched; "Preferred" converts to the nearest well-fitting unit in the user's chosen system (e.g. a `cup` quantity converts to `ml` under Metric; an already-metric recipe stays as-is under Metric). "Best-fitting" is a small ordered preference list per class+system (e.g. prefer `l` over `ml` above 1000 ml, prefer `tbsp` over `cup` below 1/4 cup) so conversion doesn't produce awkward values like "1500 ml" or "0.125 cup." This needed a real client-updates-its-own-profile path that doesn't exist yet (`src/household/api.ts` currently only fetches/inserts `profiles`, never updates) — this phase adds `updateProfile()`.

**5. `recipes` gains a nullable `servings_count integer`, parsed from `yield_text` by a pure `parseServings()` alongside the ingredient parser, at the same write-time call sites.** Only a clear single serving count parses ("Serves 4" → 4); a range ("Serves 4-6") or a non-serving yield ("makes one 9x13 pan", "makes 2 loaves") leaves it null, per execution-plan.md's own framing — those recipes get the ½×–4× presets only, no arbitrary-serving-count stepper. `yield_text` itself is untouched and remains what "Original" shows. When `servings_count` is set, `RecipeDetailScreen` additionally offers a numeric serving-count input; the multiplier it produces (`target / servings_count`) feeds the exact same scaling pipeline as the ½×–4× preset chips, so there's one scaling code path, not two.

**Multipliers, kitchen-friendly formatting, and the approximation indicator are all pure, display-time computations over the stored structured fields — never persisted.** `scaleQuantity()` multiplies `quantity_min`/`quantity_max` by the active multiplier (preset chip or arbitrary-serving-derived); `formatQuantity()` then rounds to a practical value (nearest common fraction — 1/8, 1/4, 1/3, 1/2, 2/3, 3/4 — for cup/tsp/tbsp; a per-unit step size for everything else) with a floor so a small scaled-down quantity never displays as zero, and prefixes the result with "~" whenever rounding actually changed the exact value beyond a negligible epsilon. A range (`quantity_min ≠ quantity_max`) scales and formats both bounds independently and renders as "min–max unit" with one shared approximation indicator if either bound was rounded.

## Alternatives considered

- **Compute parsing on the fly from `line_text` at every render, no schema change.** Rejected: execution-plan.md explicitly calls this a migration to design, and a stored, inspectable parse result is more testable against the exit gate's fixture corpus than a re-derived one, at negligible storage cost.
- **Parse inside `save_recipe` (plpgsql).** Rejected: fraction/range/unit regex and conversion-table logic in SQL is fragile and would need a second implementation to keep in sync with the TS version used for fixture testing — unacceptable risk for safety-critical arithmetic.
- **A user-extensible unit vocabulary (e.g. a `units` lookup table like `categories`).** Rejected: unlike categories, "safe conversion" is a safety property, not a taxonomy — an open vocabulary would let a bad entry (or an AI-invented unit string) introduce an unreviewed, potentially unsafe conversion factor. The vocabulary is a fixed, reviewed TS constant; extending it is a code change, deliberately.
- **Persist the active multiplier / Original-vs-Preferred choice per recipe.** Rejected: nothing in the PRD asks for it, and it would mean a recipe silently "remembers" a scaling state from a prior cook, which cuts against Original values always being one tap away.

## Consequences

- `save_recipe`'s ingredient-line payload shape changes (string → object) — an additive-but-breaking signature change for that one field, handled the same way ADR-0016 handled `create_import_job`'s new optional parameter: old callers must move to the new shape, there's no dual-signature compatibility window (this repo doesn't ship to external API consumers). One exception: `restore_recipe_version` (ADR-0011) replays a *stored* `recipe_versions.snapshot` back through `save_recipe`, and snapshots taken before this migration are frozen in the old string-line shape — they can't "move to the new shape" the way a live caller can. `save_recipe`'s ingredient-line insert branches on `jsonb_typeof` so a pre-Phase-11 snapshot still restores correctly (as an unparsed line, every structured field null), rather than hitting the `line_text` not-null constraint.
- The local SQLite mirror's `ingredient_sections` JSON blob (currently `{ title, lines: string[] }`) becomes `{ title, lines: { lineText, quantityMin, quantityMax, unit, ingredientText }[] }` — a schema version bump (v5 → v6) and a sync-engine change, not a resync-cursor reset (mirrors Phase 10's `original_photo_path` precedent: new data, no pre-existing row could have had a real value to backfill... except here existing rows *do* have `line_text` without structured fields already synced locally). Existing local rows get the new shape on their next server-driven upsert; until then they render as unparsed (safe default, same as a genuinely unparsed line).
- Existing `recipe_ingredients` rows in staging/prod keep `quantity_min`/`unit`/etc. as `null` until the recipe is next edited and re-saved — no bulk backfill migration is written, since that would mean a second parser implementation (plpgsql) purely for one-time use. Acceptable given Keepsake's actual scale (friends and family, a handful of test recipes today) and consistent with the "unparsed falls back safely to original text" design already in place for exactly this case.
- `docs/threat-model.md` should get a short entry (or an extension of T5/T14) noting the parser is a new consumer of AI-extracted text and must degrade to "unparsed" rather than trust an adversarial or malformed quantity string — recorded once built, per this repo's convention of documenting security decisions after they exist in code, not before.
- Settings gains its first true user-preference control (`preferred_unit_system`) and the first `profiles` UPDATE path this app has ever needed — small, but worth noting since every prior phase's profile interaction was fetch/insert-only.
