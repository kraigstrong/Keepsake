# ADR-0015: URL import pipeline design (Edge Function boundary, secure fetcher, data model)

- **Status:** Accepted
- **Date:** 2026-08-04
- **Phase:** 8

## Context

Phase 8's build scope (execution-plan.md) is the first phase to actually cross the boundary ADR-0008 reserved but didn't need yet: "Edge Functions are reserved for Phase 8+'s external Anthropic API calls, where a request needs to leave Postgres entirely." Turning a URL into a saved recipe means: fetch a page Keepsake doesn't control (SSRF surface, prd.md §30), reduce it to text, call Claude (prompt-injection surface, threat-model.md T5), validate the output, acquire an image without hotlinking (IMG-01), and create the recipe — while never putting `ANTHROPIC_API_KEY` in the client bundle (SEC-06, T2).

None of the PRD, execution-plan.md, or an existing ADR resolves:

1. **Where does each step run, and with what privilege?** The fetch and the Anthropic call must be server-side (credentials, cost control). Does the server-side step also need `SUPABASE_SERVICE_ROLE_KEY` to write the resulting recipe, or can it reuse the caller's own session?
2. **What does an SSRF-safe fetcher actually mean in a Deno Edge Function**, where there's no raw-socket control the way a Node process on infrastructure Keepsake operates would have?
3. **What shape is the `ImportJob` entity** (prd.md §26 names it but doesn't define columns), and how does "Progress and retry" (build scope) actually surface to the client without a queue/worker system that doesn't exist yet?
4. **Can Phase 1's `server/ai/extractRecipe.ts` risk-spike code run as-is inside a Deno Edge Function**, or does it need a rewrite?

## Decision

**1. Edge Function uses the caller's own JWT, not the service-role key, for every Supabase read/write.** `supabase/functions/import-recipe/index.ts` forwards the incoming `Authorization` header into its own `createClient(url, anonKey, { global: { headers: { Authorization } } })` — the exact same RLS-scoped identity the client itself has. `save_recipe` (Phase 4/5, `SECURITY DEFINER`, already resolves the household from `auth.uid()`) is called through this client unchanged; no new bypass path is added. The service-role key is not read by this function at all — only `ANTHROPIC_API_KEY` is a genuinely new server-only secret this phase needs deployed (`supabase secrets set`). This keeps RLS as the actual enforcement boundary (prd.md §30's first bullet) instead of trusting the Edge Function's own logic not to leak across households — the same reasoning ADR-0008 already applied to RPCs.

**2. The fetcher is DNS-resolve-then-validate before every connection (including each redirect hop), not just the origin URL.** `server/import/secureFetch.ts`: reject any URL whose scheme isn't `http`/`https`, reject any URL whose hostname is a raw IP literal outright (no legitimate recipe site is ever handed to a user as a bare IP — this closes a whole attack class for free), resolve DNS for the hostname and reject if *any* resolved address is private/loopback/link-local/multicast/reserved (RFC 1918, 127.0.0.0/8, 169.254.0.0/16, CGNAT 100.64.0.0/10, IPv6 equivalents), then fetch with `redirect: 'manual'` and repeat the full check on every `Location` header before following it (capped at 3 hops) — a redirect to an internal address after the origin passed validation is exactly threat-model.md T6. A running byte counter aborts the read once a 2MB cap is exceeded (`AbortController`), an overall 10s timeout bounds slow-loris-style stalls, and `Content-Type` must start with `text/html` before the body is read.

   **Named residual risk, not silently assumed away:** the DNS-resolution check and the actual `fetch()` call are two separate operations — `fetch()` does its own internal DNS resolution at connect time, which this code cannot force onto the specific IPs already validated. A DNS answer that changes between our check and `fetch()`'s own lookup (DNS rebinding) is not fully closed by this design. Fully closing it needs raw socket control (`Deno.connect` to a pinned IP, hand-rolled HTTP framing with the original `Host` header) — a real hardening step, deliberately deferred rather than attempted now given the added complexity/risk for a foundation phase, tracked in Known limitations below and in `docs/threat-model.md` T6.

**3. `import_jobs` is household-scoped (mirrors every other Phase 4+ table), columns: `id uuid`, `household_id`, `created_by`, `source_url text`, `normalized_url text`, `status` (`'processing' | 'complete' | 'failed'`), `error_message text null`, `recipe_id uuid null` (set on success or when resolved as a duplicate), `duplicate_of_recipe_id uuid null`, `created_at`, `updated_at`.** No separate queue/worker: the client calls the Edge Function synchronously (the Phase 1 spike measured ~13s per Claude call, well inside a mobile request timeout with a spinner), and the function writes the `import_jobs` row as its *first* action (`status: 'processing'`) before doing any slow work, then updates it once at completion (`'complete'` + `recipe_id`, or `'failed'` + `error_message`). "Progress" for this phase is coarse (a spinner while the single request is in flight, not per-step live updates) — granular multi-step progress and a real retry queue are Phase 9's "Leave-and-return progress" problem (Share Extension/bulk import, where the client genuinely isn't there to wait on a synchronous response). Retry here just means: a failed job's row stays queryable, and the client can resubmit the same URL, which is idempotent by construction (see next point).

**4. Duplicate detection is server-side, by normalized URL against the household's existing recipes, checked before spending any Claude tokens.** `server/import/normalizeUrl.ts` (pure, unit-tested): lowercases scheme/host, drops default ports and the fragment, strips a known tracking-parameter denylist (`utm_*`, `fbclid`, `gclid`, ...), sorts remaining query params, drops a trailing slash except at the root. The Edge Function normalizes the incoming URL, checks it against `recipes.source_url` (normalized the same way) for the caller's household; a match short-circuits the job to `status: 'complete'`, `duplicate_of_recipe_id` set, `recipe_id` set to the existing recipe — no fetch, no AI call, no new recipe. This is also what makes retrying a failed/slow request safe to just resubmit rather than needing a client-generated idempotency key threaded through (unlike Phase 9's Share Extension queue, which genuinely needs one per the `durable-import-submission.md` design — that document's idempotency-key approach is for when the *client* can't wait for a synchronous result, which doesn't describe Phase 8's in-app flow).

**5. `server/ai/extractRecipe.ts` is imported unchanged into the Edge Function via a relative path, not rewritten.** It already only uses `fetch`-based APIs (`@anthropic-ai/sdk` documents Deno as a supported runtime) — no Node built-ins. `supabase/functions/import-recipe/index.ts` imports it directly (`../../../server/ai/extractRecipe.ts`), so the schema/prompt stay Jest-tested in Node (fast, no deploy needed to iterate) while the exact same code executes in Deno in production — one implementation, not a port. The new Phase 8 modules (`normalizeUrl.ts`, `reduceHtmlToText.ts`, `secureFetch.ts`) are written the same way: plain TS, Web-standard APIs only (`fetch`, `URL`, `TextDecoder`, `AbortController`), so they're Jest-testable in Node and Deno-executable unchanged, with only DNS resolution behind an injected `resolveDns` function (Node has no `Deno.resolveDns`; the Edge Function supplies the real one, tests inject a fake one to simulate rebinding/private-IP scenarios deterministically).

**6. Content reduction is a heuristic tag-stripper, not a full Readability port.** `server/import/reduceHtmlToText.ts`: strip `<script>`/`<style>`/`<noscript>`/`<svg>`/`<nav>`/`<header>`/`<footer>`/`<aside>`/`<form>`/`<iframe>` and HTML comments outright; prefer the first `<main>` or `<article>` element's contents if present; fall back to `<body>` otherwise (the "Content fallback" build-scope item) or if the preferred extraction comes out suspiciously short (< 200 chars, likely a JS-rendered shell); strip remaining tags, decode common HTML entities, collapse whitespace, and cap total length (bounds Claude token cost, per prd.md §8's stated reasoning). Regex-based rather than a DOM parser dependency — no HTML-parsing library is in `package.json` today, and adding one is a real supply-chain surface (execution-plan.md T8) for something a well-scoped regex pass can do adequately for recipe blogs' typically-simple structure. Flagged as a quality tradeoff to revisit if real-world extraction quality disappoints (see Known limitations).

**7. Image acquisition reuses the fetcher's security posture, not `heroImage.ts`'s upload primitive as-is.** The page's `<meta property="og:image">` (or first `<img>` inside the same content region content reduction preferred) is downloaded through the same `secureFetch` primitive (an image URL is exactly as untrusted as the page URL — it's still attacker-controlled input, IMG-01's "do not hotlink" plus SSRF apply equally), capped at 8MB and validated `Content-Type: image/*`, then uploaded via the caller's own JWT to the existing `recipe-images` bucket using `heroImage.ts`'s existing `<household_id>/<random-id>.jpg` path convention (reused, not duplicated) — no EXIF-strip re-encode pass this phase (unlike the manual hero-image path) since a fetched web image is already a rendered file, not a camera photo; if that turns out to matter, it's a small addition to the same call site, not a design change.

## Alternatives considered

- **Service-role key in the Edge Function, for both the recipe write and the Storage upload.** Rejected: strictly more powerful than needed, and every other write path in this codebase (Phase 3 onward) goes through RLS via the caller's own identity specifically to avoid a second, harder-to-audit authorization mechanism existing in parallel. The only thing that genuinely requires server-side execution here is reaching the public internet and holding the Anthropic key — neither requires bypassing RLS.
- **A real job queue (pg-boss, a cron-polled table, Supabase's own queue extension) for "Progress and retry."** Rejected for this phase: no PRD requirement calls for background processing on the in-app URL-entry path specifically (unlike Phase 9's Share Extension, which structurally can't wait synchronously). Building queue infrastructure now would be solving Phase 9's problem early, against a data model Phase 9 hasn't been designed against yet — the `import_jobs` table shape here is deliberately compatible with Phase 9 adding a `submitted_via` / batch reference later, not precluding it.
- **A DOM-parsing library (`linkedom` or similar) for content reduction.** Rejected for now — real dependency-scan surface for a first pass that a regex-based reducer can likely handle adequately; revisit if the human import-quality review (this phase's own validation bullet) finds real sites the regex approach mishandles.
- **Raw-socket pinned-IP fetching to fully close the DNS-rebinding TOCTOU gap.** Rejected for this phase as disproportionate complexity/risk for a foundation phase — named explicitly as a residual risk instead of silently assumed solved, consistent with how ADR-0013 disclosed the SQLite backup-location gap rather than pretending it was closed.

## Consequences

- **Credentials:** only `ANTHROPIC_API_KEY` is newly needed as a *deployed Edge Function* secret this phase (already provisioned in 1Password's `Keepsake Server` environment since Phase 1 — see the `keepsake-phase-secret-timing` memory — but not yet `supabase secrets set` for the deployed function specifically, since no Edge Function has existed until now). `SUPABASE_SERVICE_ROLE_KEY` is *not* read by this function. Deploying requires `devtools.env` (`SUPABASE_ACCESS_TOKEN`), already provisioned.
- **The "no server credential in client bundle" CI check**, deferred since Phase 0 (`docs/phase-status.md` carried-forward items), is now worth building for real — this is the first phase where a client-bundle leak of `ANTHROPIC_API_KEY` is an actual live risk rather than a hypothetical one. Tracked as this phase's concrete trigger for that item, per the note already left for exactly this moment.
- **Testability:** every new Phase 8 module (`normalizeUrl`, `reduceHtmlToText`, `secureFetch`'s pure IP/redirect-validation logic) is Node/Jest-testable without a Deno runtime or a real deploy, following the same `node:sqlite`-style "test the real logic against a real-enough environment" precedent Phase 1 and Phase 7 both used. The Edge Function's own thin entrypoint (wiring + `Deno.resolveDns`) is the one piece that can only be verified by an actual deploy + live invocation against staging — a required human/session step before this phase can exit, same category as every phase's Simulator-verification gap.
- **T5/T6 in `docs/threat-model.md`** move from "intended design" to "implemented, DNS-rebind TOCTOU named as a residual gap" — update their evidence column once this lands, per the note already left there ("re-examine T5/T6 against the actual fetcher implementation").
