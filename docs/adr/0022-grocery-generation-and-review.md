# ADR-0022: Grocery generation, canonical identity, and review persistence

- **Status:** Accepted
- **Date:** 2026-08-08
- **Phase:** 13

## Context

execution-plan.md's Phase 13 build scope (`docs/execution-plan.md:1066-1075`) lists eight bullets the PRD text (`docs/prd.md` §19) doesn't specify the mechanics of: scaling, canonical ingredient identity, conservative merging, categories, staples, grouped review, include/exclude, and deterministic hashing. The security section is unusually load-bearing for this phase: **"No AI call at export time"** rules out the obvious approach (ask Claude to categorize/merge ingredients) that every AI-adjacent phase so far (8, 10, 19-hint) has otherwise reached for. The Validation section — "Large must-merge and must-not-merge fixture suite… a false merge is more severe than a missed merge" — sets the same bias ADR-0018 already established for unit conversion: degrade to showing something safe-but-plain over guessing.

Five real design questions, none answered by an existing ADR:

1. Is the grocery list a persisted server entity, or computed on demand from data that already exists (`planning_entries`, `recipes`, `recipe_ingredients`)?
2. What makes two ingredient lines "the same" for merging, conservatively enough that the fixture suite's must-not-merge cases actually hold?
3. How are categories assigned without an AI call?
4. What is a "staple," and how does "omitted by default" actually work given GRO-07/PRD §19 also says no merge UI and no editing?
5. What is the deterministic hash *for* — the phase lists it as a bullet on its own, separate from merging?

## Decision

**1. The grocery list is never persisted — it is a pure, stateless computation over already-RLS-authorized data, recomputed every time the review screen loads.** A new module, `server/groceries/`, follows the exact convention `server/units/` set in Phase 11 (ADR-0018): pure TypeScript, Web-standard-APIs-only, Jest-tested, no server round-trip to compute. The client fetches the confirmed `weekly_plan`'s `planning_entries` joined to `recipes` and `recipe_ingredients` via ordinary RLS-scoped Postgrest queries (same "bypasses `src/sync/*`, direct queries" pattern as This Week, ADR-0021) and runs `generateGroceryList()` locally. This is what makes "No AI call at export time" trivially true — there was never a network call in the computation at all, satisfying "Authorized plan data only" by construction (RLS already gated everything the function reads) rather than by a separate authorization check. Review is only reachable from a `status = 'confirmed'` plan, matching the "Ready for groceries? → Export" banner ADR-0021 already staged on the Confirmed mockup and deliberately left unwired.

**2. Scaling reuses Phase 11's pipeline exactly.** Per planning entry, `multiplier = recipe.servingsCount ? entry.servings / recipe.servingsCount : 1` — the same ratio `RecipeDetailScreen.tsx` already derives for its own scaler. Recipes with no parsed `servings_count` (an unparseable yield, e.g. "makes one 9x13 pan") contribute ingredients unscaled, same "don't fabricate a number" posture as the detail screen. `scaleQuantity()` (`server/units/scaleQuantity.ts`) does the actual multiplication, unchanged.

**3. Canonical identity is a two-step, deliberately narrow normalization — no dictionary, no stemmer, no synonym table:**
   - Take `ingredientText ?? lineText` (the parsed descriptive remainder, or the raw line if unparsed), split on the first comma, and keep only the portion before it — this drops preparation clauses ("large diced", "at room temperature") that would otherwise make near-identical ingredients look distinct.
   - Lowercase, trim, collapse internal whitespace, strip trailing punctuation, then apply a small fixed suffix rule to the *last word only* (`ies`→`y`, `oes`→`o`, `ches`/`shes`/`xes`/`sses`→ strip `es`, a lone trailing `s` not preceded by `s`→ strip `s`).

   The suffix rule is safe under "false merge is worse than missed merge" for a structural reason, not just a judgment call: it is a deterministic function applied independently to each string, so it can only ever cause two spellings of the *same* underlying word to collide (a true singular/plural pair) — it has no mechanism to make two different foods collide, unlike a synonym table or a fuzzy-match threshold would. Its failure mode is exclusively under-merging (irregular plurals it doesn't know, adjectives left in front so "yellow onion" never merges with "onion") — an accepted, conservative gap, not a defect the fixture suite needs to close.
   - No stemming beyond this, and no cross-recipe synonym folding ("scallion" vs "green onion" stays two items). If the fixture suite later shows this misses too much in practice, the fix is a small, explicitly reviewed synonym constant — same "fixed, reviewed constant, extended deliberately" precedent ADR-0018 used for the unit vocabulary, not an automated inference added on top of this ADR's approach.

**4. Merging sums quantities only when safely summable; otherwise the canonical group still displays as one row, but lists the distinct original amounts instead of fabricating a total.** Two occurrences merge for display whenever their canonical keys match. Their quantities are only *summed* into one number when both are unitless, or both units share a class (`unitClass()`, `server/units/quantityVocabulary.ts`) — converted to a common unit via `convertQuantity()` and added, reusing the exact volume/mass conversion table ADR-0018 already reviewed for safety. A same-canonical-key pair spanning volume vs. mass (e.g., "2 cups flour" and "1 lb flour") is exactly the volume↔mass ambiguity ADR-0018 refused to guess at — it is never summed, and the item's line shows both original phrases side by side rather than inventing a shared unit.

**5. Categories and staples are both static, curated, reviewed TypeScript constants — no AI, no per-household configuration UI.** `server/groceries/categoryDictionary.ts` maps keyword patterns to the six PRD categories (Produce/Meat/Frozen/Dairy/Pantry/Other), matched against the canonical key; no match falls back to `Other`. `server/groceries/staples.ts` is a fixed list of common pantry staples (salt, pepper, common oils, flour, sugar, baking soda/powder, common condiments, water) matched the same way. There is no "mark as staple" affordance and no settings screen for it — the phase's own build scope has no such bullet, and PRD §19 ("No merge UI… No editing") reads as the same minimalism extended to categorization. A staple match sets the review row's *default* `included` state to `false`; everything else defaults to `true`. Both lists are ordinary reviewed code, extendable the same way the unit vocabulary is — a deliberate code change, not a data-driven or AI-driven one, for the same reason ADR-0018 kept units closed: an open/inferred categorization is the false-merge-style risk this phase is explicitly trying to avoid, just for aisle assignment instead of identity.

**6. The deterministic hash is the merge key's stable identity across regenerations, not a display concern.** `itemHash = fnv1a64(canonicalKey)` (a small dependency-free non-cryptographic hash — collision resistance for this purpose only needs to hold within one household's own grocery vocabulary, not globally, so a fast synchronous hash beats an async `crypto.subtle.digest()` for looping over a plan's full ingredient list with no real security stake). Because the list itself is never persisted (decision 1), the hash is what lets a re-rendered, freshly-recomputed list reattach a user's prior include/exclude choice to "the same" item — and, ahead of Phase 14, gives that phase a ready-made idempotency key for duplicate-protection on re-export without this phase needing to guess at Phase 14's export-record shape.

**7. Include/exclude state is the one thing that *is* persisted, in a new table, sparse by construction.** `grocery_item_selections (id, weekly_plan_id, household_id, item_hash text, included boolean not null, updated_at, updated_by)`, unique on `(weekly_plan_id, item_hash)`, RLS-readable by household members (mirrors `weekly_plans`' `is_household_member(household_id)` policy shape exactly). A row is written only when a user actually toggles an item away from its computed default — untouched items have no row at all, so the table only ever holds explicit deviations, not a full snapshot of every regenerated list. Writes go through a new RPC, `set_grocery_item_selection(plan_id, item_hash, included)`, `security definer`, membership-checked and upserting on the unique key — mirroring `add_to_weekly_plan`'s shape (`supabase/migrations/20260806110200_weekly_plan_rpcs.sql:62-114`) rather than relying on an RLS `INSERT`/`UPDATE` policy directly, consistent with every other mutating path in this codebase (`save_recipe`, the import job RPCs, all six weekly-plan RPCs) never being a bare RLS-permitted write.

**8. "Debug provenance hidden from normal clients"** means the review screen can show, gated behind `__DEV__` (the existing convention, `src/session/useDevAutoSignIn.ts:11,24`), which rule matched an item's category/staple status and its computed `itemHash` — useful for building and defending the fixture suite against real production data shapes, never shown in a release build.

## Alternatives considered

- **Persist a generated `grocery_items` table per weekly plan.** Rejected: it would need its own regeneration/staleness invariant (what happens when a plan's entries change after generation?) and a cleanup story symmetrical to Phase 9's outbox — unnecessary complexity when the underlying source data (`planning_entries`, `recipe_ingredients`) is already the durable, authorized source of truth and recomputation is cheap and pure.
- **Call Claude to categorize and/or merge ingredients.** Rejected outright by the phase's own security section ("No AI call at export time"), and inconsistent with the "AI must never confidently invent information" non-negotiable (CLAUDE.md) applied to a domain (grocery aisles) that has no ambiguity-flagging mechanism the way import extraction does.
- **A general stemmer/lemmatizer (e.g., pluralize libraries, fuzzy string matching) for canonical identity.** Rejected: unlike the fixed suffix rule adopted, a general fuzzy matcher's failure mode includes false merges (distinct ingredients whose names happen to be edit-distance-close), which is precisely what the phase's own validation section names as the worse failure.
- **Per-household editable staples list / settings UI.** Rejected for this phase: no such bullet in the build scope, and it reopens "no editing" territory PRD §19 explicitly closes for this flow. Worth revisiting only if the developer finds the fixed list wrong often enough in practice — flagged here, not built speculatively.
- **RLS-permitted direct `INSERT`/`UPDATE` on `grocery_item_selections` instead of an RPC.** Rejected for consistency: every other mutating path in this codebase goes through a `security definer` RPC that re-derives household from `auth.uid()`, never a client-supplied value; introducing the one bare-RLS-write table would be a silent divergence from an otherwise uniform pattern.

## Consequences

- New table + RPC (`grocery_item_selections`, `set_grocery_item_selection`), no changes to any existing schema — Phase 13 adds no columns to `recipes`, `recipe_ingredients`, or `planning_entries`.
- The merge/categorize/hash algorithm must stay a pure, versioned function in practice: because selections are keyed by `itemHash = fnv1a64(canonicalKey)` and the list is never snapshotted, a future change to canonicalization logic silently stops matching old selection rows for affected items (they simply revert to computed default). Acceptable for a friends/family-scale app with low stakes per ADR's own household-isolation and "conservative merge" priorities, but worth remembering before casually tweaking the normalization rules later.
- Because nothing is persisted except selections, "regenerate" has no explicit action or button — the list is simply always current, by construction, every time the screen is open. This also means Phase 13 has nothing that needs cleanup/expiry the way Phase 9's outbox or Phase 16's tombstones do.
- Phase 14 (Apple Reminders export) can reuse `itemHash` directly as its duplicate-protection idempotency key without needing to invent its own identity scheme — this phase's hash decision is deliberately shaped to serve that need, though Phase 14 remains free to layer its own export-record concept on top.
- `categoryDictionary.ts` and `staples.ts` will need real-world tuning once actual household recipes exercise them; both are ordinary reviewed TS files, so extending them is a normal code change, not a migration or config change.
