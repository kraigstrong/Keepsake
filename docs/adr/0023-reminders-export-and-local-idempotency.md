# ADR-0023: Apple Reminders export, local idempotency, and permission recovery

- **Status:** Accepted
- **Date:** 2026-08-08
- **Phase:** 14

## Context

execution-plan.md's Phase 14 build scope (`docs/execution-plan.md:1096-1119`) lists eight bullets the PRD (`docs/prd.md` §19) doesn't specify the mechanics of: point-of-use permission, permission recovery, a "Pantry list strategy," item creation, duplicate protection, export records, opening Reminders, and retry/partial failure. Phase 1's risk spike (`docs/risk-spikes/reminders.md`, `src/reminders/reminders.ts`) already proved the core EventKit calls work via `expo-calendar/legacy` (a real deprecation bug was hit and fixed there — see that file's own header comment) and established list-reuse-not-duplication as the list strategy; this ADR is Phase 14 building the real feature on that proof, not re-deciding it.

One fact drives most of this ADR's decisions: **Reminders is a local, per-device EventKit store — Keepsake has no server-side representation of it and no way to sync it across a household's devices.** Unlike everything else this app has built so far (recipes, plans, grocery selections), "did we already export this item" is not a fact the server can hold, because the server never touches Reminders at all.

## Decision

**1. Export bookkeeping lives in the local SQLite mirror, not Supabase.** A new table, `grocery_exports` (schema v9, `src/db/schema.ts`) — `weekly_plan_id`, `item_hash`, `household_id`, `reminder_id`, `exported_at`, primary key `(weekly_plan_id, item_hash)`. `item_hash` is exactly the deterministic hash ADR-0022 already computes for merge/selection identity — Phase 14 needed no identity scheme of its own, just a reason to finally use that hash as an idempotency key, which ADR-0022's own Consequences section anticipated. Household-scoped (`household_id` column, matching every other local table's pattern per ADR-0020) even though ADR-0004 means it can never actually be exercised by a household switch in MVP — kept for consistency with the established pattern, not because the scenario is reachable today.

**2. `grocery_exports` survives sign-out, deliberately excluded from `wipeDatabase()`'s table list** — the same reasoning `database.ts` already documents for `import_outbox`: an exported reminder is a real, already-happened side effect in a system (EventKit) this app doesn't control and can't undo by wiping its own local cache. If sign-out wiped this table, re-exporting the same plan after signing back in would recreate every item as a duplicate in the real Reminders app, silently defeating "duplicate protection" the moment a session boundary crossed it.

**3. Duplicate protection = "have we recorded a `grocery_exports` row for this `(weekly_plan_id, item_hash)`, and is that reminder still open."** Before creating a reminder, the export function checks the local table; a hit is skipped, not re-created. This is also what makes retry free: **retrying a partially-failed export is just running the same export operation again** — already-succeeded items are skipped via this same check, so there is no separate "retry" code path or stored "pending retry" state to maintain. An item's `itemHash` stays stable across list regenerations (ADR-0022 decision 6), so this also survives the ordinary case of revisiting the review screen (which always recomputes the list fresh) between two export attempts.

> **Amended 2026-08-08 (developer device-testing feedback):** the original version of this decision treated a `grocery_exports` row as an unconditional, permanent skip. That's wrong given decision 6 below and ADR-0021: `weekly_plans` is a singleton per `(household_id, week_key)`, so clearing/replanning a week reuses the same `weekly_plan_id` rather than minting a new one. A row recorded from a prior shopping trip can easily outlive that trip — the developer hit this directly (exported, checked everything off, cleared the plan, replanned, re-exported, and got "nothing added" because every item_hash was still on record from the first pass). A skip is now conditional on the recorded `reminder_id` still being open in Reminders, checked via a single `getActiveReminderIds()` call (one `getRemindersAsync` per export, not one `getReminderAsync` per item) before the loop. This also fixes a second, narrower case for free: a reminder the user deletes by hand (not via completion) simply stops appearing in that fetch, so it's treated the same as completed — eligible for re-export, no separate "not found" branch needed. `recordExport`'s existing `on conflict … do update` (decision 1) already made overwriting a stale row's `reminder_id` safe; this amendment is what actually triggers that path in the case that matters. Decision 4 (no un-export) is unaffected — this only changes when a row stops being treated as "still true," not the never-delete-a-reminder-Keepsake-didn't-just-create posture.

**4. Already-exported items are never touched again if later excluded from review.** No delete/un-export mechanism exists — removing a reminder the user (or someone else) may have already interacted with in their own Reminders app is exactly the kind of "unrelated list modification" the phase's own security section rules out, and no build-scope bullet asks for it. An accepted, documented gap: unchecking an item in review after it's been exported does not retract it from Reminders.

**5. Point-of-use permission, with `canAskAgain` driving recovery.** `requestReminderPermission()` (evolved from the Phase 1 spike's boolean-returning version to return the full `PermissionResponse` — `{ granted, canAskAgain, status, expires }` — its only caller before this phase was its own test) is called only when the user taps Export, not at screen load or app launch. iOS never re-prompts once a permission is denied; when the response is `granted: false` and `canAskAgain: false`, the UI shows a distinct "recovery" state with an "Open Settings" action (`Linking.openSettings()`, `expo-linking` — already this codebase's Linking import of choice where richer than `react-native`'s, see `src/settings/SettingsScreen.tsx`) rather than a dead-end error.

**6. "Pantry list strategy" is the Phase 1 spike's answer, wired into the real flow.** `getOrCreateGroceryList()` finds-or-creates one persistently-reused "Keepsake Groceries" list — never a new list per export, never per household member (each device has its own list by construction, since Reminders itself is per-device). Called at the start of every export; cheap and idempotent.

**7. Export is a synchronous, in-screen action, not a new polling screen.** Unlike URL import (Phase 8/9, genuinely async and server-processed, hence `ImportActivityScreen`'s poll-and-summarize pattern), an EventKit write is a fast local call with no server round trip and no job queue — sequentially looping a typical grocery list's ~10-30 items completes in a few seconds. A dedicated result panel (`GroceryExportPanel`, rendered inline on `GroceryReviewScreen`) shows a live per-item count while running, then a summary (added / already exported / failed) with "Open Reminders" (`Linking.openURL('x-apple-reminderkit://')`, the exact URL the Phase 1 spike verified opens the real app) and, when anything failed, a "Retry failed items" button that — per decision 3 — is just the same export call again.

**8. "No reminder content in logs" is enforced by omission, not redaction.** The export function's failure records carry `itemHash` and the native error message, never the item's display text (`amounts.join(', ')`, the actual grocery content); nothing in the export path calls `trackEvent`/`logError` with an item's text at all — there was simply never a reason to.

## Alternatives considered

- **Server-side export records (a new Supabase table, e.g. shared across household members).** Rejected: Reminders has no cross-device representation to reconcile against, so a shared server record would claim a level of shared truth ("this household exported X") that doesn't correspond to any shared reality — two members' phones have two independent Reminders lists. Local-only avoids inventing a fiction.
- **A separate "already exported" marker fetched from the server alongside `grocery_item_selections`.** Rejected for the same reason — plus it would need a way to reconcile against a local EventKit list the server can never see, which the local-only approach doesn't need to solve.
- **Query existing Reminders by title text before creating, instead of a local table.** Rejected: title strings aren't a stable identity (two different underlying items could format to the same text; the same item's formatted text can change between a merge-rule tweak or a scaling recompute), and a live EventKit scan for every export is slower and messier than a keyed local lookup this app already has the infrastructure for.
- **A dedicated `ImportActivityScreen`-style polling result screen.** Rejected: there's no async job to poll — the operation is a synchronous loop with a result available immediately after; a full navigable screen for that is unnecessary weight matching execution-plan.md's own "prevent scope expansion" principle.
- **Un-export (delete the reminder) when an item is excluded after having been exported.** Rejected: touches a system this app doesn't fully control and the user may have already interacted with directly; no build-scope bullet asks for it.

## Consequences

- New local-only migration (`src/db/schema.ts` v9 → `grocery_exports`), no Supabase migration, no RLS — the first Phase 14+ table with zero server involvement in this app.
- `requestReminderPermission()`'s return type changes (boolean → `PermissionResponse`) — a breaking signature change, but its only prior caller was its own test file (Phase 1 spike, never wired into a real screen), so there's no other call site to update.
- Reinstalling the app (or restoring a device from backup that predates this table, however unlikely) loses export history entirely — a fresh local database has no row to match against, so a re-export after reinstall would recreate every item as a duplicate in Reminders. Accepted: this mirrors the general local-mirror-is-rebuildable posture everywhere else in this app, and a full reinstall is a much rarer event than an ordinary sign-out.
- Because retry is just "run export again," there is no separate retry-tracking state to keep correct — one less thing to get wrong, but also means a transient failure and a permanent one look identical to the retry mechanism (both just get attempted again). Acceptable for a friends/family-scale app; nothing here distinguishes "will never succeed" from "failed once."
