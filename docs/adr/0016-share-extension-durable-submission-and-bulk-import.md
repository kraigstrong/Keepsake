# ADR-0016: Final Share Extension durable submission, and bulk URL import

- **Status:** Accepted
- **Date:** 2026-08-05
- **Phase:** 9

## Context

Phase 9's build scope (execution-plan.md) has two halves that share very little implementation but the same exit gate: turn the Phase 1 Share Extension spike into a durable submission path (offline staging, retry handoff, signed-out recovery), and add bulk URL import (multiple URLs at once, from a pasted list, per the developer's choice — a multi-line paste box, not a repeatable-row UI or Share-Sheet-multi-select).

`docs/risk-spikes/durable-import-submission.md` (Phase 1) already designed the Share Extension half in detail — App Group queue directory, local SQLite outbox, client-generated idempotency key. This ADR adopts that design as-is and resolves what it left open, plus the bulk-import half it explicitly didn't cover, plus one real conflict the durable-submission design creates against an existing Phase 6 decision.

Four things neither the PRD, execution-plan.md, nor an existing ADR resolves:

1. **The outbox and Phase 6's sign-out wipe are in tension.** ADR-0013 (Phase 6) wipes the entire local SQLite file on sign-out (`wipeDatabase()`) — reasonable for a rebuildable server mirror, but the durable-import-submission design's outbox is the opposite: the *only* copy of a not-yet-submitted share until it reaches the server. Phase 9's own build scope explicitly lists "Signed-out recovery" — an outbox wiped on sign-out cannot recover anything.
2. **Phase 8's `import_jobs`/`create_import_job` has no client-supplied idempotency key.** The server generates the id and the abuse-control cooldown assumes one interactive request at a time (execution-plan.md's Phase 8 "Idempotency" bullet was satisfied there by duplicate-URL detection, not a replay key — durable-import-submission.md decision 4 explicitly calls this out as insufficient for a client that can't wait synchronously and may retry after a kill).
3. **What does "batch job" mean server-side**, and how do bulk submission and the existing per-request rate limits (5s cooldown, 30/rolling-hour cap) coexist without either defeating bulk import's purpose (20 back-to-back 5s waits) or letting one batch call blow through the hourly cap unnoticed?
4. **How does "leave-and-return progress" work** when neither a Share Extension submission nor a bulk batch can hold a screen open for the full duration (Phase 1's spike measured ~13s per Claude call — a batch of several URLs is minutes, not seconds)?

## Decision

**1. The outbox is a separate SQLite table, explicitly excluded from `wipeDatabase()`.** `import_outbox` lives in the same local database file as the recipe mirror (one `expo-sqlite` connection, simplest migration story) but `src/db/wipeDatabase()` is changed from "drop the file" to "delete rows from the recipe-mirror tables by name" (`recipes`, `recipe_ingredient_sections`, `recipe_ingredients`, `recipe_instruction_sections`, `recipe_instructions`, `recipe_fts`, `recipe_trigram`, `deleted_recipes`, `sync_cursor`) — `import_outbox` is not in that list. A signed-out share now genuinely survives sign-out, matching this phase's own "Signed-out recovery" bullet; it drains and submits on the next sign-in, gated on session state exactly as durable-import-submission.md decision 5 describes ("same retry loop as offline, just gated on session state instead of network state"). Cached hero images (`ImageStore`) are unaffected either way — untouched by this table's presence.

**2. `create_import_job` and the new `create_import_batch` both accept an optional client-generated UUID and are idempotent on it.** `import_jobs` gains a nullable `client_import_id uuid`, unique per household (partial index, same null-handling pattern as `recipe_drafts`' partial unique indexes from ADR-0011). If a caller supplies one that already exists for their household, the RPC returns the existing row — whatever its current status — instead of inserting a duplicate or erroring; the Edge Function branches on this (see decision 4) to avoid re-running the pipeline (and re-spending Anthropic tokens) on a replayed request. Phase 8's existing single-URL in-app import flow keeps working unchanged by never supplying one (`client_import_id` stays `null`, normal insert). This is the idempotency key durable-import-submission.md's decision 4 already named — the outbox mints it at capture time (Share Extension) or at submission time (bulk paste, see decision 3), never invented later.

**3. Bulk paste is a direct, online, in-app action — it does not go through the offline outbox at all.** The developer's chosen UX (multi-line paste box) is submitted while signed in and connected, same trust context as Phase 8's existing single-URL screen; routing it through the Share-Extension-specific durable queue would solve a problem bulk paste doesn't have. New `import_batches` table (`id`, `household_id`, `created_by`, `client_batch_id uuid` nullable/unique-per-household, `total_count`, `created_at`); `import_jobs` gains a nullable `batch_id` FK. New RPC `create_import_batch(urls text[], client_batch_id uuid default null)`: rejects empty or >20-URL arrays (a number, not a PRD-mandated one — chosen to keep one batch call comfortably under the existing 30/rolling-hour household cap rather than being able to exhaust it in a single call); if `client_batch_id` already exists for the household, returns the existing batch + jobs instead of re-inserting (protects a bulk submission retried after a network blip from creating a second batch). The existing 5s-cooldown guard is evaluated once per *call* (batch or single), not once per URL inside a batch — a legitimate one-shot paste of 15 URLs is not the scripted-loop abuse pattern the cooldown exists to slow down; the 30/rolling-hour cap is checked against `current_count + array_length(urls)` up front and the whole batch is rejected atomically if it would exceed the cap (no partial batch, so the client never has to reconcile which of N URLs silently didn't queue).

**4. The Edge Function accepts an optional pre-created `jobId`, used by both batch items and outbox-drained Share Extension submissions; progress is a pollable `import_jobs`/`import_batches` row, not a held-open request.** `supabase/functions/import-recipe/index.ts`'s request body gains optional `jobId` and `clientImportId` fields. If `jobId` is present, the function looks up that existing job (RLS-scoped, must be the caller's own household and `status = 'processing'`) instead of calling `create_import_job` — this is what lets `create_import_batch` reserve N job rows up front (so the client has something to poll immediately, before a single Claude call has run) and lets the function process each one independently. If `clientImportId` is present (Share Extension path, no pre-created job), the function calls `create_import_job` with it; when that returns a *non*-`'processing'` row (an idempotent-replay hit), the function skips the entire pipeline — no fetch, no AI call — and returns the already-stored outcome directly, satisfying "Replays are idempotent" without a second Anthropic charge. For "leave-and-return progress": the client fires each batch item's Edge Function call with limited concurrency (3 at a time, chosen to bound simultaneous Anthropic spend/rate without serializing a 20-item batch into minutes of dead time) and does not require the initiating screen to stay mounted — a lightweight polling read of `import_jobs where batch_id = X` (RLS already scopes it) is what renders progress, so navigating away and back just re-subscribes to the same rows rather than needing any client-held state. If the app is killed mid-batch, jobs left at `status = 'processing'` with no in-flight client call are picked back up on next launch: the client re-issues the Edge Function call for any of *its own* batch's still-`processing` jobs it doesn't have a known-in-flight request for — safe by construction, since `complete_import_job`/`fail_import_job` only transition a row that's still `'processing'`, so a duplicate call against an already-finished job fails harmlessly and is ignored client-side.

**5. The Share Extension's confirmation state changes from a 0.6s auto-dismiss to a 1.5s state with a checkmark icon and a success haptic**, addressing the Phase 1 physical-device finding (`docs/risk-spikes/safari-share-extension.md`) directly. `ShareViewController.swift` now writes into a `share-inbox/` directory (one `<uuid>.json` file per share, matching durable-import-submission.md decision 1) with an `id` field carrying that UUID, shows `UINotificationFeedbackGenerator().notificationOccurred(.success)` plus a checkmark, then dismisses — still "send and go," not a composer, just legible enough to register per the developer's original "it just disappeared" complaint.

## Alternatives considered

- **Route bulk paste through the same outbox/idempotency-key path as the Share Extension.** Rejected: bulk paste has none of the failure modes (background process, no session guarantee, app-not-open) the outbox exists for — it's a normal foreground authenticated form submission, and forcing it through the outbox would add a drain/poll round-trip for no benefit.
- **A real background job queue (server-side worker) for batch processing**, instead of the client driving each batch item's Edge Function call itself. Rejected for the same reason ADR-0015 rejected it for Phase 8: no infrastructure exists for it yet, and client-driven-with-limited-concurrency is sufficient for the stated scale (a pasted list, not a sitewide crawl) while keeping the same "no queue infra" posture Phase 8 established — revisit only if real usage shows the client-must-be-reachable-during-processing assumption breaks down in practice.
- **Cap batch size much higher (e.g. 50–100) to match "bulk."** Rejected: 20 keeps one batch comfortably inside the existing hourly household cap (30) with room for other imports the same hour, and a pasted list beyond ~20 recipes at once is an unusual enough case that a second paste is a reasonable ask rather than a limit worth designing further around now.
- **Keep `wipeDatabase()` dropping the whole file, and stage signed-out shares in a separate non-SQLite store (e.g. a flat file) instead.** Rejected: adds a second persistence mechanism and a second migration/durability story for no real benefit over just excluding one table by name from the wipe — `expo-sqlite`'s per-table `DELETE` is no less reliable than a file-based store here.

## Consequences

- **`docs/threat-model.md`** needs a new or extended entry: bulk import's atomic hourly-cap check (decision 3) is this phase's version of T6's "missing rate limits" category, and idempotent replay (decision 2) is this phase's concrete answer to execution-plan.md's Phase 9 "Replays are idempotent" security bullet — both to be recorded once built, not assumed.
- **`ImageStore`/hero-image caching (Phase 6) is unaffected** — `import_outbox` carries only URLs and status, no image data.
- **Phase 8's Edge Function gains two optional request fields** (`jobId`, `clientImportId`) but its existing single-URL, no-optional-fields call shape from the in-app import screen keeps working unchanged — this is an additive, backward-compatible change, not a rewrite of the Phase 8 pipeline.
- **Testability:** the schema/RPC changes (idempotent replay, batch atomicity, cap-against-batch-size) are pgTAP-testable the same way Phase 8's abuse controls were — real Postgres, no mocking. The Swift changes (directory-based queue, confirmation UX) can only be verified by a real Simulator/device pass, same category as every Share-Extension-touching change since Phase 1 — required physical-device demonstration for this phase's exit gate, per ADR-0003.
