## Phase 4 summary (for reference — see History below once the exit record lands)

13 commits on `phase-4-manual-recipe`. ADR-0010: recipe data model decisions (sections as separate ingredient/instruction table pairs with plain-text lines, not structured quantity/unit — that's Phase 11's job; categories as a seeded lookup table, not an enum or free array; tags as plain `text[]`; no versioning/lifecycle/AI this phase). Schema + RLS for `recipes`/`recipe_ingredient_sections`/`recipe_ingredients`/`recipe_instruction_sections`/`recipe_instructions`/`categories`/`recipe_categories`, `household_id` denormalized onto every child table so RLS stays a flat `is_household_member(household_id)` check everywhere (ADR-0004: a recipe's household never changes). Single `save_recipe` RPC handles both create and edit atomically — wipes and reinserts child rows on edit rather than diffing, since child rows have no external identity; pgTAP proves real atomicity (an invalid category mid-write rolls back the whole recipe, not just the bad row) alongside cross-household denial and no-household denial. Client `src/recipes/api.ts` wraps the nested-embed read and the RPC write. Hero image handling (`src/recipes/heroImage.ts`): native square-crop UI via `expo-image-picker`, an explicit `expo-image-manipulator` resize+re-encode pass (strips EXIF as a side effect — SEC checklist item, not incidental), upload to the Phase 3 `recipe-images` bucket keyed by a random id (not the recipe's own id, since a hero photo can be picked before a new recipe has an id yet), and a signed-URL helper for display since the bucket is private. `RecipeEditorScreen` (create and edit share one screen/form) and `RecipeDetailScreen` (read-only) as testable `src/recipes/` components with thin `app/recipe/` route wrappers; `LibraryScreen` rewritten to fetch real recipes on tab focus (not just mount, so returning from create/edit shows the change) with loading/error/empty states; the global Add sheet's "Create manually" option now actually navigates to `/recipe/new` instead of showing a placeholder.

Found and fixed a real bug while writing this phase's end-to-end route tests: `app/_layout.tsx`'s `Stack.Protected` block only listed `"(tabs)"` and `"settings"` — the new `recipe/*` routes existed on disk and were fully unit-tested in isolation, but were never registered under the authenticated Stack, so `/recipe/new` and friends were unreachable in the real app despite looking complete. Added `app/recipe/_layout.tsx` (mirrors Settings' header styling) and registered it; `src/navigation/recipeRoutes.test.tsx` now exercises create/detail/edit through the real router, which is what caught it.

REC-01/02/03/04/06/07/09, IMP-06, IMG-04, ORG-01/02/03 → `Done (tested)`; NOTE-04 → `In Progress` (Phase 4 only materializes its half — permanent notes as their own column — the "separate from cooking history" half needs Phase 15 to exist to mean anything). 42 suites, 203 passed, 1 skipped; typecheck/lint/format clean. No Simulator/device verification this phase (see Current's Blocked-on note) — the whole phase's UI evidence is Jest: component-level tests per screen plus `expo-router/testing-library` `renderRouter` tests proving the routes are reachable end-to-end, not just isolated renders.
