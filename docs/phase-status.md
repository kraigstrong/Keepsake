## JSON-LD structured-data import hint (ADR-0019, cross-cutting — not a numbered phase)

Developer-flagged gap, 2026-08-06: `reduceHtmlToText` (Phase 8, ADR-0015 decision 6) unconditionally strips `<script>` tags, discarding schema.org Recipe JSON-LD that most recipe blogs carry alongside their visible content. Not previously evaluated or rejected — just never built — and explicitly out of scope for the Phase 11 units/scaling work underway on its own branch when it was noticed. ADR-0019 resolved the design question of how far to lean on it: JSON-LD becomes a sanitized text hint prepended to what Claude already sees, never a bypass of the AI extraction call — prd.md §8 documents one workflow ("Page reduced to relevant text → AI parses → Uncertainties highlighted → Save") for every URL import, and a full bypass for "complete-looking" structured data would silently change that contract plus reintroduce category/tag inference and reconciliation logic Claude's own extraction already does. New `server/import/extractJsonLdHint.ts` (pure, Web-standard APIs only, following the existing `server/import/*.ts` pattern): finds a `Recipe` node (top-level, in a top-level array, or nested in `@graph`), flattens `recipeInstructions`' several legal shapes (string / array of strings / `HowToStep` / `HowToSection`), parses ISO 8601 durations, and sanitizes + length-caps every field (500 chars/field, 100 items/list, 4000 chars total) before formatting a labeled plain-text block — treated exactly as untrusted as the rest of the page (threat-model.md T17, same mitigation class as T5: the hint only ever becomes more prompt input, never a second path into `save_recipe`). `supabase/functions/import-recipe/index.ts`'s URL path prepends this hint to `reduceHtmlToText`'s output when present, and now also attempts extraction (rather than failing at the 200-char minimum-useful-text gate) when a thin-content page still carries real JSON-LD underneath — a real pattern on JS-rendered sites that still server-render structured data for SEO. No changes to `RecipeExtractionSchema`, the extraction prompts, or the Sonnet/Opus escalation logic — the hint is just better input to an unchanged call. 22 new Jest tests (`extractJsonLdHint.test.ts`) cover `@graph`/array-`@type`/top-level-array Recipe discovery, all four `recipeInstructions` shapes, ISO 8601 duration parsing (including unparseable-duration honesty), HTML/entity sanitization, malformed-block skip-and-continue, and every length/count cap. No PRD IDs owned (strengthens AI-01/05/06/08's existing reliability, isn't a distinct requirement); no schema, RPC, or telemetry changes. Not yet verified with a live Anthropic call (needs the developer watching, per this project's live-API-test convention) — Jest evidence only at this point, same category every other `server/import/*.ts` module started in before its first live/staging exercise.

**Not yet confirmed:** the 1.5s+checkmark+haptic Share Extension confirmation UI — screenshots kept landing just after it would have shown. The file-write succeeding (which gates that code path) makes it very likely correct, but "likely" isn't "confirmed" the way everything else is.

**Five real gaps found live and fixed this same session:**
1. A Share-Extension-originated import had no user-visible signal at all once the background drain/submit finished — no screen, no toast, nothing; the developer had to ask "where did it go?" to surface this. Fixed: `submitPendingOutboxItems()` now returns per-item outcomes, and `app/_layout.tsx` shows a toast summarizing them via the existing `ToastProvider`.
2. A recipe's hero image can silently vanish after import. Root cause: a **pre-existing Phase 6 bug**, not Phase 9's — both `ensureImageCached` and `readCachedImageUri` trusted a `cached_images` row's `local_uri` without checking the file still exists, and iOS is documented to purge `Library/Caches/` under storage pressure at any time — exactly where hero images live (ADR-0013). A live, latent bug for any real user, not just this session's repeated terminate/relaunch testing (which happened to reproduce it reliably). Fixed: `ImageStore` gained `fileExists(uri)`, checked before trusting a cache hit.
3. The hero image's first-view load was a genuine layout jump (a 200×200 placeholder swapping to a full-width 200-tall image), not just a content pop, and the fallback path never cached what it fetched — meaning a just-imported recipe re-fetched and re-downloaded its image from the network on *every* view, not just the first. Fixed: the placeholder is now sized to match the real image and stays mounted underneath, crossfading the image in on load; the fallback path now caches via `offlineRecipes.cacheHeroImage`.
4. Drain/submit only ran on cold launch or network reconnect — not a plain foreground, which is the actual realistic path ("share from Safari, switch back to Keepsake," not force-quit-and-relaunch). Confirmed live: a share sat undrained in the queue for a full minute until the app was foregrounded. Fixed: `ImportOutboxLifecycle` now also listens for `AppState` transitioning to `'active'`, mirroring `SessionProvider`'s existing pattern.
5. **The serious one**: sharing one URL produced two separate recipes, 3 seconds apart, from a single outbox entry. The existing idempotent-replay check only protects against replaying an *already-finished* job — it does nothing when two concurrent callers both find the same job while it's still genuinely in flight (very plausibly made easier to hit by fix #4 adding another trigger point). Both calls ran the full pipeline independently, each creating its own recipe. Fixed with `claim_import_job` — an atomic, single-winner claim (60s staleness window) — plus a `recipes(household_id, source_url)` partial unique index as a database-level backstop independent of the specific fix. This is the same underlying issue previously tracked as an unexplained "double-processing" delay (self-healing, no visible data loss) — it wasn't harmless, it just hadn't produced a visible duplicate yet.

## Carried-forward items (not phase-blocking, but tracked so they aren't lost)

- **Share Extension confirmation-state UX** — physical-device finding: the "Saved to Keepsake" state (0.6s) is too brief to register as a real confirmation. Phase 9 ("Final Share Extension") should evaluate a longer/more legible confirmation, a success icon, or haptics. See `docs/risk-spikes/safari-share-extension.md`.
- **`captureFromCamera()` physical-device confirmation** — deliberately deferred by the developer (not forgotten). Low risk: shares its permission/cancel pattern with the already-confirmed `pickExistingPhoto()`. Worth a quick check before Phase 10 builds on top of it.
- **"No server credential in client bundle" CI check** — deferred since Phase 0, still not built. `server/ai/extractRecipe.ts` references `ANTHROPIC_API_KEY`. Phase 3 ended up needing no new server-side secret at all (ADR-0008: RPCs, not Edge Functions — no `SUPABASE_SERVICE_ROLE_KEY`), so this didn't get more urgent this phase, but it's worth building before whichever phase first adds a real Edge Function.
- **1Password CLI wiring into CI** (Service Account + `op run`) — still not added. Concrete consequence: Phase 1's live Claude-extraction test is `describe.skip`-gated on `ANTHROPIC_API_KEY`, which is never present in CI. Phase 3's local-Supabase auth/RPC tests didn't need it (local dev/CI uses the Supabase CLI's own generated keys, no 1Password involvement — see execution-plan.md's secret-timing note), but real staging email-OTP delivery will need it eventually.
- **1Password SSH agent guidance** — not addressed. Low priority for a single-developer project.
- **Squash-merge is still allowed at the repo level** — not urgent, not yet revisited.
- **Fake-secret detection fixture** — deliberately not built, trusting gitleaks' maintained ruleset instead.
- **`@bacons/apple-targets` dependency-scan exception** — re-run `npm audit` without `--omit=dev` periodically to check whether the upstream `@xmldom/xmldom` finding gets a fix.
- **Local SQLite cache is included in iOS device/iCloud backups** — found in Phase 6 (ADR-0013's "Backup implications" section). `expo-sqlite`'s default location is the backed-up Documents-directory-equivalent, not the (correctly-excluded) cache directory hero images use. Judged low-severity (a rebuildable server mirror, no credentials) and not fixed blind — `openDatabaseAsync`'s `directory` override could redirect it to `Paths.cache`, but `Directory.uri`'s `file://`-prefixed format vs. `defaultDatabaseDirectory`'s plain-path format needs on-device verification before trusting it. Still not addressed — Phase 7 added two more local-DB schema migrations (FTS tables, `created_at`) without touching this. Worth a real-device check before too many more phases stack on top of the local DB.
- **Sentry/PostHog accounts** — not yet created; both stay no-ops until the developer adds real `EXPO_PUBLIC_SENTRY_DSN`/`EXPO_PUBLIC_POSTHOG_KEY` values to the `Keepsake Client` 1Password Environment. `@sentry/react-native`'s native config plugin (source-map/debug-symbol upload) is deliberately not added to `app.json` until then either — see the "Wire redacted logging" Phase 2 commit message for the reasoning.
- **Brief onboarding flash on cold launch** — physical-device finding, 2026-08-04: on reload, the "What should we call you?" onboarding screen flashes for a fraction of a second before correctly landing on This Week for an already-onboarded user. Likely `AuthenticatedRouteBoundary`'s session-then-household loading sequencing (a window where session is confirmed but household/profile hasn't resolved yet renders the `needsOnboarding` branch). Not urgent — developer's own call to defer. Best fit is probably Phase 18 (Performance, Accessibility, Privacy, Security, and Reliability Hardening) under its general polish/reliability scope, but no phase owns loading-state UX specifically; reassess when picked up.
- **Add/Settings visual redesign** — developer feedback, 2026-08-04: dissatisfied with the current look/feel of the global Add sheet and Settings screen, separate from the sheet-open-from-header-vs-library-empty-state consistency fix already shipped this phase. Developer intends to revisit with a fresh design pass later; no specific phase assigned yet.
- **ORG-04/AI-06 category mapping is coincidence-reliable, not robust** — found at Phase 8 exit review. Import's category assignment is exact-string matching Claude's free-text guess against an 11-value seeded vocabulary Claude is never told about; it works because the guess happens to line up (confirmed in live testing), not by design. Worth passing the real category list into the extraction prompt so the AI targets the actual vocabulary directly. No phase assigned yet.
- **Staging magic-link email is unusable for real sign-up** — found 2026-08-03 on the first real physical-device sign-in attempt. `signInWithOtp` sends Supabase's *default* magic-link template, which only renders a clickable `{{ .ConfirmationURL }}` link, not the `{{ .Token }}` code `verifyOtp` expects the user to type — so there's no code to enter even if the link worked. The link also 404s today since the staging project's Auth "Site URL" is still Supabase's scaffolding default (`http://localhost:3000`), same unedited default sitting in `supabase/config.toml`. Not blocking phase-by-phase dev testing (bootstrap a test account by hand via Dashboard → Authentication → Users → Add user, with a password, then use "Sign in with password instead"), but a real blocker for any actual new user signing up before launch. Fix: add a custom `magic_link` email template (`supabase/templates/`) surfacing `{{ .Token }}`, matching the existing SMS OTP template pattern (`"Your code is {{ .Code }}"`), and push it to the staging project (needs `supabase link` + a Supabase access token, or a manual Dashboard edit — developer's call, not attempted yet).

- **Orphaned original-photo Storage objects (T15, Phase 10, ADR-0017)** — upload-before-processing means a photo upload that succeeds but whose extraction/save fails afterward (or whose client abandons the flow mid-way) leaves an unreferenced object in the `recipe-images` bucket. Not a data-exposure risk (already household-scoped by the bucket's existing RLS), just an accumulating storage-cost item. No cleanup mechanism built yet — Phase 9's 30-day outbox expiry is a plausible pattern to reuse if this becomes a real cost concern in practice.
