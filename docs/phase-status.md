ADR-0014 resolved three design questions before writing schema or client code: FTS5 tables are standalone, not external-content against `recipes` (recipes.id is a text UUID; SQLite's implicit rowid for external-content linking isn't VACUUM-stable) — `recipe_id` is a plain `unindexed` FTS5 column instead, maintained by the sync engine's delete-then-reinsert, not SQL triggers. ## Carried-forward items (not phase-blocking, but tracked so they aren't lost)

- **Share Extension confirmation-state UX** — physical-device finding: the "Saved to Keepsake" state (0.6s) is too brief to register as a real confirmation. Phase 9 ("Final Share Extension") should evaluate a longer/more legible confirmation, a success icon, or haptics. See `docs/risk-spikes/safari-share-extension.md`.
- **`captureFromCamera()` physical-device confirmation** — deliberately deferred by the developer (not forgotten). Low risk: shares its permission/cancel pattern with the already-confirmed `pickExistingPhoto()`. Worth a quick check before Phase 10 builds on top of it.
- **"No server credential in client bundle" CI check** — deferred since Phase 0, still not built. `server/ai/extractRecipe.ts` references `ANTHROPIC_API_KEY`. Phase 3 ended up needing no new server-side secret at all (ADR-0008: RPCs, not Edge Functions — no `SUPABASE_SERVICE_ROLE_KEY`), so this didn't get more urgent this phase, but it's worth building before whichever phase first adds a real Edge Function.
- **1Password CLI wiring into CI** (Service Account + `op run`) — still not added. Concrete consequence: Phase 1's live Claude-extraction test is `describe.skip`-gated on `ANTHROPIC_API_KEY`, which is never present in CI. Phase 3's local-Supabase auth/RPC tests didn't need it (local dev/CI uses the Supabase CLI's own generated keys, no 1Password involvement — see execution-plan.md's secret-timing note), but real staging email-OTP delivery will need it eventually.
- **1Password SSH agent guidance** — not addressed. Low priority for a single-developer project.
- **Squash-merge is still allowed at the repo level** — not urgent, not yet revisited.
- **Fake-secret detection fixture** — deliberately not built, trusting gitleaks' maintained ruleset instead.
- **`@bacons/apple-targets` dependency-scan exception** — re-run `npm audit` without `--omit=dev` periodically to check whether the upstream `@xmldom/xmldom` finding gets a fix.
- **Local SQLite cache is included in iOS device/iCloud backups** — found in Phase 6 (ADR-0013's "Backup implications" section). `expo-sqlite`'s default location is the backed-up Documents-directory-equivalent, not the (correctly-excluded) cache directory hero images use. Judged low-severity (a rebuildable server mirror, no credentials) and not fixed blind — `openDatabaseAsync`'s `directory` override could redirect it to `Paths.cache`, but `Directory.uri`'s `file://`-prefixed format vs. `defaultDatabaseDirectory`'s plain-path format needs on-device verification before trusting it. Still not addressed — Phase 7 added two more local-DB schema migrations (FTS tables, `created_at`) without touching this. Worth a real-device check before too many more phases stack on top of the local DB.
- **Sentry/PostHog accounts** — not yet created; both stay no-ops until the developer adds real `EXPO_PUBLIC_SENTRY_DSN`/`EXPO_PUBLIC_POSTHOG_KEY` values to the `Keepsake Client` 1Password Environment. `@sentry/react-native`'s native config plugin (source-map/debug-symbol upload) is deliberately not added to `app.json` until then either — see the "Wire redacted logging" Phase 2 commit message for the reasoning.
- **Brief onboarding flash on cold launch** — physical-device finding, 2026-08-04: on reload, the "What should we call you?" onboarding screen flashes for a fraction of a second before correctly landing on This Week for an already-onboarded user. Likely `AuthenticatedRouteBoundary`'s session-then-household loading sequencing (a window where session is confirmed but household/profile hasn't resolved yet renders the `needsOnboarding` branch). Not urgent — developer's own call to defer. Best fit is probably Phase 18 (Performance, Accessibility, Privacy, Security, and Reliability Hardening) under its general polish/reliability scope, but no phase owns loading-state UX specifically; reassess when picked up.
- **Add/Settings visual redesign** — developer feedback, 2026-08-04: dissatisfied with the current look/feel of the global Add sheet and Settings screen, separate from the sheet-open-from-header-vs-library-empty-state consistency fix already shipped this phase. Developer intends to revisit with a fresh design pass later; no specific phase assigned yet.
- **Staging magic-link email is unusable for real sign-up** — found 2026-08-03 on the first real physical-device sign-in attempt. `signInWithOtp` sends Supabase's *default* magic-link template, which only renders a clickable `{{ .ConfirmationURL }}` link, not the `{{ .Token }}` code `verifyOtp` expects the user to type — so there's no code to enter even if the link worked. The link also 404s today since the staging project's Auth "Site URL" is still Supabase's scaffolding default (`http://localhost:3000`), same unedited default sitting in `supabase/config.toml`. Not blocking phase-by-phase dev testing (bootstrap a test account by hand via Dashboard → Authentication → Users → Add user, with a password, then use "Sign in with password instead"), but a real blocker for any actual new user signing up before launch. Fix: add a custom `magic_link` email template (`supabase/templates/`) surfacing `{{ .Token }}`, matching the existing SMS OTP template pattern (`"Your code is {{ .Code }}"`), and push it to the staging project (needs `supabase link` + a Supabase access token, or a manual Dashboard edit — developer's call, not attempted yet).
