- **Phase 17 walkthrough — 79 of 139 `recipe_ingredients` rows (57%) on staging had never been parsed** (`ingredient_text`/`quantity_min`/`unit` all `null`), found while root-causing why "large eggs" and "large eggs, at room temperature" wouldn't merge on the grocery list. Every recipe created on 2026-08-05 was 100% unparsed; everything from 2026-08-07 onward (when Phase 11's parsing pipeline actually landed) was mostly or fully parsed — the five pre-Phase-11 recipes' ingredient rows were simply never backfilled once parsing shipped. One-time backfill run directly against staging, 2026-08-14 (developer approved): re-ran `parseQuantity()` — pure syntax, no AI call — against all 79 null rows and updated the 70 that now parse cleanly; 9 stayed `null` correctly (genuinely quantity-less lines like "Salt and pepper, to taste," "Butter, for coating the pan"). No code changed — this was a data-only fix for historical rows; new imports have gone through the real parser since Phase 11.
- **Phase 17 walkthrough — alternate-unit annotations ("1 lb / 500g beef," "800g, 28oz can crushed tomato," "(290 g) all-purpose flour") didn't scale, and the parenthesized form was also silently blocking "all purpose flour" from folding into "flour."** Only the leading quantity is ever structured (ADR-0018 — one quantity/unit per line); a second, alternate-unit number sitting inertly inside `ingredientText` doesn't scale with it ("3 lb / 500g beef" after 3x is visibly wrong), and when it sat *before* the ingredient name (the parenthesized form), it blocked `canonicalKey()`'s `DEFAULT_VARIETY_PREFIXES` fold from ever reaching "all-purpose" — which also silently broke staple detection for the same ingredient, since `isStaple()` checks the same canonical key. Fixed in `parseQuantity.ts` (`stripAlternateUnit`/`stripParentheticalAlternateUnit`): stripped at parse time rather than parsed and scaled — developer decision, matches the "don't show a number this code can't vouch for" posture ADR-0018 already takes, and Original/Preferred unit display (UNIT-02) already covers seeing a converted amount that stays in sync with scaling. `import-recipe` redeployed twice (`parseQuantity.ts` is bundled into it) so new imports get both fixes. Backfilled 20 already-parsed-but-still-noisy rows across staging (3 slash/comma, 17 parenthetical) — the earlier 79-row null-parse backfill didn't touch these since they already had non-null `quantity_min`. Confirmed fixed: `canonicalKey('flour') === canonicalKey('all-purpose flour')` and `isStaple()` agrees on both.
- **Phase 17 walkthrough — the grocery list had the same "whichever unit the source wrote first" problem as Cooking Mode, and stripping the alternate unit (previous item) made it worse.** Once only one unit survived parsing, the grocery list showed exactly that unit with no awareness of the household's own preference ("2400g tomato, 1lb beef" on the list itself, not just in Cooking Mode). Developer wanted the surviving unit to default to whichever the household prefers when a recipe originally listed both ("800g/28oz crushed tomato" should show as 28oz, not 800g). Fixed by threading the same `fetchProfile` → `preferredUnitSystem` → `convertToSystem()` flow already shipped for Cooking Mode through `generateGroceryList()`/`fetchGroceryReview()`/`GroceryReviewScreen.tsx`, converting each occurrence before grouping (unit class survives conversion, so summability is unaffected — only which unit a total lands in). Developer explicitly declined a packaging-size special case (e.g. always favoring "28oz" as a recognizable can size over whatever `bestFitUnit` computes) — chose "keep it consistent" with Cooking Mode/Recipe Detail's existing best-fit behavior. No Edge Function redeploy needed (grocery generation is client-side only).
- **Two rarer alternate-unit phrasings found while inspecting the backfill, deliberately not chased further:** `"3 cup(s) all-purpose flour"` (an optional-plural `"(s)"` directly suffixed to the unit word, not a number — `stripParentheticalAlternateUnit` correctly declines to touch it, leaving `"(s) all-purpose flour"`) and `"(600 ml / 290 g) all-purpose flour"` (two alternate units nested inside one parenthetical — the strip expects a single number+unit before the closing paren, so a `/`-separated pair inside stops it early, leaving the whole parenthetical). Neither was part of what was reported; both are narrower, rarer variants of the same underlying pattern. Revisit only if they turn out to be common enough to matter — same "accept some gap, escalate deliberately" posture this app already takes elsewhere (ADR-0018/ADR-0022), not something to keep patching blind.
- **Codex review, PR #54 — three findings, 2026-08-16.** (1) LIB-01's 2-week cutoff was inclusive at the exact boundary (`>= cutoff`), one day past what "\<2wk" (strict) requires — fixed to `> cutoff` (developer decision: match the literal requirement rather than keep the inclusive interpretation), `librarySort.test.ts` now covers both sides of the boundary. (2) The Phase 16 audit-actor migration (`archived_by`/`deleted_by`/`restored_by`) was real and already pushed to staging, but stranded on `docs/phase-16-exit-decision` — never merged into any Phase 17 branch, so this doc's own "re-verified after the migration landed" claim didn't match this branch's history. Folded forward, same commits (`git cherry-pick`), no new migration written. (3) **New finding, not previously covered:** photo-import uploads declare their own `contentType` to Supabase Storage and the bucket's MIME allowlist trusts that declaration, not the actual bytes — `import-recipe` then sends whatever was uploaded to Anthropic as `image/jpeg` unsniffed.
