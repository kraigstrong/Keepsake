# Roadmap

Milestones organize the meaningful outcomes still ahead — the roadmap layer of `Product Vision → Milestone → Work Item → Execution`. A milestone describes what "done" looks like; it is never handed to an agent as a single execution instruction — each work item under it is planned, delegated, and reviewed individually. See `docs/architecture.md` for how the system works today and `docs/prd.md` for product requirements; this file is what's still left to build toward, not a description of the system itself.

Scope, deliberately: this roadmap stops at getting Keepsake in front of friends and family and learning from that. Release-readiness (App Store submission, production rehearsal) isn't planned here yet — revisit once Preview Learning & Iteration has actually run.

Work items are listed here as short entries — objective and why it matters. Full acceptance criteria and constraints get written when a work item is actually selected for execution, not speculatively for the whole backlog up front.

## 2. Reliability

**What done looks like:** production issues are observable and recoverable without guesswork — you can tell what broke, and the system degrades gracefully instead of losing data or getting stuck.

**Backlog:**
- Add crash reporting.
- ~~Add structured server error logging.~~ **Done, 2026-08-19** (branch `reliability/server-error-logging`) — `supabase/functions/import-recipe/index.ts` now `console.error`s at the failure branches that indicate Keepsake's own pipeline broke (AI extraction, and Storage/DB reads or writes past the point they're expected to succeed), so those are findable in Supabase's function logs without first knowing which job to query for. Deliberately does not log expected/user-driven outcomes (a losing claim race, a malformed URL, an unreachable third-party page, thin page content) — those already surface via the stored job row and response, and logging them as errors would just be noise against genuine breakage. `import-recipe` is Deno-only and has no local test coverage (per the file's own header comment); this is a design decision documented in a new comment on the `fail()` helper, not something a test asserts.
- ~~Define retry behavior for recipe import failures.~~ **Partially done, 2026-08-19** (branch `reliability/import-retry-behavior`) — the outbox now automatically retries an import that never got a confirmed response from the Edge Function (`ImportTransportError`, `src/import/api.ts`/`src/import/outboxEngine.ts`), the same treatment already given to the household-rate-limit case. See `src/import/api.ts`'s `ImportTransportError` doc comment for why the current fix can't just be extended to this case.
- Add recovery handling for interrupted image uploads.
- ~~Close the orphaned original-photo Storage object gap (T15, Phase 10/ADR-0017).~~ **Done, 2026-08-18** (branch `reliability/orphaned-photo-cleanup`) — see `docs/threat-model.md`'s T15 entry.
- Verify true two-connection concurrency for the invitation-redemption race and import-claim fencing (ADR-0020) — provable by pgTAP for logic, not yet verified under genuine concurrency. See `docs/history/phase-11.5-import-concurrency.md`'s Conditional Pass follow-ups (also `docs/threat-model.md` T18/T19).
- ~~**Enforce the category vocabulary at the schema/decoding level, not just the prompt.**~~ **Investigated and reframed, 2026-08-19** — the premise turned out to be wrong on inspection, not just unimplemented. Two problems found in `server/ai/extractRecipe.ts`'s actual call path (`@anthropic-ai/sdk@0.115.0`'s `zodOutputFormat`/`transformJSONSchema`, `node_modules/@anthropic-ai/sdk/src/lib/transform-json-schema.ts`): (1) this SDK version's structured-output path only forwards a fixed whitelist of JSON Schema keywords (`type`/`properties`/`additionalProperties`/`required`/`items`/`minItems`/a small `format` allowlist/`description`/`title`/`$ref`/`$defs`/`anyOf`/`oneOf`/`allOf`) — `enum` is not in it, so `z.enum(categoryValues)` gets flattened into a `description` string instead of a real constraint, meaning Anthropic's structured-output decoding would never actually see it as a closed set (verified directly: `zodOutputFormat` on a `z.array(z.enum([...]))` schema produces `items: { type: 'string', description: '{enum: [...]}' }`, not a JSON Schema `enum` array). (2) Separately, even if it *did* reach the API, `messages.parse()`'s own client-side validation (`zodObject.safeParse` in the SDK's `zod.ts`) would then throw and fail the *entire* extraction the moment the model emits one category string that isn't an exact case-sensitive vocabulary match — turning today's graceful degradation (`mapCategoryNamesToIds`' fuzzy match silently drops a near-miss, recipe still saves) into a hard import failure, which is a regression for a Reliability-milestone item, not a hardening. Real schema-level enforcement would need either a hand-built JSON Schema bypassing `zodOutputFormat` (unverified whether the API itself supports `enum` at all, independent of this SDK's whitelist — untested, no live call made) or a lenient variant that drops invalid entries instead of failing the parse (its own small design decision). Left here rather than actioned blind — needs a developer look before deciding whether it's worth revisiting, given the closed set is already reasonably enforced by prompt instruction + fuzzy post-hoc mapping (PR #79).

## 4. Smart Meal Selection ("Help Me Choose")

**What done looks like:** a household member can start a selection round, swipe through a deck of their own recipes, and land the ones they picked into This Week — without ever typing into a search box. Sequenced **ahead of Friends & Family Preview** (developer decision, 2026-08-20): the beta ships with this feature in it, not as a follow-up.

**Architecture:** [`docs/proposals/smart-meal-selection-architecture.md`](proposals/smart-meal-selection-architecture.md) is the codebase-grounded design — domain model, lifecycle, server operations, the deterministic non-LLM ranking heuristic, concurrency/security. [`ADR-0027`](adr/0027-smart-meal-selection-round-model.md) records the decisions from it that clear the ADR bar. Design handoff: [`docs/design/help-me-choose-handoff/`](design/help-me-choose-handoff/).

**Build order — solo flow first, walkable skeleton first** (developer decisions, 2026-08-20). Two deliberate departures from the proposal's own M1–M8 sequence, both recorded here so a reviewer doesn't have to reconstruct why:

1. **Solo before group.** Solo exercises the entire spine (round → deck → swipe → review → apply) and is verifiable by one person, so it doesn't inherit MVP Validation's blocked two-actor session. The **full four-table schema still ships up front**, including `mode`, `closes_at`, and `selection_round_participants`, and the blind-ballot RLS is written correctly from day one — a solo round is a one-participant group round as far as Postgres is concerned, so scoping down the schema would only buy a migration rewrite later. Only the RPC surface and the UI are scoped down.
2. **Walkable skeleton before smart ranking.** The client lands on a deliberately filter-only deck, so the solo path is walkable on a real device before the ranking heuristic exists; scoring is wired in after. The proposal has the client last (M6), but `docs/architecture.md`'s "vertical slices, not layers" points the other way, and deck *quality* is a judgment call that needs a developer looking at real decks — which is impossible until something walks.

**Backlog:**
- ~~Place this as a real milestone (roadmap entry + ADR).~~ **Done, 2026-08-20** — this entry and ADR-0027.
- **Extract `ServingsConfirmationStep`.** The proposal's §8/M6 assume the review step can reuse "the existing servings-confirmation component." It doesn't exist — it's a `step === 'servings'` branch inside `src/thisWeek/AddToThisWeekScreen.tsx`. Extract it as a real shared component with that screen's existing tests kept green. Independent of all server work.
- **Schema + RLS + grants**, four tables per the proposal's §2, with the pgTAP isolation suite modeled on `weekly_plan_rpcs.test.sql`. Two details from ADR-0027 that Codex review caught before any SQL existed, and that need explicit pgTAP cases rather than trusting review: the `selection_decisions` reveal predicate is an **allowlist** (`status IN ('ready_for_review','applied')`), because the obvious `!= 'active'` phrasing turns open-access `cancel_selection_round` into a ballot-disclosure path around the creator-only close gate; and rounds are born `pending_candidates` with the singleton index covering **every** non-terminal status (`pending_candidates`, `active`, `ready_for_review` — a review-stage round isn't terminal, since a refill reopens it), paired with claim-fenced adoption, so a half-finished creation is resumable without letting a delayed finalize activate a stale round later.
- **Round lifecycle RPCs + `select-candidates` Edge Function**, filter-only deck (proposal §5's filter step, no scoring), plus the client `api.ts`. **The Edge Function owns the This Week exclusion** — `finalize_selection_round_candidates` deliberately does not re-enforce it (Codex review, PR #96): the check is inherently racy, so rejecting a whole deck on a mid-flight add would turn a rare coincidence into a visible failure, and the invariant that actually matters — never double-adding to a plan — is enforced by `apply_selection_round`'s re-check instead. The lazy-deadline transition goes in **one helper every round-scoped RPC calls**, not a hand-maintained list of which RPCs check it — a test should assert that a post-deadline `clear_selection_decision` or `finish_selection_participation` cannot mutate a round that should already have closed. `finalize_selection_round_candidates` must **re-derive and validate every candidate `recipe_id` against the caller's own household**, not just the round's ownership: the Edge Function calls it with the caller's ordinary JWT, so any client can call it directly with a hand-written array. Needs a pgTAP case that invokes it directly, bypassing the Edge Function entirely. Creation is fenced as a claim (`claim_token` + atomic status-guarded transition), so a delayed finalize from a superseded attempt can't activate a stale round.
- **Decision RPCs + close + results** — `record`/`clear`/`finish`, `close_selection_round`, `get_selection_round_results`, including the required cases that results *raise* rather than return anything during an active round, and that a **cancelled** round never reveals ballots to anyone but their owner.
- **`apply_selection_round`** — the highest-risk item in this milestone. Transactional, revalidating, idempotent on replay, locking the round *and* the target weekly plan before any duplicate filtering. Gets independent verification from someone who didn't write it.
- **Client solo flow** — This Week entry point, swipe screen (real gesture physics), review screen, behind `FLAGS.smartMealSelection`. Then a live solo walkthrough on a real device: no test can judge whether the swipe *feels* right.
- **Wire the scoring heuristic in *before* the client deck** (developer decision, 2026-08-24). Not a polish call: with the filter-only deck the eligible pool is ordered by recipe `id` and sliced, so a given library yields **the same cards every round** — invisible at three recipes, obvious at fifty. The deck isn't a deck until scoring lands, and `reason_codes` (which back 1d's per-card meta signal) come along with it.
- **Screen 1f's "Why this recipe" explanation modal is out of MVP** (developer decision, 2026-08-24) — deferred, not cancelled. It sits behind a tap on the recipe-detail modal, so few users meet it during a 12-card deck. **1d's per-card meta signal stays in**: it's visible on every card without a tap, and it's what separates "here are some recipes" from "here's why these."
- **Palette: `src/theme/tokens.ts` is canonical; do not repaint** (developer decision, 2026-08-24). `docs/design/help-me-choose-handoff/HELP-ME-CHOOSE.md` instructs using paper `#F5F0E8` / ink `#1C1B19` and "updating the older token list", claiming those are the shipped values. They are not — `tokens.ts` holds `#F7F3EC` / `#211D18`, i.e. what the handoff calls older. The design was sampled from screenshots and the ~2% shift is consistent with a Display-P3 round-trip. Following that instruction literally would repaint the entire app from sampled pixels. Recorded here because the handoff's wording invites someone to "fix" it later.
- **Smart Selection v1 heuristic** — the pure `server/selection/scoreCandidates.ts` module wired into the Edge Function, plus `reason_codes` and the "why this recipe" copy. Then a second live walkthrough, judging whether the deck actually surfaces interesting recipes.
- **Observability + rollout** — the `AnalyticsEvent` additions from the proposal's §11, `docs/prd-traceability.md`, and the flag flip.
- **Beta scope settled (developer decision, 2026-08-23): the beta may ship solo-only, but group is preferred if it can be made to happen.** So the group flow is *not* a beta gate — it must never become the reason Friends & Family Preview slips — but it is wanted, not merely tolerated. Practical consequence for sequencing: finish the solo flow through a live walkthrough first, then reassess group against whatever time remains before the beta. Do not interleave group work into the solo slices to "save a pass"; that trades a shippable solo flow for two half-finished ones.
- **Group flow — separate work item, not scoped here.** Participant picker, group waiting screen, results-bucket UI, `refill_selection_round` ("suggest a few more"), the Remind affordance. Carries one requirement from ADR-0027 decision 2a: a refill must not un-blind the round, so decisions on already-revealed candidates are frozen and only refill-added candidates stay swipeable. Without it, a participant can read the results screen, hit "suggest a few more," and flip an earlier vote knowing everyone else's. **Open question to settle before the flag flip:** whether the beta ships solo-only or waits for group, given that group is arguably the point of the feature for friends and family.
- **Push notifications are out of scope for this milestone entirely** — no push infrastructure exists anywhere in the codebase (no `expo-notifications`, no device tokens, no APNs config). The design's copy assumes it; v1 substitutes in-app awareness. Real push would be its own separately-scoped work item.

## Not yet triaged

Small items with no milestone assignment yet — moved here from `docs/current.md`'s old carried-forward list rather than left with nowhere to live. Needs its own pass to sort into milestones above; not force-sorted into this first draft.

- **"Send to → Keepsake" from Photos (and from Instagram/Pinterest).** Developer request, 2026-08-22, after importing a photo the long way: open the app, choose import-from-photo, then scroll to find the picture. **A share extension already exists** (`targets/share/`, ADR-0016, the App Group bridge in `modules/app-group-bridge/`), so this is an extension of working infrastructure rather than net-new. The two halves have very different lifts, and conflating them would misjudge the work:
  - **Photos — plumbing, and mostly already built.** `targets/share/Info.plist` declares only `NSExtensionActivationSupportsWebURLWithMaxCount` and `...WebPageWithMaxCount`, which is exactly why Keepsake doesn't appear in the Photos share sheet. `ShareViewController.swift` handles `UTType.url` and `UTType.plainText` attachments and writes a payload into the App Group container (`writeSharePayload`), which `src/appGroup/appGroupHandoff.ts` drains. A separate photo-import pipeline already exists (`src/photoImport/`, plus the `photo_import_*` migrations and Storage policies). So the work is: add image activation, handle an image attachment in the extension, carry the image through the App Group handoff (bigger payloads than a URL — worth checking the container-size and copy-vs-reference tradeoff), and route it into the photo path instead of the URL path. The idempotency-key design ADR-0016 established should carry over unchanged.
  - **Instagram/Pinterest — probably not a plumbing problem at all.** Those apps share a *web URL*, which the extension already accepts, so "Send to Keepsake" may well work there today. The real question is whether `import-recipe` can extract anything useful from those pages: both are JavaScript-heavy and partly login-walled, and the recipe usually lives in a caption or burned into an image rather than in JSON-LD. Worth a quick manual test of the existing share flow against a few real posts *before* scoping any work — the answer may be that extraction, not sharing, is the whole job, which makes it a very different item. The developer has no Instagram, Facebook, or Pinterest accounts, but his wife does and can test it (2026-08-22) — so validation is available, it just isn't self-serve. Plan the work around that: get a handful of real post URLs from her *first* and check what `import-recipe` actually returns for them, before committing to any extraction work. That test is cheap and decides the whole shape of the item — if the existing share flow already reaches those URLs and extraction is the only gap, this is an AI/scraping item, not a share-extension one. The Photos half stands on its own and needs none of this.
- **Bring Library's sort modes and filters to the Add Recipes screen.** Developer request, 2026-08-22, with the observation that they're arguably *more* useful there: Library is for browsing, but Add Recipes is where you're actively choosing what to cook, and it currently offers only a plain title search (`src/thisWeek/AddToThisWeekScreen.tsx:102` — a `title.toLowerCase().includes(query)` match) while Library has Smart / A-Z / Recent / Frequent plus category Filters. Encouragingly, most of the machinery is already extracted rather than screen-bound: `src/recipes/libraryFilters.ts` exposes `filterRecipes`, `activeFilterCount`, and `toggleCategoryFilter` as pure functions with their own tests, and both screens already call the same `fetchRecipes()`. The sort-mode labels and chip row still live inline in `LibraryScreen.tsx:36-48`, so the real work is extracting that control row into a shared component — the same shape as the `ServingsConfirmationStep` extraction in PR #93 — rather than reimplementing the logic. Worth deciding at pickup whether Smart sort means the same thing on a screen where you're picking *for This Week*, since its ranking may want the same This Week-overlap awareness Smart Meal Selection's deck uses.
- **[BETA-BLOCKING — see milestone 5]** **Scaling leaves a parenthetical alone when its unit isn't in the vocabulary: "1 cup (2 sticks)" doubles to "2 cups (2 sticks)".** Developer report, 2026-08-22, doubling a chai tea loaf. **Not the same bug as [PR #83](https://github.com/kraigstrong/Keepsake/pull/83) or [PR #89](https://github.com/kraigstrong/Keepsake/pull/89)**, despite looking identical from the outside — worth stating, because the reflex is to treat it as another `stripParentheticalAlternateUnit()` parsing gap and it isn't. In #83 the unit was recognized and a trailing period blocked the match; in #89 the parenthetical's internal structure (ranges, dual units) wasn't handled. Here the parse is working exactly as written: `stripParentheticalAlternateUnit()` calls `matchUnit()` on the parenthetical body and bails with `if (!unit) return text` (`server/units/parseQuantity.ts:253-254`), and **"stick" is not a unit this codebase knows** — `grep -i stick server/units/` returns nothing. So the annotation stays literal text and never scales.
  Two candidate fixes, and they are meaningfully different in risk:
  - **Add `stick` to the unit vocabulary** (1 stick butter = ½ cup = 8 tbsp). Narrow, obvious, and it's a genuinely common US measure. Fixes this line and nothing else.
  - **Scale a `<number> <word>` parenthetical even when the word is unknown.** More general, and more dangerous: it would correctly fix "(3 cloves)" but would also wrongly scale "(9x13 inch pan)" or "(2 inches thick)". Needs a real rule for which trailing words are quantities of an ingredient versus descriptions of equipment or geometry.
  Recommend the narrow fix first and only revisit the general one if more unknown-unit parentheticals show up. When picked up, add the real line to `server/units/realWorldIngredientCorpus.ts` — that corpus exists to be extended by exactly this kind of report, and its snapshot test would have caught a regression here.
- **Hero-image pre-cache logs a transient network drop as an ERROR, though it's already handled.** Developer report, 2026-08-22, while importing a recipe: `[logError] [Error: UnableToDownloadException: Unable to download a file: The network connection was lost.] {"context": "cacheHeroImage", ...}` — **the import itself succeeded**, which is the point. `cacheHeroImages()` in `src/sync/offlineRecipes.ts`'s caller (`src/sync/syncEngine.ts:23-32`) wraps each download in try/catch and logs the failure, and the header comment there already says this pre-cache is "additive, not sync-blocking." `RecipeDetailScreen.tsx:167` independently does `.catch(() => null)`, so a missing local copy degrades to fetching the signed URL later. So the behavior is correct and the message is noise. Two things to weigh when picked up: (a) this is the exact category PR #81 deliberately excluded from error logging — expected/transient outcomes that "would just be noise against genuine breakage" — so it likely wants a downgrade to a debug-level log or a narrower catch that only reports non-network failures; (b) there is no retry, so a recipe whose hero image drops mid-sync stays uncached until some later sync happens to re-attempt it, which is probably fine but is currently unstated. Not diagnosed further and deliberately not fixed — logged at the developer's request.
- **`authenticated` holds TRUNCATE on every public table (latent, not reachable today).** Found by `security-check` during milestone 4's schema slice, 2026-08-21. Supabase's default privileges grant `REFERENCES,TRIGGER,TRUNCATE` to `anon`/`authenticated` on new tables; our migrations then add `SELECT` and deliberately withhold INSERT/UPDATE/DELETE. TRUNCATE is **not** filtered by RLS, and a live `set local role authenticated; truncate public.selection_decisions;` succeeds in local Postgres. **Not currently exploitable:** `anon` and `authenticated` are `NOLOGIN`, so nobody can connect directly as them, and PostgREST — which does switch to `authenticated` — only ever issues the SQL it generates from REST requests, never TRUNCATE. So this needs a direct database connection as `authenticator` (a server-side secret) to reach.
